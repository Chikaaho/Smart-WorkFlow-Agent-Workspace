本轮版本为 **0.2.1**。目标是在本地可运行环境中持续接收、修复并逐项验收缺陷，Owner 明确宣布“全部结束”后再完成状态同步、分支合并、0.2.1 发布和发布后同步。

本任务跨 Server、Web、多个会话及正式发布链，按 **L 级**跟踪。唯一缺陷入口为 `product/0.2.1-bugfix/items.md`。当前不预置缺陷，不扩大为新功能开发，也不改变现有 P 编号、正式功能数或历史验收结论。

## 分支与本地服务

Executor 开始后先核实三仓实时状态，不沿用历史提交快照：

1. Server 与 Web 分别更新远端引用，确认当前 `develop`、跟踪关系、ahead/behind、未提交及未跟踪内容；保护用户已有改动，尤其不得覆盖已记录的 `vite.config.ts` 在途内容。
2. 两个业务仓分别从核实后的 `develop` 建立并推送 `codex/0.2.1-bugfix`，设置同名远端跟踪。若某仓存在无法安全带入或隔离的本地改动，保留现场并报告精确对象，不重置、不清理、不夹带。
3. 根仓保持现有规划分支，承载本方向、台账、回执及必要 gitlink 更新；规划文档不要求另建业务分支。
4. 按 `project.md` 和两端工程宪法启动本地 Server 与 Web。服务必须有稳定会话或任务身份、可持续读取的日志与健康结果、明确停止和清理动作；禁止 `nohup`、脱离进程或无法观测的后台启动。
5. 本地服务启动完成后回传访问入口、健康结果、使用的非秘密环境说明、进程或会话身份及停止方法。凭据、Token、密钥和连接秘密不得写入台账或回执。

分支初始化回执写入 `product/0.2.1-bugfix/receipts/branch-init-021-01.md`。完成条件是两仓分支来源、远端跟踪、工作树保护和本地双端服务均可回读；仅创建分支、仅保留进程句柄或仅报告端口不算完成。

## 缺陷修复与逐项验收

修复阶段由 Owner 与 Executor 持续对话推进，按以下规则处理：

- Owner 提交新缺陷后，Executor 在台账分配下一个稳定编号，记录问题、复现条件、预期行为和附件或目标对象。
- Executor 先复现并确认范围，再实施修复。单项风险仍按实际影响判断；触及认证、权限、租户隔离、数据模型、迁移、公共 API 或跨仓契约时，不因“Bug”名称降低验证强度。
- 每项完成后先做受影响路径的最小充分验证，再提交并推送内聚批次。提交信息遵循 Angular/Conventional Commits，主题使用中文；只暂存本项文件，不夹带其他改动或运行产物。
- Executor 将单项状态更新为“待验收”，给出本地复测入口、操作步骤和实际结果。UI 缺陷提供用户可见、可交互的浏览器结果；接口、权限、数据或流程缺陷按风险提供对应 HTTP、数据库或运行行为证据。
- Owner 验收通过后，同一编号标记“已修复 / 通过”；未通过时记录实际差异，沿原编号继续修复，不换号、不把执行自验当成 Owner 通过。
- 已通过项锁定。只有相关实现再次变化、新增反证或证据快照失效时，才复验受影响部分。
- 每个编号的执行回执追加到 `product/0.2.1-bugfix/receipts/`，命名为 `B021-NNN-<轮次>.md`。原始输出完整留存在可读位置，回执只写结果、位置和适用范围。

首轮证据清单一次确定为：问题与对象、复现结果、必要变更摘要、适用测试或实际行为结果、提交与远端回读、Owner 验收结论。证据以行为是否符合预期为准，不把附件数量或文字格式当成独立验收门槛，不执行非必要产物哈希或整包校验。

## 服务与数据边界

- Executor 只管理本轮由自己启动且身份明确的本地进程，不按端口或进程名批量停止用户已有服务。
- 非即时任务必须有完成条件、进展观察、任务特定超时、取消和清理路径；状态未变化时不空转轮询。
- 默认不清库、不重置用户数据、不改写迁移历史、不读取或传播秘密。确需破坏性动作、真实凭据、MFA 或外部环境权限时，先提交精确对象、影响和恢复方案。
- 验收数据按单项需要创建和清理；不能用近似用户、近似租户、替代数据库或其他实例冒充目标对象。

## Owner 宣布结束后的交付链

Owner 明确宣布“全部结束”是修复阶段转入收口的唯一条件。收到该指令后：

1. Executor 冻结台账，汇总全部编号的修复、Owner 通过、延期及未通过结论；停止接收未获 Owner 明确重开的新范围。
2. 按已验收事实先同步 `knowledge/` 权威状态，再按授权同步受影响的 `memory/`、`todo/`、项目声明和交接；本轮缺陷修复默认不新增正式业务功能数、不核销 P 编号。
3. Planner 读取回执和实际行为证据，复核冻结范围及同步口径；纯文字差异由规划直接消解，真实行为缺口仍回原编号处理。
4. Executor 将 `codex/0.2.1-bugfix` 依次合入各自 `develop`、完成 0.2.1 版本及生效发布配置收敛，再合入 `main`；操作前报告远程、分支、精确范围、ahead/behind 和工作树状态，合并推送后回读远端。
5. 沿现有发布通道发布 **0.2.1**，分别核实正式版本、开发版本、制品版本、CI 结果及实际部署版本。发现版本来源不一致时修复真实配置，不用更新摘要替代。
6. 发布后再次同步并复核分支、提交、版本、制品、部署、缺陷摘要和唯一下一动作；全部一致且授权内剩余动作清零后结束交付。
