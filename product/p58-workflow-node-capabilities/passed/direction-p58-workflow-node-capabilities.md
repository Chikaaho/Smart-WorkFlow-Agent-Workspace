## 1. 背景与方案选择

P57 已建立统一节点契约、启动发现、唯一注册、发布校验、运行扩展和前端能力清单，但生产节点仍只有 START、APPROVAL、END。当前审批只支持固定单用户且 DESIGNATED 数组只取首人；会签、分支、抄送均无生产实现；审批拒绝路径不发布通知事件；审批历史没有意见、动作或低代码表单数据。

P58 采用“共享基础先行、节点逐阶段闭环”的方案：先建立所有人员型节点共用的选人契约、受控表达式和审批意见低代码契约，再依次完成普通审批、会签、分支、抄送与通知。每种能力都必须通过 P57 的统一节点注册、设计、保存、发布和运行链，不得为某个节点建立独立硬编码路径。

不采用一次性平铺各节点的做法，因为选人、审批意见、事件和通知记录是多个节点的共同依赖；如果各节点分别实现，会形成配置模型、权限校验、用户快照和失败处理的多套权威。

## 2. 产品目标

1. 管理员能够使用固定用户、角色、流程表达式和后端流程适配器四种统一策略配置节点参与人。
2. 普通审批支持多人候选、任一有效候选完成后原子结算，并完整记录实际处理人与其他候选人的失效结果。
3. 会签支持所有人、任一人和比例三种结算方式，具有确定的计数、提前结算、并发和审计语义。
4. 流程支持可视化普通条件分支，设计、发布和运行使用同一分支配置。
5. 抄送节点向命中的全部用户生成可查询、可审计的抄送记录，不阻塞人工审批。
6. 通知节点及审批事件能够发送站内信，并通过统一渠道 SPI 预留短信、飞书、钉钉、企业微信、公众号和小程序等第三方能力。
7. 每个审批或会签节点默认使用“备注”意见，也可关联轻量低代码审批意见表单；意见数据可以安全读取流程主表单数据进行初始化联动，并与审批动作和历史版本一起长期追溯。

## 3. 关键规划裁决

### 3.1 通用参与人选择契约

- 建立单一参与人配置与解析契约，至少支持 `FIXED_USER`、`ROLE`、`EXPRESSION`、`ADAPTER` 四类稳定策略；审批、会签、抄送和通知节点共同使用，不能各自定义一套人员配置。
- 固定用户保存稳定用户标识；角色保存稳定角色标识，运行时解析同租户、启用且有效的角色成员；结果按用户标识去重。
- 流程表达式由前端可扩展选择器生成结构化配置，运行时由后端基于流程变量、主表单数据和受控上下文解析。前端选择器只帮助生成配置，不是运行期权威。
- 流程适配器由后端 Bean 实现统一 Resolver SPI，以稳定适配器标识注册；能力清单只暴露允许配置的标识和元数据，不暴露 Bean 名、类名或任意调用入口。
- 禁止 `eval`、`new Function`、动态远程脚本和管理员直接提交任意可执行 JavaScript。前端数据联动与表达式选择使用 AST/白名单函数/只读变量上下文；后端重新校验配置并对运行结果执行租户、用户状态和权限约束。
- 节点进入时解析并保存参与人快照。相同用户去重；固定配置在发布时不存在即拒绝，动态策略运行时零命中则进入明确失败或节点声明的受控空结果，不能静默指派其他用户。

### 3.2 普通审批节点

- 普通审批保留 APPROVAL 稳定类型并扩展配置，不另建平行审批节点。
- 选人策略可命中一个或多个候选人。节点生成一个共享审批范围；任一有权候选人首先成功提交有效动作后，该节点原子结束。
- 并发提交只能有一个胜出者；后续提交必须返回“节点已由谁、以何动作处理”的确定结果，不能重复推进流程。
- 记录候选人快照、实际处理人、审批动作、处理时间、审批意见与其他候选人的失效原因。不得继续只依赖 Flowable assignee 和历史时间表达完整业务审计。
- 必须支持的动作：
  - `APPROVE`：完成当前节点并进入正常后续路径；
  - `RETURN`：退回到本次实例已经经过、且设计时允许退回的人工审批节点；目标节点及表单数据恢复规则必须明确，禁止跳到未经过节点；
  - `REJECT`：结束当前流程并形成拒绝终态；
  - 后续动作扩展使用稳定动作契约，但转办、委托、加签、抢办、撤回不纳入本轮。

### 3.3 审批意见低代码表单

- 每个普通审批和会签节点默认生成一个“备注”字段；管理员可以改为关联一份已发布的审批意见表单版本。
- 审批意见表单采用低代码表单基础能力，但只开放轻量控件：单行文本、多行文本、数字、单选、多选、下拉、日期/时间和说明文字。附件、图片、富文本、子表格、外部数据源及其他高级控件不进入本轮。
- 支持必填、长度、数值范围、选项合法性、显隐和字段联动。审批动作提交时必须由后端依据绑定的表单版本重新校验，不能只依赖前端校验。
- 管理员可配置“流程主表单/流程变量 → 审批意见字段”的初始化映射。审批页进入时，前端在只读页面变量上下文中使用受控表达式计算初值；用户可编辑字段按配置决定是否允许覆盖。
- 初始化表达式不得修改流程主表单、调用网络、访问浏览器全局对象或执行任意脚本。后端提供权威流程数据快照，并校验表达式声明、目标字段和提交结果；前端联动结果不构成权限依据。
- 每次提交保存不可变意见快照，至少关联流程实例、节点实例、任务、处理人、动作、意见表单定义及版本、初始化来源摘要、最终数据和时间。后续修改表单不得改变历史意见展示。
- 会签中每位参与人保存独立意见；节点结算结果另存聚合摘要，不能用最后一人的意见覆盖其他人。

### 3.4 会签节点

- 新增稳定会签节点类型，通过 P57 统一契约进入能力清单、配置、发布校验、翻译和运行链。
- 进入节点时解析参与人并冻结去重后的分母；运行中角色成员变化不改变本次会签分母。
- 三种结算模式：
  - `ALL`：全部参与人均 `APPROVE` 才通过；任一人 `REJECT` 时可立即结算不通过；
  - `ANY`：第一份有效审批动作立即决定节点结果；
  - `RATIO`：配置通过比例，按“通过人数 / 初始有效参与人数”计算；达到阈值立即通过，当剩余人数全部通过也无法达到阈值时立即不通过。
- 比例使用整数百分比并明确边界，发布时拒绝小于 1% 或大于 100%、空参与人及非法组合。重复操作不重复计数，并发计数必须原子化。
- `RETURN` 属于流程控制动作：任一有效参与人提交 RETURN 时终止本轮会签并按配置目标退回；其余待处理任务统一取消并保留取消原因。
- 结算后记录参与人快照、每人动作与意见、通过/拒绝/未处理计数、阈值、结算原因和被取消任务，支持实例详情完整回看。

### 3.5 普通分支

- 新增普通排他条件分支，使用稳定节点类型和边条件配置；不把分支逻辑塞入 APPROVAL 或前端私有字段。
- 一个分支节点允许多个条件出口，并且必须有且仅有一个默认出口。非默认出口包含稳定分支标识、名称、优先级和结构化条件。
- 条件读取流程变量和主表单数据，使用与通用表达式一致的受控表达式能力；禁止任意脚本。按显式优先级求值，第一条为真者命中；均不命中时走默认出口。
- 发布时校验出口数量、默认出口、优先级、字段引用、操作符、值类型和目标节点；运行时类型不一致或表达式失败应形成明确失败记录，不能悄悄走默认分支。
- 运行轨迹必须记录实际命中的分支、条件版本和输入摘要，使结果可以解释和回放。

### 3.6 抄送节点

- 新增抄送节点并复用通用参与人解析；向命中的全部有效用户发送，按用户去重并保存进入节点时的收件人快照。
- 抄送形成独立业务记录，并通过既有站内信入口让收件人查看流程摘要；抄送人没有审批权，不能完成或改变流程任务。
- 抄送节点完成持久化投递后继续流转。动态策略零命中、部分用户失效或投递失败必须留下明确状态和审计；不得显示成功却没有收件记录。
- 收件人只能查看其权限范围内的流程摘要和允许展示的表单字段，不因收到抄送获得流程管理或完整数据权限。

### 3.7 通知节点、审批事件与渠道扩展

- 新增统一通知事件契约，至少覆盖待审批、审批通过、审批退回、审批驳回、流程通过和流程拒绝；审批不通过必须通知流程发起人，且通知可关联实际节点、处理人和意见摘要。
- 新增通知节点，允许配置参与人、模板和渠道；站内信是本轮必须真实闭环的内置渠道。
- 所有通知统一经过现有 NotifyFacade 业务入口并生成发送记录，不能由 BPM 模块分别直写站内信表或调用厂商 SDK。
- 建立统一渠道 SPI，使用稳定渠道标识、统一消息模型、发送结果、外部消息标识、失败原因、超时和幂等键。预设短信、飞书、钉钉、企业微信、公众号、小程序的渠道类型和注册接缝。
- 本轮不要求接入真实厂商账号或交付各厂商生产 Adapter；必须用一个隔离验证 Adapter 证明新增 Bean 无需修改中心分派即可注册、发送、记录结果并可清理，且验证实现不得进入生产能力目录。
- 站内信持久化成功后才能声明站内信投递成功；第三方通知失败不得伪装成功。通知节点的失败策略支持“阻断并等待处理”或“记录失败后继续”，由节点明确配置。

### 3.8 历史兼容与单一权威

- 既有 START、APPROVAL、END、`graph_json`、DESIGNATED 与 skeleton 路径必须保持可用；旧 APPROVAL 配置读取时按兼容规则解释为固定用户普通审批，不能静默改变已发布流程语义。
- 新发布流程必须使用 P57 统一节点能力和本方向的新配置契约。不得新增前端静态节点目录、中心类型 `switch`、独立选人表或 BPM 私有通知通道。
- 历史已发布 BPMN、运行中实例、外部租户 `graph_json` 和通知记录未被仓库事实证明不存在。执行层发现真实存量时必须先提供兼容矩阵和迁移/不迁移方案，不得直接改写历史定义。
- 发起路径现有 skeleton 与图发布流程并存。本轮只允许在保持历史兼容的前提下让新节点进入图发布流程，不以删除 skeleton 作为完成条件。

## 4. XL 阶段边界

### 阶段 A：共享契约与审批意见基础

统一参与人配置/解析、受控表达式、参与人快照、审批动作和意见数据模型；完成默认备注、轻量审批意见表单绑定、版本快照及主表单初始化联动。阶段通过不等于功能完成。

### 阶段 B：普通审批完整闭环

完成多人候选任一处理、原子结算、APPROVE/RETURN/REJECT、实际处理人和候选失效审计，并补齐审批退回/驳回站内信事件。

### 阶段 C：会签完整闭环

完成 ALL/ANY/RATIO 多人任务、每人意见、并发幂等、提前结算、退回和实例详情聚合回看。

### 阶段 D：条件分支完整闭环

完成设计器多出口配置、结构化条件、默认分支、发布校验、真实运行命中及轨迹解释。

### 阶段 E：抄送与通知扩展

完成全员抄送、通知节点、站内信闭环、统一渠道 SPI 和隔离第三方 Adapter 扩展证明。

### 阶段 F：组合流程与整体回归

以同一真实流程完成“发起 → 普通审批 → 条件分支 → 会签 → 抄送/通知 → 通过或拒绝终态”，覆盖审批意见低代码联动、历史回看、失败路径、权限隔离和存储一致性；全量回归后才可提交功能级 completion receipt。

## 5. 功能级验收标准

1. 四类参与人策略均通过统一契约配置、发布校验和运行解析；角色/表达式/Adapter 结果具有租户、有效用户、去重、零命中和快照证据。
2. 前端扩展选择器与审批意见数据联动不使用 `eval/new Function` 或动态远程脚本；非法表达式、越权变量和篡改提交被明确拒绝。
3. 普通审批命中多人时，所有候选均能看到同一待办范围；任一候选首先提交后节点只推进一次，其他候选得到已处理结果并留下失效审计。
4. 普通审批的 APPROVE、RETURN、REJECT 均有真实请求、运行轨迹、实例状态和持久化证据；退回目标合法，驳回形成一致流程拒绝终态。
5. 默认备注与自定义审批意见表单均可真实提交；必填、显隐、联动和后端校验成立，主表单数据能够在进入审批页时按受控表达式初始化意见字段。
6. 每条审批意见绑定正确流程实例、节点、任务、处理人、动作和表单版本；修改意见表单后历史意见仍按原版本完整展示。
7. 会签 ALL、ANY、RATIO 三模式分别以固定输入完成通过和不通过案例；比例边界、提前结算、重复请求和并发提交计数准确。
8. 会签中每人意见独立保留，聚合结果、未处理任务取消原因和最终实例状态一致，不出现任务已结算但业务状态仍运行的矛盾。
9. 条件分支能够设计、保存、发布并按流程数据进入正确路径；默认分支、多条件优先级、非法配置、表达式失败和零错误部署均有行为证据。
10. 抄送节点向所有命中且去重后的用户生成记录和站内信；收件人可查看授权摘要但不能审批或越权查看完整流程数据。
11. 审批退回与驳回均产生站内信通知，流程发起人能从通知进入对应流程结果；通知记录与实际动作、意见摘要一致。
12. 通知节点通过站内信真实发送；隔离第三方 Adapter 经启动发现后完成成功、失败、超时和幂等行为，生产目录和产物中不存在验证实现残留。
13. 节点能力清单、前端设计器、保存、发布、翻译和运行只使用 P57 统一权威；新增策略、节点或渠道不需要修改平行固定目录或中心分派。
14. 既有 START→APPROVAL→END、DESIGNATED、skeleton、历史 `graph_json` 和已有站内信路径保持成立；真实存量边界被如实披露。
15. 同一真实组合流程覆盖普通审批、审批意见联动、分支、会签、抄送/通知及通过/拒绝结果；页面、接口、Flowable 轨迹、业务状态和持久化互相一致。
16. 后端、前端、Mock、数据库迁移、权限与受影响全量回归通过；回执计数必须来自原始输出，并区分聚焦验证与正式全量基线。

## 6. 证据要求

- 每阶段提交追加式回执，绑定 checkout/提交、固定输入、真实身份、原始命令、请求响应、DOM、运行轨迹、数据库前后值、退出码和清理结果。
- 人员型节点至少用两个普通用户和一个角色验证候选解析、权限、去重和越权拒绝；不得只用管理员身份或 Mock。
- 审批和会签必须提供并发/重复请求证据，证明流程只推进一次、计数不重复、其他任务有明确终态。
- 审批意见必须提供表单版本前后变化、初始化联动、用户编辑、后端校验失败和历史只读回看证据；测试类名、DOM 字段存在或前端自校验不构成通过。
- 分支必须以同一已发布定义运行至少两个条件路径和默认路径，并对非法表达式证明零部署残留。
- 通知必须绑定业务事件、消息记录、收件箱 DOM 和渠道结果；“事件已发布”或“Adapter Bean 存在”不能替代真实投递与持久化证据。
- 隔离表达式/节点/渠道验证实现必须在最终生产构建产物中零命中，并清理测试用户、角色、流程、意见、抄送和通知数据。

## 7. 非目标

- 不实现转办、委托、加签、抢办、撤回或任意历史节点跳转。
- 不开放任意 JavaScript、远程脚本、浏览器全局对象或由前端决定权限/候选人的能力。
- 不把完整低代码表单设计器复制进审批意见；附件、图片、富文本、子表格、外部数据源及高级布局不在本轮。
- 不交付短信、飞书、钉钉、企业微信、公众号、小程序的真实厂商账号、生产 Adapter 或现场联调；本轮交付统一 SPI、预设渠道类型和隔离扩展证明。
- 不全面重做流程设计器视觉体系，不顺带完成流程监控耗时分析、人工干预或其他 P4 缺口。
- 不删除 skeleton 兼容入口，不静默迁移或改写外部存量流程、意见和通知数据。

## 8. 风险与停止条件

- **脚本安全风险**：若必须依赖 `eval/new Function`、动态远程脚本或把客户端表达式结果作为权限依据，停止并回传替代方案。
- **并发结算风险**：普通审批或会签在并发下无法证明单次推进、单次计数和一致终态时，不得进入下一阶段。
- **历史语义风险**：发现真实运行实例或已发布定义会被新审批配置重新解释时，停止自动迁移并提交兼容方案。
- **双权威风险**：如实现需要在 P57 注册表之外维护节点目录，或为不同节点复制选人、意见、通知逻辑，不得继续。
- **权限与租户风险**：动态选人、意见联动、抄送或通知暴露跨租户用户/表单数据时，立即停止并修正边界。
- **外部渠道风险**：缺少厂商凭据不是本轮 SPI 完成的阻塞；不得虚构真实厂商发送成功。
- 同类实现或验证连续失败两次，按治理规则升级并返回仅剩缺口，不得用结构证据替代真实行为。
