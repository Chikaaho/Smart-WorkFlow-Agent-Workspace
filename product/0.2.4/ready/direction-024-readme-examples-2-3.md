## 1. 场景原文（来源：todo/ch-apaas-project-update.md §3.2、§3.3）

- **示例二（校园大门流量异常）**：某校园的其中一个大门有一天突然出入校流量异常，先从流程和知识库搜索近期有没有相关活动或者校园活动，再联网搜索近期是否有公开活动或者特殊节日；如果符合特殊情况，仅作日志记录并发起 P1 工单；如果不符合任何正常情况，发起 P0 工单并给负责人发送告警，以及短信、电话提醒。
- **示例三（MES 温度研判）**：某厂房 MES 流程告警阈值为机器温度 80℃，必须停机温度 85℃，常温 75℃。偶尔人工加料时会超过 80℃。业务人员可以自己配置 Agent 知识信息、输入样本。短时间内超过 80℃时判定异常，发起工单并告警；缓慢上升超过 80℃且小于 85℃时，判定符合正常操作行为，仅作记录；超过 85℃时按正常紧急告警流程处理。

示例一已于 0.1.9 验收通过（product/readme-first-example-acceptance），其搭建方式、证据层级和协作方式可直接沿用。

## 2. 做法与范围

- **配置优先**：先用平台已有能力搭建两个示例，包括表单、流程/BPM、Agent graph（LLM、知识检索、工具、条件分支）、知识库、IoT/MQTT、预约、通知和权限。**Owner 判断现有功能已足以支持两个示例（2026-11-06）**，本版重心是搭建、验证和修复缺陷。只有现有配置确实表达不了的环节，才补平台能力；能力要做成通用、可配置的，不写示例专用的硬编码分支。
- **通知渠道（Owner 2026-11-06 定）**：本版只用**邮件和站内信**。短信、电话尚未采购，不在本版范围内；示例原文中的“短信、电话提醒”由邮件和站内信承接，并登记为后续待办。
- **范围内（已预授权，不需要再申请）**：
  - 修复阻断或使两个示例偏离预期的缺陷。
  - 搭建中确实发现、两个示例必需、且落在现有模块内的小缺口，在回执中逐项写明为什么现有配置表达不了。
  - 这些能力的权限、租户隔离和必要迁移。
- **需要 Owner 裁决的情况**：新建独立业务子系统，例如脱离表单和流程的全新工单产品；引入需要采购或签约的外部供应商；改变示例原意。遇到这些情况，只就该项停下，其他项继续推进。
- **外部依赖**：联网搜索、邮件发送（SMTP）等真实服务需要账号或 Key 时，由 Owner 在页面录入，规划和执行都不得读取或外传秘密。接口层用可控对端完成验证。Owner 提供凭据后，再补跑一次真实链路；没有凭据时，如实记为外部依赖，不阻塞其他验收项。
- **不纳入**：短信、电话渠道（未采购）；示例一的回归重做（只在共用能力有变化时做受影响验证）；P20；P62 性能；Agent 逐节点进度事件；多模态。无关问题登记到待办。

## 4. 验收标准（固定，首轮一次列全）

### 示例二 S2

| ID | 通过条件 |
|---|---|
| S2-01 触发 | 大门流量异常事件（含大门标识、时间窗口、实际流量与常态基线）能经 IoT/MQTT 遥测或接口进入平台，并自动启动研判；也可以手工发起。事件和研判实例可以互相回查。 |
| S2-02 内部检索 | 研判过程中实际查询近期流程记录和知识库中的校园活动；命中和未命中的内容都记录在执行轨迹中。 |
| S2-03 联网搜索 | Agent 实际调用联网搜索工具，记录查询词和结果摘要。工具不可用或失败时要显式记录，不能静默当作“无特殊情况”。 |
| S2-04 判定分支 | 判定为特殊情况时，只记日志并发起 P1 工单；判定为无正常解释时，发起 P0 工单并给负责人告警。判定理由要持久化。研判失败或无法判定时，按 P0 升级处理（失败即升级）。 |
| S2-05 工单与告警 | 工单有级别、负责人、来源事件和处理状态，可在页面处理和回查。P0 时实际给负责人发出站内信和邮件告警，两个渠道的发送结果分开记录。站内信要在页面上实际可见；邮件已配置 SMTP 的发真实邮件，没有配置的用可控对端验证，并按第 2 节外部依赖处理。 |

### 示例三 S3

| ID | 通过条件 |
|---|---|
| S3-01 业务配置 | 业务用户在页面上就能维护常温、告警、停机三个阈值（75/80/85）、“短时间”窗口或斜率参数，以及 Agent 知识和输入样本，不需要改代码或重新部署；有权限控制。 |
| S3-02 数据接入 | 机器温度遥测按设备和时间持久化，可以按时间窗口回查。 |

| S3-04 可追溯 | 每次判定都记录输入序列、所用规则或样本、Agent 理由和产生的动作，可以在页面回查。 |
