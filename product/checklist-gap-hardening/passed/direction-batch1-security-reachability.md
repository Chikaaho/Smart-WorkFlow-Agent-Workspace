# 需求方向：checklist-gap-hardening 第一批 —— 安全与可达性缺口修复

> 规划层需求方向文档（D75 待确认→已由用户授权"规划层推荐即定"）。执行层自行拆 Step、设计执行/测试方案、自主闭环，完成后提交功能级完成回执，规划层最终验收。

## 背景

2026-08-12 功能清单全量审计（`search_fallback/feature-checklist-full-audit.md`，89/89 条核对）暴露一批"清单虚高"缺口（knowledge/known-issues.md I31-I44，Step5 已完成状态同步）。其中两项属于**安全缺陷或交付断裂**性质，风险等级显著高于其余记录性缺口，用户已确认按规划层推荐优先修复：

1. **停用用户仍可登录（I33，高）**：`UserDetailsProviderImpl` 登录加载链路（审计定位 L55-123）不校验 `SysUser.status`，账号停用形同虚设——清单 M01-F02-02"账号启用/停用"因此从 ✅ 降 🟦。
2. **M10 定时任务/文件存储生产菜单不可达（I43/I44，中）**：`JobList.vue`/`JobLog.vue`/`StorageList.vue` 功能代码与后端全链完整（job-scheduler / storage-multi-provider 两功能均已 PASSED），但生产菜单树（V6/V10/V15/V26 菜单 SQL）无 job/storage 菜单行，仅 dev:mock 的 seeds.ts 注册——正式环境用户无入口，属"已完成功能未交付"断裂。清单 M10-F03-01/F06-01 因此从 ✅ 降 🟦。

## 目标

1. **登录停用校验**：登录认证链路对 `SysUser.status` 为停用状态的账号拒绝登录（含拒绝签发 access/refresh token），并对已停用账号的既有 refresh token 刷新路径做同等拦截（若刷新链路同样不校验 status，一并覆盖；若已有校验，回执中给出证据即可）。错误提示语义区分"账号或密码错误"与"账号已停用"由执行层按安全惯例自行裁定（防用户枚举 vs 提示友好，两者权衡执行层决定并在回执说明）。
2. **生产菜单 seed**：为定时任务（job：任务管理+执行日志，按前端现有页面结构）与文件存储（storage）补生产菜单树 Flyway seed（h2/postgresql 双份），使正式环境菜单可达，层级/父目录/权限标识遵循既有菜单 seed 先例（V6/V10/V15/V26）与 seeds.ts mock 中的现有结构。
3. 两项完成后，按 system.md §3.3 第10项（本轮新固化）执行知识库全量同步：清单 M01-F02-02、M10-F03-01、M10-F06-01 状态按交付实际回升（预期 🟦→✅，以执行层核实为准）；known-issues I33/I43/I44 补修复记录；current-status.md 清单计数同步。

## 非目标

- **不做** M02-F04-01 数据权限（DataScope）完整落地——数据范围控制横切所有业务查询，是独立大功能，留待后续轮单独规划（known-issues I 对应条目维持待排期）。
- **不做** I31-I44 中其余记录性缺口（M01/M02 关联筛选要素、M03 控件库/删除、M05 删除/过滤等）——按需另行排期。
- **不做**验证码/密码策略/登录失败锁定（M02-F06-01 的 SPI 空接口维持现状，非本轮范围）。
- **不改**登录认证双 token 架构本身（auth-seam-completion 已完结的结构不动，只加 status 校验点）。
- **不新增**菜单管理配置 UI（M02-F02-01 范围，不在本轮）。

## 影响范围（预期，最终以执行层探索为准）

- 后端：`sw-security`（UserDetailsProvider 登录/刷新链路）、`sw-bootstrap` Flyway 新版本菜单 seed（root 路径 V26 之后的空闲版本号，h2/postgresql 双份；agent 路径 V28 已占用，注意两条迁移路径版本互不冲突，以执行层现场确认为准）
- 前端：预期零改动或仅菜单相关适配（页面/路由已存在）
- 测试：登录停用/刷新拦截需新增单测覆盖；菜单 seed 迁移需通过既有 Flyway 校验测试
- 基线参考：后端 426 tests / 前端 63f/552t（2026-08-12 CONFIRMED）

## 关键方向性判断

- **两项打包一轮**：都是"小改动+高风险/高价值"，共同来源于同一次审计，一轮交付一次验收，避免碎片化。
- **停用校验位置**：应落在认证链路服务端（登录+刷新两个入口都拦截），不能只做前端提示——具体落点由执行层依据现有 `UserDetailsProviderImpl`/token 刷新实现自行设计。
- **菜单 seed 是 Flyway 迁移而非手工 SQL**：正式环境交付必须走迁移链，与 V26 agent 菜单迁移先例同构。

## 验收标准（规划层最终验收依据）

1. 停用账号登录被拒绝（新增测试证明），停用账号 refresh 刷新被拒绝或给出"已有校验"证据；启用账号登录回归不受影响。
2. 生产菜单 SQL（h2/postgresql）包含 job/storage 菜单行，层级与权限标识与既有先例一致；Flyway 全链迁移测试通过。
3. 后端全量测试 BUILD SUCCESS 0 failures（基线 426+新增）；前端四连（test/typecheck/lint/build）全绿。
4. 知识库全量同步完成（§3.3 第10项）：清单状态回升、I33/I43/I44 修复记录、回执含"清单变更明细+知识库触碰文件清单"。
