## 2. 问题（进入阶段 3 前补齐）

- **U1（阻断）缺表结构一致性检查。**
  - `SeedComparisonTest` 只比“共有列”。如果某个方言整列缺失，或者多出一列，比对结果仍然是 0 差异。
  - 列缺失恰恰是手工转换和生成脚本最容易出的问题。7 个非 PG 方言里，SQL Server 用生成基线，DM 由 Oracle 转换而来。
  - 新增表结构一致性测试，以 PG 0.4.0 终态为基准，对每个实测库（MySQL 5.7/8.0、MariaDB、Oracle、openGauss、SQL Server）比对三项：
    - 表集合；
    - 每张表的列集合；
    - 每列是否可空。
  - 允许的差异（如 `sw_knowledge_vector`、pgvector 列）用白名单列出，并写明原因。
  - DM、Kingbase 做静态比对：解析脚本得到表名和列名，再与 PG 比。
  - 测试结果要写进最终回执的矩阵。
- **U2 SQL Server 用终态基线加占位脚本，接受，但要补维护规则。**
  - 首次支持、没有升级路径，用终态基线合理。生成工具和输入都已入库。
  - 需要补三点：
    - 1）这是一次方案偏离：方向要求“同一版本序列”，现在 SQL Server 的版本号相同，但内容是占位脚本。回执和部署文档都要标明。
    - 2）后续维护规则：PG 以后修改**可重复脚本**（`R__`）时，SQL Server 的占位脚本不会跟着重跑。要写进 Server 工程文档：凡是改 PG 迁移或种子，必须同时改 SQL Server 增量脚本；同时加一个门禁，PG 的 `R__` 校验和变了而 SQL Server 没有对应改动时就失败。办法是在测试里固化当前清单。
    - 3）`pg_dump` 的输入是 PG 18。请说明 UAT 的 PG 大版本和 dump 来源，确认 dump 内容只由迁移链产生，不含手工数据。
- **U3 Kingbase、openGauss 的兼容模式检查。**
  - KingbaseES V8 初始化时有数据库模式（Oracle、PG、MySQL）。Oracle 模式下 `''` 等于 NULL，和 PG 脚本的语义不一致。
  - Kingbase README 要写明按 PG 模式初始化。`DatabaseCompatibilityGuard` 要像 openGauss 一样强制检查兼容模式；如果检查用的系统参数名没法实测，就在 README 里列出来，请 Owner 验证时确认。
- **U4 证据的提交身份。**
  - 矩阵写的是“本批最终工作树（提交前）”。要补一句：执行矩阵时的工作树与提交 `02598b8c` 完全相同，用 `git diff` 为空或 `git stash list` 证明。
  - 如果不能证明，就在 `02598b8c` 上至少重跑一个库（建议 SQL Server）。
