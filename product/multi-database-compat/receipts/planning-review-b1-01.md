## 2. 问题

- **R1（阻断 B2 实库）启动检查执行得太晚。**
  - `DatabaseCompatibilityGuard` 是 `ApplicationRunner`，要等 Spring 上下文启动完成才执行。这时 Flyway 和 `SwVendorMigrationRunner` 早已跑完。
  - 结果是在 latin1 或 `_ci` 排序的 MySQL 上，表会先按错误的字符集和排序规则建好，之后才报错。这样起不到“不符合就拒绝启动”的作用。
  - 必须改为在任何迁移执行前检查，例如放进 `FlywayConfiguration` 的迁移策略里，在 Runner 入口先调用。
  - 补一个测试：检查不通过时迁移一条都不执行。
  - 修完才能连接真实 MySQL、SQL Server、Oracle。
- **R2 MySQL 5.7 的资源段探测偏离了裁决。**
  - 审查 01 裁决 3 定的是“原子 `UPDATE…WHERE` 领取”。实现改成了 `FOR UPDATE` 加 `innodb_lock_wait_timeout=1`，超时就当作段忙。
  - 这样有两个问题：
    - 会阻塞最长 1 秒，而 SKIP LOCKED 是立即跳过，行为不同。
    - `innodb_lock_wait_timeout` 是会话变量，连接池里的连接用完如果不还原，会把 1 秒超时带给后续无关的事务。
  - 二选一：
    - (a) 按原裁决做原子 `UPDATE…WHERE` 领取。
    - (b) 保留现方案，但要在回执里写清为什么 `probeIdleRow` 的流程必须持有行锁；`finally` 里还原会话变量，并补测试证明连接归还池子后超时值已恢复。
  - 两种做法都要在真实 MySQL 5.7 上通过多线程测试：不重复领取，等待时间有上限。
  - 另外，达梦用语句超时的理由也要写明。如果 DM8 实测支持 `SKIP LOCKED`，就直接用 `SKIP LOCKED`。
- **R3 种子比对只做了第一层。**
  - 审查 01 裁决 5 定了两层：
    - 第一层：所有表比行数，关键列精确比对。
    - 第二层：其他列把 `''` 和 NULL 归一后比对。
  - `SeedComparisonTest` 只比了全表行数和 18 张表的关键列哈希，第二层没做。
  - B2 第一次跑比对之前补上，差异报告要列到“表/主键/列”。
- **R4 迁移版本号 `V0.4.1` 比发布版本 0.4.0 还高。**
  - 新增向量表用的是 `V0.4.1`，而本次发布是 0.4.0。将来真发 0.4.1 时，版本号会混淆。
  - 还没发布，可以直接改名：改为 `V0.4.0__…`。如果 V0.4.0 已经被占用、或另有原因，要在回执里说明。
  - 改名后重跑全链和 0.3.2 升级测试。
- **R5 `enabled` 整数绑定的修复来源要说清。**
  - 回执说 Boolean 参数比较在 H2/PG 上失败（H2 90110），并改了 5 个类 10 处。
  - 如果这是 0.3.2 线上已有的缺陷，说明 UAT 上智能体工具启用过滤一直有问题，要登记到需求池并说明影响。
  - 如果是 B1 自己的改动（拦截器、`JdbcVendorSupport` 等）引出的，要写明是哪一处引出的，以及为什么改调用方而不是改源头。
  - 请写清楚是哪一种情况。
- **R6 `comment` 改名改用可重复迁移，接受，但要确认两点。**
  - 接受的理由：建表在 `R__0.2.0` 这个可重复迁移里，版本化迁移在空库上会比建表先执行。
  - 要确认：
    - 1）`R__0.2.0` 将来如果因为内容改动重跑，里面没有任何语句会把 `comment` 列重新加回来，例如 `ADD COLUMN IF NOT EXISTS comment`。
    - 2）Oracle 和达梦上 `comment` 是关键字，`R__0.2.0` 原样建表会直接失败。所以这两个库（也建议其余新方言）的建表脚本直接建 `opinion_comment`，`R__0.4.0` 在这些库上空跑不报错。
- **R7 证据要补齐。**
  - 全量 2,445 个测试跑在 `46180dd8` 之前，`ConcatPortabilityTest` 是单独跑的。B2 第一份回执要附在分支最新提交上重跑全量的结果。
  - `.last` 129 处现在只有“按写法类型”的单测。要补一个语料测试：从源码提取全部 129 个 `.last` 字面量，断言都符合 `LIMIT n [OFFSET m]`，并且在 Oracle 和 SQL Server 两种改写下都不抛异常。这样以后新增不合规写法会被测试拦下。
  - SQL Server 没有 `ORDER BY` 时会补 `ORDER BY (SELECT NULL)`。没有排序时结果不确定这一点和 PG 一样，可以接受。但“带 OFFSET 却没有 ORDER BY”的站点要列出数量，应为 0 或逐个说明。

**观察**：手写 LIMIT 在 B0 数成 6 处，B1 实际是 10 处。这是继阶段 A 之后第二次盘点数目不准。B2 每个库的回执，凡涉及站点数，一律附可复跑的统计命令。
