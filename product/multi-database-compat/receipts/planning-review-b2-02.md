## 2. 问题

- **T1（阻断单库验收）MySQL / MariaDB 脚本里的 `||` 告警。**
  - 回执 §4 提到 MySQL 8.0 有 `'|| as a synonym for OR'` 告警，并归为“后续整理”。这不能算告警：在 MySQL / MariaDB 默认模式下，`||` 是逻辑或。如果脚本本意是拼接字符串，结果会**悄悄写成 0/1**，执行时不会报错。
  - 要做的事：
    - 列出 MySQL / MariaDB 全部脚本中每一处 `||`，给出文件:行和原意。
    - 凡是本意为拼接的，改成 `CONCAT`。
    - 写明这些位置是否落在种子比对覆盖的表和列里。种子比对 0 差异只覆盖种子数据，覆盖不到 DDL 默认值、视图、存储过程和运行时 SQL。
    - 运行时 Java SQL 里如果有 `||`，同样要列出。
- **T2 种子比对要在最终提交上重跑。**
  - MySQL 5.7 / 8.0 和 Oracle 的种子比对还是 B2-01 的结果，但本批已经改了 Oracle 的 9 个唯一索引、`metadata_json` 默认值、动态宽表 DDL 等。
  - 进入阶段 3 之前，**所有实库**（含 SQL Server）都要在同一个最终提交上重跑一遍矩阵：迁移、种子两层比对、启动冒烟、业务冒烟。结果写成一张表。
  - 本批允许先引用旧结果，但必须标注“旧提交”。
- **T3（阻断交付 Owner 验证）DM8 脚本还没做可空唯一键。**
  - DM8 脚本是从 Oracle 脚本转过来的，Oracle 的 9 个函数索引和 `uk_sw_bpm_binding_active` 的处理却没有同步过去：回执 §7 写的是“普通唯一索引”，并留给 Owner 确认。
  - 但 `sw_bpm_form_binding` 有多条 `active=0` 的历史绑定是正常业务数据。用普通唯一索引，第二次解绑就会失败，这是确定的缺陷，不需要 Owner 实测来判断。
  - 要做的事：
    - DM8 按 Oracle 的方式改成函数索引。DM8 支持函数索引。
    - Owner 验证清单里加上正例和反例：“空键可以并存、非空键仍然唯一、多条 `active=0` 可以并存”。
  - 改完这些，才算“交给 Owner 验证”的状态。
- **T4 有两处“几个库一致”的说法缺证据。**
  - S2 结论写的是“四方言终态一致”，但 `FormKeyConstraintTest` 只断言了 H2 和 PG。要补 MySQL、Oracle 的断言（DM8 静态比对即可），或者在下一批的实库矩阵里一并断言。
  - Oracle 的 9 个函数索引要写明判断条件是“**所有**键列都非空才参与判重”，和 PG 语义一致（PG 只要任一列为 NULL 就不判重）。把 9 个索引的定义列出来，逐个对照。
- **T5 DM8 的 H2 代理检查改为别的方式。**
  - H2 代理检查做不了，Executor 如实标了 `@Disabled`，没有伪造通过，这一点认可。
  - 改用两项检查代替：
    - 1）用 `SwVendorMigrationRunner` 的切分逻辑，对 30 条 DM 脚本只解析、不执行，断言语句数和 Oracle 版本一致（或者列出差异）；
    - 2）出一份 DM 与 Oracle 脚本的差异报告，列出每一处转换。
  - 这两项写进 DM8 的完成口径。
- **T6 动态宽表的标识符改写要防误改。**
  - 受控执行入口会把 ANSI 双引号改成反引号。要补单测：字符串字面量里的双引号、单引号转义、注释里的双引号，都不能被改。现有 3/3 单测有没有覆盖，请写明。

**观察**：openGauss 必须使用 `DBCOMPATIBILITY 'PG'` 建库，启动检查已经强制。0.4.0 的部署文档要写明这一点，并同 MySQL 的 `utf8mb4_bin`、SQL Server 的 `_CS_` 一起放进“建库前提”章节。
