## §2 三项关键决策（本会话与用户确认）

### 决策 1：工具节点语义 —— 改为独立图节点（显式工作流式调用）

**结论**：放弃 Step3 建立的"工具是 LLM 节点内部 Function Calling 选项、由 LLM 自主决定是否调用"的 agentic 语义。F02 图设计器中的工具节点是图上独立、可连线的节点，执行顺序由图拓扑决定，而非 LLM 自主判断。

**对现有实现的影响**：`AgentGraphFactory.callModel()`（L160-190，回执问题1）当前把 `TOOL_CALLBACKS_BINDING` 经 `ToolCallingChatOptions` 传入 Prompt，tool_calls 循环内建于 `ChatModel.call()`——这一整套机制是**当前单节点执行路径的实现细节，F02 的多节点图不会复用它**。F02 的工具节点需要独立的节点执行逻辑：直接调用 `AgentToolCallbackFactory` 已有的 `buildInternalCallback`/`buildExternalCallback`（回执问题3(c)，`AgentToolCallbackFactory.java` L112-144/150+）产出的 `ToolCallback`，但由图执行引擎主动调用，不经过 LLM 的 tool_calls 协议。

**F01 既有能力不受影响**：`sw_agent_tool_internal`/`sw_agent_tool_external` 白名单表（V20）、`AgentToolCallbackFactory` 的白名单装载与 `FunctionToolCallback` 构造逻辑，在 F02 中仍是工具节点的底层实现依据，只是**调用方式**从"LLM 内部协议驱动"变为"图拓扑驱动"。V20 表结构本身无需改动。

### 决策 2：MVP 节点类型范围

**本轮实现**：LLM 节点、工具节点、条件分支节点。
**推入 todo（后续批次）**：并行节点、循环节点——复杂度最高（需定义汇合语义、失败处理、循环终止条件，且仓库无任何先例），本轮不阻塞图设计器/执行引擎骨架落地。

**条件分支节点的求值方式**（本轮需要一并定案，否则节点类型选型不完整）：回执确认仓库无条件分支先例。建议采用**表达式匹配 LLM 输出文本**的最小实现（如分支边携带一个关键词/正则条件，图执行引擎按上一节点输出文本逐条匹配边条件，取第一个命中的边），不引入独立的表达式引擎依赖（如 SpEL/MVEL）——`sw-bpm` 的 `GraphElement.config`（不透明 Map）先例支持这种"条件配置随边携带、执行引擎只做字符串匹配"的轻量方案。**此为本文档给出的推荐值，非用户已拍板项，下一个 Step 方案中需再次显式确认。**

### 决策 3：执行引擎形态 —— 图定义驱动执行（真正按拓扑解释执行）

用户原话："你建议即可，如不阻塞可以进入 todo"。

**推荐结论：不能推入 todo，必须本轮（或紧接的下一个 Step）落地图定义驱动执行**，理由是技术必然性而非偏好：

- 决策 1 已确定工具节点是独立、可连线的图节点。一旦存在"LLM 节点 → 工具节点 → （可能再回到 LLM 节点）"这种多节点顺序，就不可能仅靠"图定义只是可视化配置层，运行时仍走现有单节点管道"来支撑——现有单节点管道（`START→callModel→END`）在结构上只能表达"一次模型调用"，无法表达"先调 LLM 再调独立工具节点再回传结果"的多步顺序。
- 换言之，"图定义仅作可视化配置层"这个选项在决策 1 拍板的那一刻已经被技术性排除，不是一个仍然开放、可以留到以后再选的选项。若真要保留"仅配置层"的轻量路径，唯一方式是同时反悔决策 1（工具退回 LLM 内部 Function Calling），但用户已明确拍板决策 1。
- **可以推入 todo 的是"并行/循环"这两种节点的执行语义**（决策 2 已裁定），因为它们不影响"LLM 节点 + 工具节点 + 条件分支节点"这条最小顺序执行链的落地——图执行引擎第一版只需支持顺序/条件跳转（单入单出 + 条件分支的多出边选一），暂不支持 fork/join 或循环边。

**架构含义**（仅陈述结论，具体设计留给下一个 Step 方案）：
- `AgentGraphFactory`（LangGraph4j `StateGraph` 单节点工厂）不再是 F02 场景下"图"的最终形态——F02 需要的是**按用户绘制的图定义动态构造多节点执行序列**的能力。回执问题1(c) 已确认 LangGraph4j 1.5.14 无 JSON/配置反序列化入口，`addNode`/`addEdge` 只能 Java 硬编码——这意味着"动态图"无法直接用 LangGraph4j 的 `StateGraph` API 实现（该 API 假设图结构编译期已知）。
- 因此 F02 执行引擎大概率**不能复用 LangGraph4j 的 `StateGraph`**，需要自建一个"按 `graph_json`（节点/边列表）解释执行"的轻量解释器（遍历节点、按类型分发到 LLM 调用/工具调用/条件求值逻辑、按边转移），LangGraph4j 依赖是否保留、`AgentGraphFactory`/现有单节点管道是否废弃或并存，是下一个 Step 方案需要明确裁定的架构问题（不在本文档拍板，避免超出本轮"设计澄清"的范围）。
- F01 已交付能力（模型管理、工具白名单、会话持久化、多 Key 轮询）在语义上仍应保留——新解释器需要能复用 `ChatModelFactory.build()` 构造 ChatModel、复用 `AgentToolCallbackFactory` 的工具白名单装载，而不是重新发明这两块。
