## 1. 目标

将需要可靠交付的跨模块业务动作从“内存事件 + `@Async` + `AFTER_COMMIT` 是唯一交付链”收敛为**事务内持久意图、可恢复调度、幂等消费、有限重试和可审计终态**。

Spring Event 可以继续承担进程内通知或持久任务的唤醒加速，但不能再作为 must-deliver 动作的唯一事实源。暂不因本阶段引入 MQ；优先复用现有持久命令、消息、触发和回调结构，只有无法满足统一生命周期时才新增通用 outbox。

## 2. 已锁定事实与交付分类

Phase 2 已确认：5 类事件、11 个发布点、4 个生产监听者；4 个监听者均为 `@Async + AFTER_COMMIT`，不存在通用 outbox，存在无监听者、无事务发布、吞异常和无恢复重试路径。

| 事件/接缝 | 本阶段分类 | 必须达到的业务结果 |
|---|---|---|
| `ScheduledFlowTriggerEvent` | MUST_DELIVER | FLOW 定时任务必须形成持久流程启动意图；不能“未启动流程却记录 SUCCESS” |
| `IotProcessTriggerEvent` | MUST_DELIVER | IoT 规则与脚本触发均能在提交后恢复执行；非事务脚本路径不能静默丢失 |
| `BpmDeviceCommandEvent` | MUST_DELIVER | 审批通过后的设备命令必须持久、幂等、可重试；缺少 IoT Bean/瞬时失败不能直接丢弃 |
| `BpmNotifyEvent` → 通知 | MUST_PERSIST_INTENT | 审批/待办/超时等通知意图必须先持久化，再由现有通知恢复机制投递；通知失败不得回滚已合法业务动作 |
| `BpmNotifyEvent` → OpenAPI 回调 | MUST_DELIVER | 对启用回调的应用形成持久、可恢复且幂等的回调任务；3 次进程内尝试后不能只留日志并永久放弃 |
| `FormSubmittedEvent` 兜底 | ORDINARY / RETIRE_FALLBACK | 生产权威路径继续是 `FlowStartPort + sw_bpm_command`；无监听者兜底不得继续伪装成可靠降级，应移除或显式失败 |

上述分类是本阶段范围，不允许执行角色自行把 must-deliver 降级为普通事件。外部 SMS/EMAIL/FEISHU/DINGTALK/WECHAT_WORK 的真实 Provider 验证仍遵循既有 Owner 延期边界；本阶段只证明通知意图与内部投递生命周期可靠，不冒称外部渠道真实送达。

## 3. 范围

- 上表五类 must-deliver 接缝的发布、持久化、领取、消费、重试、幂等、失败终态与审计；
- `ScheduledFlowTriggerEvent` 和 `FormSubmittedEvent` 两条当前无监听者路径的语义纠正；
- Flowable 回调、显式事务、Quartz、IoT 规则与脚本等不同事务来源的持久化边界；
- 现有 `sw_bpm_command`、`sw_notify_message`、`sw_notify_send_attempt`、`sw_openapi_callback_log`、`sw_iot_process_trigger`、`sw_iot_device_command` 的复用或演进；
- 必要的迁移、机械守门、真实数据库并发/恢复证据及受影响范围回归。

执行角色可选择通用 Transactional Outbox、按领域复用现有持久队列，或二者组合；选择必须以原子性、恢复能力、幂等身份和迁移成本为依据，而不是以技术名词统一为目的。

## 4. 非目标

- 不引入 Kafka/RabbitMQ 等 MQ，不建设分布式事件平台。
- 不验证已延期的外部通知 Provider 真实送达，不改变其 Owner 延期状态。
- 不实施 BAO-01—04、06—10，不顺手拆模块、改 BOM/Enforcer/H2/版本号或 Debug 制品。
- 不改变审批、流程启动、设备控制、通知订阅与 OpenAPI 回调的公开业务语义或 HTTP 契约。
- 不追求“消息绝不重复”；目标是至少一次可恢复交付 + 业务幂等，使重复执行不产生重复业务结果。
- 不自动授权 commit、push、合并、tag、Release、部署或生产数据操作。

## 5. 必须达到的结果

### A. 原子持久化与真实状态

1. 每个 must-deliver 发布点必须在业务事务提交时同时形成可恢复持久意图；原业务回滚时不得留下可执行孤儿任务。
2. 原本无事务的 Quartz/脚本路径必须建立明确事务边界；不能依赖 `AFTER_COMMIT` 在无事务时“碰巧执行”。
3. 业务日志、Job 日志和对外状态必须反映真实阶段：仅持久化意图时不得写成下游动作已经成功。
4. 进程在“业务提交后、异步监听前”退出，重启后仍能发现并继续任务。
5. `FormSubmittedEvent` 无监听者兜底必须被移除或转为显式失败；权威持久命令路径不得被降级。

### B. 领取、重试与失败终态

1. 持久任务必须具有可复算状态机，至少区分待处理、处理中、成功、可重试失败和终止失败；不得用日志文本代替状态。
2. 多实例/多线程只能由一个有效领取者执行同一尝试；领取租约过期后可以安全恢复，旧领取者不能覆盖新结果。
3. 瞬时失败使用有限重试和明确退避；达到上限进入可审计终止态，并提供受控恢复入口或明确人工处置路径。
4. 进程重启、执行器拒绝、Bean 暂不可用、HTTP 失败和设备下发失败均不能造成任务永久消失。
5. 失败处理不得吞掉业务错误后仍把任务或 Job 记为成功。

### C. 幂等与业务结果

1. 幂等键必须来自稳定业务身份，不得在每次重试时重新随机生成：
   - FLOW 定时启动至少包含 `jobId + fireTime`；
   - IoT 触发沿用稳定 `idempotentKey/triggerId`；
   - 设备命令绑定审批业务身份与命令身份；
   - 通知沿用租户、事件、业务、发生序号、接收人与渠道身份；
   - OpenAPI 回调绑定应用、触发类型和业务对象。
2. 同一任务重复领取、进程重启后重放、超时后迟到完成，都不能重复创建流程、设备命令、通知意图或成功回调结果。
3. FLOW 定时任务必须真实启动一次流程或进入明确失败/重试态；禁止静默成功。
4. IoT 规则与脚本触发必须具有一致的可靠性，不得保留脚本路径静默丢事件。
5. 审批提交成功后，设备命令、通知与已订阅回调的持久意图均可追溯；其下游失败不反向篡改已完成审批。

### D. 兼容、验证与守门

1. 提供发布点 → 持久结构 → 领取者 → 幂等键 → 业务结果的完整矩阵，覆盖 11 个既有发布点及所有替代路径，零未分类 must-deliver 旁路。
2. 使用真实 PostgreSQL 行为证明：原子提交/回滚、提交后崩溃恢复、并发领取、租约回收、重复投递、重试耗尽与迟到完成隔离；H2 可继续承担轻量回归，但不得替代 PostgreSQL 并发与持久语义。
3. 对 Scheduled FLOW、IoT 规则、IoT 脚本、审批设备命令、通知意图和 OpenAPI 回调分别提供端到端内部行为证据；外部 Provider 可使用受控适配器，不冒称真实厂商送达。
4. 若修改 schema，必须提供既有记录兼容、前置数据检查、正向迁移、终点版本和回滚/恢复边界；不得以清空数据库证明迁移成功。
5. 建立机械守门：must-deliver 路径不能重新退回裸 `DomainEventPublisher` + 内存监听作为唯一链路；无事务 `AFTER_COMMIT` 和无监听者 must-deliver 事件必须被识别。
6. 受影响模块测试和 Server 全量门禁绿色；计数只取实际命令输出，并冻结行为输入和证据哈希。

## 6. 风险与回滚方向

- 新增持久任务可能与现有消息/命令表形成双写或重复消费；迁移期必须指定单一权威入口和切换条件。
- 至少一次交付会放大既有非幂等副作用，必须先固定业务身份再启用恢复重试。
- Flowable 回调事务边界需用运行时行为确认，不能依据注释推断。
- 多实例领取、租约和迟到完成存在竞态；状态更新必须绑定领取令牌或等强度条件。
- 外部回调与设备操作无法由本地事务回滚；只能通过持久意图、幂等、重试和补偿形成最终一致性。
- 回滚必须保留已经持久化的未完成任务及其可读性；不得通过删除任务表或丢弃失败记录回退。

## 7. 本机真实 PostgreSQL 环境规范

1. 本阶段真实 PostgreSQL 连接参数统一读取 Git 工作区外的 `~/.config/smart-workflow/pg.env`；`~/.zshenv` 负责自动加载，执行命令只引用 `PG_HOST`、`PG_PORT`、`PG_USERNAME`、`PG_PASSWORD`。
2. 新会话开始验证前必须先检查上述四个变量。变量齐全时直接执行，不得再次向 Owner 索要地址、端口、用户名或密码。
3. 变量值不得进入仓库文件、方向、回执、证据包、命令文本、终端日志、测试报告或 Git 元数据；证据只记录“变量已提供/未提供”和脱敏数据库身份。
4. 若变量未进入当前进程，先加载 `~/.zshenv` 或私有环境文件并复查；只有文件缺失、不可读或变量仍不完整时，才能如实登记环境输入缺失。禁止把私有环境文件复制进工作区作为替代。
5. 本规范只授权使用该环境完成 Phase 4 验证，不授权生产数据操作、凭据传播、Git 提交、远程发布或超出既定验收范围的动作。
