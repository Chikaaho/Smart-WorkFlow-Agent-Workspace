# Phase 3：动态宽表数据安全与引用完整性收口

> 下发角色：规划（Planner）  
> 指定实施角色：执行（Executor）  
> 所属总体任务：`backend-architecture-optimization`  
> 对应候选：BAO-06、BAO-07  
> 任务等级：XL  
> 状态：PASSED（规划功能级验收通过，2026-09-24；待终态同步）  
> 日期：2026-09-24

## 1. 目标

将动态宽表的租户隔离、逻辑删除、动态标识符校验和引用完整性，从分散的业务层手工约定收敛为可复用、可机械守门、可通过并发行为证明的基础设施契约。

最终结果必须同时保证：正常读写语义保持兼容；跨租户和已删除数据不可泄露或误操作；动态表名/字段名不能绕过统一校验；REFERENCE 删除与并发新增引用之间不会产生存活子记录指向已删除父记录的状态。

## 2. 已锁定事实

1. BAO-06 已确认：生产动态宽表路径存在分散的 `JdbcTemplate`/动态 SQL、重复表名正则、列名映射与校验职责分离，以及引用检查失败放行等接缝。
2. BAO-07 已确认：REFERENCE 的检查与软删位于普通事务中，但缺少能够覆盖“检查后、删除前新增引用”的数据库约束或串行化机制；静态 TOCTOU 窗口成立。
3. BAO-07 尚未完成真实并发复现；BAO-06 尚未核对活库动态表 schema。这两项是本阶段实施前后必须关闭的证据边界，不得沿用静态结论冒充行为通过。
4. `SqlExecutor` 的受控外部只读 SQL、固定表催办锁、dev-only 验证 SQL 不等同于动态宽表业务 DML，不纳入统一改造数量。

## 3. 范围

- `sw-biz-form-biz` 内生产动态宽表的定义、提交、查询、更新、删除、导入导出与 REFERENCE 校验路径；
- 动态表 DDL/DML 所使用的表名、字段名、租户、逻辑删除和参数绑定契约；
- RESTRICT/CASCADE 删除与引用新增、更新、导入之间的并发一致性；
- 为上述契约建立必要的机械守门、集成行为证据和兼容/回滚边界；
- 仅在所选方案确有需要时调整 schema 或迁移，并保持现存数据可校验、可回滚。

执行角色可根据代码事实选择统一 Repository、受控 SQL Executor、查询规格对象、锁/引用登记或数据库约束等方案，也可组合使用；不得只因扫描建议出现某个技术名词就预设实现。

## 4. 非目标

- 不改造通用外部数据源 `SqlExecutor`，不禁止所有 `JdbcTemplate`，不处理与动态宽表无关的固定表 SQL。
- 不实施 BAO-01—05、08—10；不顺手修复事件、BOM、Enforcer、H2、版本号或 Debug 制品问题。
- 不改变公开 HTTP 契约、表单业务权限语义、租户归属规则或正常的空结果行为。
- 不以增加注释、复制正则、补人工规范或单个 `FOR UPDATE` 的存在替代并发正确性证明。
- 不自动授权 commit、push、合并、tag、Release、部署或生产数据操作。

## 5. 必须达到的结果

### A. 动态 SQL 安全边界

1. 所有生产动态宽表 DML 均有完整清单，并被归类为统一受控入口或有明确理由的基础设施例外；不得存在未分类旁路。
2. 动态表名和字段名在 SQL 构造边界统一校验；名称映射不能替代合法性校验，历史/越权元数据也不能绕过守门。
3. 需要租户隔离和逻辑删除的读写由基础设施契约强制表达，业务调用者不能通过遗漏条件获得跨租户或已删除数据。
4. 元数据扫描、引用检查或目标表访问失败时必须 fail closed，并返回可诊断错误；不得记录告警后继续删除。
5. 参数值继续使用绑定方式，不因统一封装退化为字符串拼接。

### B. REFERENCE 并发完整性

1. 先用真实支持的数据库行为固定当前竞态，再证明修复后以下并发次序均不能留下非法状态：引用新增先到、父记录删除先到、两者重叠执行。
2. RESTRICT 必须在存在有效引用时拒绝删除；CASCADE 必须保持既有业务语义并受租户边界约束。
3. 所选串行化机制必须覆盖“当前无引用行”场景；仅锁住已查询到的引用行而不能阻止新插入，不构成通过。
4. 锁身份至少包含租户和被引用对象，锁顺序、超时、死锁恢复与事务回滚必须有明确行为。
5. 修复后不得出现存活引用指向已删除父记录，也不得发生跨租户引用误判或级联。

### C. 兼容、验证与守门

1. 提供改造前后动态 SQL 入口映射、例外清单和零未分类旁路的可复算证据。
2. 提供跨租户、逻辑删除、恶意/非法标识符、失败放行、正常 CRUD 与导入导出的集成行为证据。
3. 提供 REFERENCE 并发行为证据；静态代码、测试类名或锁语句存在不能替代实际并发结果。
4. PostgreSQL 行为作为生产语义依据；H2 继续承担开发/测试 SQL 代理时，必须明确两者差异并保持相关回归可运行。
5. 若新增或修改迁移，必须证明迁移前置数据校验、正向迁移、终点版本和回滚/恢复边界；未改迁移则明确声明并证明 schema 无变化。
6. 受影响模块测试和 Server 全量门禁必须绿色；计数以实际命令输出为准，不手工推算。
7. 建立机械守门，防止生产业务代码重新绕过受控动态宽表入口或恢复 fail-open 路径。

## 6. 风险与回滚方向

- 统一注入 tenant/deleted 条件可能改变既有查询结果，必须区分安全修复与业务语义变更。
- fail closed 会把历史静默放行转为显式失败，需要稳定错误映射与可诊断信息。
- 锁或引用登记可能引入争用、死锁和吞吐下降，必须以租户/对象粒度和确定锁序控制影响。
- schema 方案可能遇到历史脏数据；不得在未盘点和未定义恢复路径时直接增加不可满足约束。
- 回滚点至少覆盖受控 SQL 入口切换、并发机制启用和任何数据库迁移，不把一次性数据动作当作代码回滚。
