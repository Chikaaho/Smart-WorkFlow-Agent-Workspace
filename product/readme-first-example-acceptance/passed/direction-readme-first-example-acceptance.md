## 首轮证据清单与保存方式

Executor 在本目录 `receipts/` 追加结果，直接引用已有可读原文与证据；一份汇总可以承载多个缺陷，不为格式重复整理或重跑。

1. 缺陷与变更摘要：实际现象、对象、预期与实际结果、修复范围、相关提交及本轮复验结论。
2. 实际流程证据：环境、时点、用户/租户、流程实例及相关任务、预约、命令标识；按 AC01—AC05 关联实际操作和输出，记录 Owner 通过结论及尚有限制。
3. 正式浏览器结果来自用户可见、可交互会话，声明 `headless=false`，保存可回读视觉制品、URL、视口、身份、对象和网络索引，按既有机器契约如实记录证据层级。Owner 手工反馈按实际来源记录。隔离回归或组件测试按其层级使用。
4. 受影响验证的实际结果及完整原文位置；长输出完整保存于允许读取的位置，回执引用路径和结果摘要。MQTT 发送确认、设备执行回执及真实环境行为各按实际取得结果表述。
5. 收尾时提供修复交付范围、Git/版本/发布事实及受影响当前入口覆盖清单。源码、测试代码和完整 diff 的核实由 Executor 完成，Planner 读取变更结论与行为证据；knowledge、README 和仓库当前事实由 Executor 回传已核实结论。

验证采用最小充分、有界且可观测的工作量。预约到点验证由 Executor 结合实际场景安排，保留真实依赖与下一动作，遵守禁止空转及后台超长任务规则。非必要产物哈希不属于证据要求。
