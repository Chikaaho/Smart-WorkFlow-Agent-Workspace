# I51 需求方向：系统管理状态语义对齐

> 本会话角色：规划。本文只定义功能目标、边界、影响范围、风险与验收口径；执行角色自行探索现场、拆分 Step、设计实现与测试方案，并在全部完成后提交功能级完成回执。

## 1. 背景

已完成的全量核验与落库回执确认：前端用户、部门管理页面把 `status` 表达为“正常=1、停用=0”，而后端用户状态契约是“正常=0、停用=1、锁定=2”。这不是注释漂移，而是实际提交值反转：通过 UI 新建的默认用户会被后端视为停用，UI 选择“停用”反而会被后端视为正常，从而抵消 I33 已落地的登录与 refresh 状态拦截。

证据来源：`search_fallback/known-issues-verification.md`、`search_fallback/knowledge-sync-apply.md`；I51 已正式登记。

## 2. 目标（一句话）

统一系统管理前端与后端的状态值语义，使用户和部门页面提交、回填、筛选及展示的“正常/停用”含义与后端契约一致，并确保 UI 创建的正常用户可以登录、被停用的用户会被既有后端安全门正确阻断。

## 3. 非目标

- 不修改后端用户、部门、角色或岗位的状态枚举、数据库字段或登录安全逻辑。
- 不改变 I33 已实现的登录与 refresh 双入口拦截，也不扩展“停用即时使既有 access token 失效”的能力。
- 不处理 I49（普通角色菜单授权缺口）或 I50（登录状态校验时序）；二者继续作为独立问题排期。
- 不重构整个系统管理模块，不借本轮统一所有业务模块的通用字典体系。
- 不新增状态值或重新定义“锁定”业务流程；仅保证现有后端契约被前端准确表达。

## 4. 影响范围（模块级）

本轮是**前端单项目功能**，执行范围限定在 `Smart-WorkFlow-Web`：

- 系统管理用户页面：新建默认值、编辑回填、状态选择、列表展示和筛选条件的值语义。
- 系统管理部门页面：新建默认值、编辑回填、状态选择、列表展示和筛选条件的值语义。
- 与上述页面直接相关的前端类型、API 适配、Mock 数据或测试夹具，仅在其仍使用反向语义时同步。
- 角色、岗位页面作为一致性对照；探索已表明其映射与后端一致，除非执行层发现直接证据，否则不得修改。

后端 `Smart-WorkFlow` 仅作为契约事实来源，本轮不得修改后端业务代码、迁移或测试。

## 5. 风险方向

1. **局部改值导致链路仍反转**：默认值、选择项、筛选、Mock、断言可能分别持有数字常量；执行层需保证提交与回填链路采用同一语义，而不是只改可见标签。
2. **历史数据误读**：既有数据按后端语义存储，前端修正后应直接正确展示；不得通过数据迁移或兼容“双重语义”掩盖前端错误。
3. **用户与部门契约差异**：执行层需以各自后端契约证据核实后落地，不能仅凭字段同名机械批量替换。
4. **安全回归**：本轮必须保留 I33 的服务端权威性；前端状态控件只负责提交正确值，不能把登录阻断逻辑复制到前端作为替代。
5. **状态常量散落**：若发现同一页面内存在多处硬编码，应在当前模块允许范围内消除导致语义再次反转的直接重复，但不得扩大为全局状态字典重构。

## 6. 功能级验收标准

1. 用户管理页面中，“正常”提交值与后端正常值一致，“停用”提交值与后端停用值一致；新建默认用户不再因前端默认值被后端判为停用。
2. 用户编辑回填、列表展示与筛选对同一状态值的解释一致；停用用户经 UI 保存后能被既有登录与 refresh 安全门阻断。
3. 部门管理页面的默认值、提交、回填、展示与筛选均与其后端契约一致，不再使用已确认的反向映射。
4. 角色、岗位等已正确页面无行为回归；执行回执需报告核对结论及是否实际修改。
5. 与本功能直接相关的前端自动化测试覆盖正常/停用两种值的提交与回填语义；前端规定质量门全部通过，测试数量不得无说明减少。
6. 后端业务代码、数据库迁移及后端状态契约零修改；如执行层发现必须改后端才能完成，应标记 `BLOCKED` 并在回执中说明，不得自行扩大范围。
7. 功能收尾按宪法 §3.3 第10项同步完整知识状态：I51 修复记录、功能追踪、当前状态、功能清单/需求池关联项（如适用）须一致，回执列明全部触碰文件和状态变化。
