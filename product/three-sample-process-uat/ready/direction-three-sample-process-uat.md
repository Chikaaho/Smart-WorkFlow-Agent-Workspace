5. **持续授权**：分支、提交、推送、合并 develop/main、打 tag 0.3.0、Release、通过既有通道部署 UAT，都按 system.md §3.0 连续推进，不逐步询问。

## 1. 目标

在平台上配置一个应用、三个流程。字段要丰富，步骤要适量，看起来像真实企业在用的配置，不像演示样例。先在本地跑通，再导入 UAT 并实际跑通。过程中暴露的平台功能缺口和缺陷直接修复，修复结果作为 0.3.0 发布。

场景原文见 `todo/ch-apaas-project-update.md` §3.1—3.3：

| # | 流程 | 必须体现的能力 |
|---|---|---|
| A | 跨部门灾备演练审批 | 多位技术负责人审批 → 按“参与部门”动态并行给分管领导审批（全部通过）→ 总公司科技部会签 → 抄送相关领导 → 表单数据进入定时队列，到预定时间发送 MQTT 指令（机房断电、火警告警，UAT 只用测试主题/测试设备） |
| B | 校园出入口流量异常处置 | 异常触发 → 检索流程与知识库中的近期活动 → 联网搜索公开活动/节日 → 判断：符合特殊情况则记日志并发起 P1 工单；不符合则发起 P0 工单，并通知负责人（站内信/邮件；短信电话渠道未采购，配置节点但标记未启用即可） |
| C | MES 设备温度研判 | 阈值：常温 75℃、告警 80℃、停机 85℃；业务人员可配置 Agent 知识样本；短时间超过 80℃ 判异常 → 工单加告警；缓慢上升到 80—85℃ 判正常操作，只记录；超过 85℃ 走紧急告警流程 |

0.2.4 已经交付了“IoT 规则启动 Agent 研判、失败升级、Agent 内部工具、渠道凭据”（示例二、三），本任务应复用这些能力，不要重新造一套。

## 2. 非目标

- 不做 P60 的 I5/I6 阶段工作，不改动 P60 方向文件。
- 不采购、不接入短信/电话渠道。
- 不向真实物理设备发送指令（UAT 本来也没有真实设备，使用测试主题即可）。
- 不做与这三个流程无关的重构。

## 3. “不像 demo”的质量标准

- 每个表单 15—25 个字段，按业务分组布局（基本信息、影响评估、时间窗口、附件与说明等），合理使用栅格。
- 字段类型和业务匹配：人员、部门、多选部门、日期时间、数字（带单位和范围）、金额/时长、下拉（真实选项）、多行文本、附件、计算或联动字段（如平台支持）。必填和校验要合理。
- 名称、选项、默认值、帮助文字使用真实业务口吻。不得出现 test、demo、示例、aaa、111 之类的内容。
- 流程 5—9 个节点。审批人按角色、部门或表单字段解析，不写死 admin。条件分支要有默认出口。
- 测试实例数据也要写真实内容，比如“2026 年 Q4 华东分公司同城灾备切换演练”。

## 4. 执行路线（按顺序连续推进）

1. **准备**：读 system.md、roles/executor.md、project.md、两仓工程宪法、`knowledge/` 中的 UAT 部署、凭据和种子文档，以及 0.2.4 回执里的 IoT/Agent 能力。从 develop 拉分支 `feature/0.3.0-sample-processes`（只在实际需要改代码的仓库拉）。
2. **本地配置**：在本地运行的平台上（沿用已在运行的 8080/5173 服务，不要停止用户的服务；需要独立实例时另起端口）用 UI 或 API 配置应用和三个流程。现有 `assets/operations-risk-workbench.appbundle.json` 可以作为起点，但必须补齐 §1 表中的全部能力，不能用关闭 IoT/Agent/搜索的方式规避。
3. **本地跑通**：每个流程至少发起一个实例并走到结束；B、C 两个流程的每条分支各跑一次。
4. **遇到缺口就修**：平台不支持某项必需能力或出现 bug 时，直接在分支上修复，补上对应测试，然后回到第 3 步。只有在确实无法实现、并且已经尝试过替代配置的情况下，才在回执里登记为“已知限制”，然后继续推进其他工作。不要为此停下来提问。
5. **导出应用包**：用平台导出功能生成最终应用包，保存到 `product/three-sample-process-uat/assets/`，替换旧包。
6. **发布 0.3.0**（仅在第 4 步产生了代码改动时执行）：门禁通过 → 合入 develop → 合入 main → 版本号统一改为 0.3.0（含种子、构建元数据、CI 默认值）→ tag/Release → 通过既有通道部署 UAT → 回读 health 和 build.version=0.3.0。没有代码改动则跳过这一步，在回执中说明。
7. **UAT 导入与验证**：浏览器可见会话登录 UAT → 应用管理“预检 → 确认导入” → 发布三个流程 → 按第 3 步的覆盖范围在 UAT 上各跑实例 → 截图留证。
8. **同步与回执**：按 executor.md §4.5 更新 knowledge 和受影响的当前入口（版本、功能摘要），写总回执，提交并推送。

## 5. 执行纪律（针对上一轮的问题）

- 能自己查到的信息自己查（凭据、种子、地址、命令）。不要把可查的信息变成问题抛给用户。
- 浏览器句柄断了就重建会话，接着操作；工具报错先换一条路径（UI ↔ API），不要宣布阻塞。
- 发现规则或文档与本方向冲突时，按本方向执行，并在回执里记一行，不要停下来。
- 只有以下情况才停下来问用户：需要用户本人才有的秘密或 MFA；需要删除或重建服务器、数据库；需要强推或改写历史。
- 进度汇报带七阶段计数，格式见 §7。

## 6. 总回执（一次提交，路径 `receipts/execution-final-01.md`）

1. 三个流程的字段清单（字段名、类型、分组）和节点列表，各自一张表。
2. 本地与 UAT 每个实例：实例 ID、走过的路径或分支、最终状态、截图路径（截图存放在本机，不入 Git，回执只写路径）。
3. 发现的缺口和缺陷：现象、根因、修复提交、对应测试。
4. 发布事实（如有）：两仓分支和 SHA、tag、Release、UAT build.version、Flyway 版本、全量测试结果。
5. 已知限制（如有）：已尝试的方案和剩余影响。
6. 七阶段进度、常规决定（一行）。

规划依据这份回执一次性验收。验收标准就是 §1 的能力表、§3 的质量标准和 §6 中的实际结果，不另外追加格式要求。
