## 2. 问题事实

| 项 | 内容 |
|---|---|
| 观察结果 | 工作台页面目前由 `WorkspaceHome.vue` 内置统计、待办、快捷发起、动态和效能等固定模板渲染；后端仅以 `sys_user_workspace.layout_json` 保存固定组件键的显隐/顺序/常用事项，服务层通过 `COMPONENT_KEYS` 白名单约束，尚无后台可维护的卡片类型目录和通用卡片元数据渲染契约。 |
| 期望结果 | 工作台卡片类型由后台配置维护；卡片定义、显示顺序、布局属性和卡片元数据通过低代码配置驱动，元数据以 JSON 持久化并按租户/用户关联读取，前端按卡片类型注册表安全渲染。 |
| 影响入口/身份/对象 | 登录后的工作台 `/workspace`；后台工作台配置入口；当前登录用户及其租户。 |
| 复现条件 | 登录任一用户进入 `/workspace`，检查页面结构与“配置工作台”保存内容：可见卡片类型和渲染结构来自前端固定实现，后台无法维护新的卡片类型或通用元数据。 |
| 风险等级 | 高（跨 Server/Web，涉及用户级配置、租户隔离、持久化契约和低代码渲染边界）。 |
| 受影响仓库 | Server / Web |
| 当前结论 | 根因已确认：现有布局存储只保存固定组件键的个人布局，卡片类型与卡片内容仍由前端模板和后端白名单硬编码，缺少后台卡片类型维护及 JSON 元数据契约。 |

## 3. 根因与修复边界

- 根因：`WorkspaceHome.vue` 直接维护固定卡片模板和组件键；`UserWorkspaceServiceImpl` 只校验固定 `COMPONENT_KEYS` 并序列化个人布局，数据表只有 `layout_json`，没有可维护的卡片类型定义和通用元数据字段。
- 修复范围：新增租户隔离的 `sys_workspace_card_type` 卡片类型目录及管理 API，使用 `metadata_json` 保存卡片定义元数据；用户布局继续写入现有 `sys_user_workspace.layout_json`，按当前用户和租户读取；Web 端通过受控 renderer 注册表按 `typeCode / order / span / metadata` 渲染统一低代码网格，并提供工作台卡片类型管理页。默认卡片由后台类型目录提供，工作台常态仅保留右上角齿轮入口，编辑态以基础组件库和画布支持拖拽排序、显隐和宽度调整。
- 明确不做：不把工作台固化为新增的一套静态卡片模板；不允许前端执行任意字符串组件路径或表达式；不改变流程目录、表单元数据和认证契约；不把 BUG-003 的响应式样式与工作空间提醒移除并入本缺陷。
- 关联/重复编号：无；BUG-003 负责同一页面的响应式布局和左下角工作空间提醒。
