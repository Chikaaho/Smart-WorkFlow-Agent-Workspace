# 0.1.1 长周期缺陷修复与版本发布方向

> 角色：规划（Planner）  
> 日期：2026-09-21  
> 等级：XL  
> 状态：READY（开放缺陷收件；未授权合并 main、打 tag、创建 Release 或部署）  
> 上一版本基线：0.1.0 `COMPLETED（规划已确认，2026-09-21）`

## 1. 背景与目标

Owner 将对 0.1.0 进行持续真实体验验收，并可能连续提交数量不定、时间跨度较长的缺陷。本任务建立一个唯一的 0.1.1 修复发布列车，使后续执行会话可以直接接收问题、逐项收敛，同时保持每个缺陷、证据与 Git 提交可追溯。

最终目标同时满足：

- Server/Web 中受影响仓库以 0.1.0 已发布 `main` 为起点维护同名 `0.1.1-bugfix` 分支；
- Owner 提出的每个独立缺陷均有稳定编号、原始描述、修复边界、行为证据和提交身份；
- 正常情况下一个缺陷在每个受影响仓库只形成一个原子修复提交，测试与必要文档随同该提交；
- 已提交缺陷仍可被 Owner 真实复验并复开，不以 Executor 自验替代 Owner 体验；
- 只有 Owner 明确确认本轮缺陷收件完成后，才冻结候选、完成整体复核，并进入 `main` 合并及 0.1.1 版本发布。

## 2. 任务边界

### 2.1 范围内

- 0.1.0 真实体验中发现的可复现错误、交互异常、文案错误、兼容问题、回归问题和明确的安全/数据正确性缺陷；
- 修复缺陷所必需的最小代码、测试、迁移、配置与用户文档变更；
- 与缺陷直接相关的受影响范围回归；
- 0.1.1 候选冻结、整体验收、main 合并、CI、版本 tag 与 Release。

### 2.2 范围外

- 与缺陷无关的新功能、体验扩建、架构重写或机会性重构；
- 顺手处理既有开放 P 编号、ADV 项、I5/I6 延期未验证边界或其他待办；
- 在 Owner 宣布收件完成前合并 `main`、创建 `0.1.1` tag/Release 或部署；
- 通过 squash 抹去逐缺陷提交边界，或通过强推、rebase 改写已共享历史；
- 未经单独授权同步其他远程分支、修改公开版本身份或部署任何环境。

若输入实质上是新功能或会改变产品目标，Executor 必须从本发布列车中分离并报告，不得伪装成 bugfix 扩大范围。

## 3. 基线与分支契约

### 3.1 锁定起点

当前规划记忆锁定的 0.1.0 发布身份为：

- Server `main/tag 0.1.0`：`d18e9a39c552918615be8b158dfe0cc278cb309f`；
- Web `main/tag 0.1.0`：`039f987437ed6369c3c131631bd7622c6ae482e7`。

Executor 在任何分支写入前必须回读本地与远端事实。若 `main` 或 `0.1.0` 身份已变化，不得静默选择新起点，应提交差异与影响。

### 3.2 分支规则

- 分支名按 Owner 指定固定为 `0.1.1-bugfix`，不另加前缀；
- Server 与 Web 各自在需要承接缺陷时使用同名分支；预计两端都会进入本轮时，可在列车初始化时同时建立；
- 分支必须直接基于各自已验证的 0.1.0 发布 `main`，不得混入 `develop` 或其他未发布功能；
- 长任务期间所有 0.1.1 修复只进入该分支；不得把未经验收的修复直接写入 `main`；
- 本方向只授权本地分支初始化与修复工作。推送远端、合并 `main`、tag、Release 和部署均保留各自动作门禁。

## 4. 缺陷收件与身份

### 4.1 编号

- 缺陷按首次确认的独立问题顺序分配稳定编号：`V011-BUG-001`、`V011-BUG-002`……；
- 一条 Owner 消息包含多个互相独立的问题时拆成多个编号；同一根因的多个表现可保留一个编号并列出全部验收场景；
- 后续发现是重复问题时保留原始记录并关联主编号，不重复制造修复提交；
- 已分配编号不得因排序、关闭或复开而重用。

### 4.2 最小问题记录

每项至少保留：Owner 原始描述、观察结果、期望结果、影响入口/身份/对象、复现条件、风险等级、受影响仓库、当前结论、行为证据、提交 SHA 与剩余边界。无法立即复现时先保留原始事实和已尝试路径，不把猜测写成根因。

### 4.3 连续输入处理

- Executor 对新问题直接收件并处理，无需 Planner 为每个普通缺陷重新出方向；
- 在不改变产品目标、授权边界和发布范围时，Executor 可自主安排缺陷的实施先后；数据损坏、安全、认证、阻塞验收或会使后续证据失真的问题优先；
- 处理当前项时收到新问题，应先稳定登记，避免丢失，再继续或按风险调整顺序；
- 缺少的信息不影响安全修复路径时按合理假设继续；只有不同答案会实质改变产品结果、引发破坏性动作或超出授权时才向 Owner 提出一个关键问题。

## 5. 单缺陷提交契约

### 5.1 原子边界

- 正常目标是“一个缺陷、一个提交、一个可独立复核的证据包”；
- 修复代码、回归测试、必要迁移和与该缺陷直接相关的文档应放在同一提交中，不把测试拆成无关后补提交；
- 一个提交不得夹带第二个缺陷、机会性重构、格式化噪声或无关依赖升级；
- 修复中发现的新独立问题应另行编号，不并入当前提交；
- 公共前置变更若同时服务多个缺陷且无法安全归属某一缺陷，必须先报告为独立工作项并取得 Owner/规划方向，不得自行制造共享重构提交。

### 5.2 跨仓缺陷

Git 无法跨仓形成单个提交。若同一缺陷同时影响 Server 与 Web，则：

- 两仓使用同一个 `V011-BUG-NNN`；
- 每个受影响仓库最多一个对应原子提交；
- 回执必须把两边 SHA、契约关系和联合验证结果绑定在同一缺陷下；
- 任一仓未完成时，该缺陷不得写成已完整验证。

### 5.3 提交信息与历史

- 提交遵循 Conventional Commits，默认中文主题，并包含缺陷编号，例如 `fix(scope): [V011-BUG-001] 修复……`；
- 提交前工作树必须证明只包含当前缺陷；
- 已共享提交不 amend、不 rebase、不强推。若后续复验发现原修复仍有缺口，保留原提交并用关联该缺陷的新修正提交如实记录；该情况属于“正常一缺陷一提交”的显式例外，不得伪造历史；
- 最终合并必须保留逐缺陷提交可追溯性，不使用 squash 合并。

## 6. 单缺陷验收边界

每个缺陷进入“已提交候选”前，至少满足：

1. 复现证据或足以唯一确认故障的真实行为证据已固定；
2. 修复结果直接命中 Owner 描述的对象、身份、入口与场景，不用近似对象替代；
3. 存在针对根因的回归保护；无法自动化时说明原因并提供等强度的可重复行为证据；
4. 受影响范围验证通过，未引入契约、权限、数据隔离、迁移或兼容性回归；
5. 可见 UI/交互问题使用用户可见、可交互浏览器会话复验，保存关键截图、URL、身份、对象与网络索引；
6. 证据中的命令、计数与结果来自实际输出，结构存在或自述不算通过；
7. 提交 SHA、变更文件、测试结果和已知剩余边界可回读。

风险会提高证据强度：认证、权限、安全、数据隔离、数据库结构或迁移问题必须按 L/XL 强门禁处理；普通局部缺陷按受影响范围做最小充分验证，但不得降低上述真实性要求。

Executor 的“修复、验证、已提交”只表示进入 0.1.1 候选。Owner 在真实体验中可随时复开；复开时沿用原编号并追加新事实，不删除旧证据。

## 7. 发布列车状态与持续回执

- 本方向是唯一主功能；各缺陷是其内部工作项，不分别制造功能级 `PASSED/COMPLETED`；
- Executor 持续维护一份累积缺陷账本，并为每个已提交缺陷追加独立回执；历史回执不得覆盖；
- 缺陷账本至少能区分：已收件、待复现、处理中、待验证、已提交候选、Owner 复开、延期/移出、待 Owner 总确认；
- 每次执行回合必须明确本轮处理编号、提交 SHA、真实测试结果、尚未关闭的已授权项与下一动作；
- 仍有已收件且可执行的缺陷时，不得把发布列车包装为完成；没有新输入时可停在“开放收件”，但不得合并或发布。

建议回执位置：

- 累积账本：`product/v0.1.1-bugfix/receipts/bug-ledger.md`；
- 单缺陷回执：`product/v0.1.1-bugfix/receipts/V011-BUG-NNN.md`；
- 最终候选回执：`product/v0.1.1-bugfix/receipts/release-candidate-01.md`。

## 8. Owner 总确认与候选冻结

只有 Owner 明确表达“本轮完成、可以合并发布”或等价且可唯一理解的指令，才关闭收件并进入候选冻结。冻结前后必须区分：

- Owner 仅确认某一个缺陷通过，不等于整个 0.1.1 完成；
- “先这样”“暂时没问题”不自动解释为远程合并与发布授权；
- 冻结后出现新缺陷，若影响发布结论则复开候选并使旧整体证据按影响范围失效。

候选冻结必须证明：

- 累积账本中不存在未处置、待验证或已复开的授权内缺陷；
- 两仓 `0.1.1-bugfix` 只包含登记过的缺陷提交，提交与回执双向可追溯；
- 各单缺陷已锁定证据仍对应当前候选；后续提交未使其失效；
- 两仓工程门禁、受影响回归、迁移完整性与正式浏览器验收满足当前工程宪法；
- 0.1.0 中明确延期/未验证的外部边界未被冒称为 0.1.1 已通过，除非本轮确有对应新证据。

Executor 提交最终候选回执后，由 Planner 对照本方向做独立功能级验收。未达到全部标准时保持 `VERIFYING`，只补剩余缺口。

## 9. main 合并与 0.1.1 发布门禁

Planner 功能级验收通过且 Owner 明确授权最终远程动作后，发布阶段才可开始。最终动作必须在执行前重新声明精确远端、分支、候选 SHA、tag、Release 范围与风险。

发布目标为：

- 将各受影响仓库的 `0.1.1-bugfix` 以保留逐缺陷提交的普通合并方式进入最新且已核对的 `main`；
- main CI 全部成功，版本产物来自 main 的不可变 CI 身份；
- 在最终 main SHA 上创建 annotated tag `0.1.1` 与对应 Release；
- Release 正文列出缺陷编号、两仓提交/最终 SHA、测试基线、已知边界与升级说明；
- 回读远端 main、tag、Release target、CI 与资产身份，证明一致。

本方向不自动授权部署演示或生产环境。若 Owner 另行要求部署，应单独明确目标环境、数据范围、制品、回滚和可见验收边界。

若仓库仍以 `develop` 作为后续集成入口，0.1.1 修复不得在发布后从未来开发线丢失；具体同步方式和远程写入需按当时仓库事实另行授权，不在本方向中预设合并动作。

## 10. 停止与升级条件

- 发现 0.1.0 基线、分支来源或候选历史不一致时，停止写入并报告差异；
- 遇到真实凭据、MFA、分支保护、权限拒绝、破坏性数据操作或授权外远程动作时，保留证据并请求对应输入/授权；
- 同类实现或验证连续失败两次时按治理规则升级、重新诊断并改变方法；
- 缺陷触发数据迁移、公共 API 兼容、安全或跨系统影响时保持 L/XL 证据强度，不因“bugfix”名称降级；
- 仍有安全且授权内的可执行动作时持续收敛，不把普通技术困难包装成阻塞；
- 不得以赶版本为由降低验收标准、合并未验证提交或虚构外部 Provider/浏览器证据。

## 11. 本方向的完成判定

本 XL 任务只有在以下条件全部成立后才可进入最终 `COMPLETED`：

1. Owner 已明确结束收件并授权发布；
2. 所有纳入 0.1.1 的缺陷均有可追溯提交与行为证据；
3. Planner 已独立判定功能级 `PASSED`；
4. 各受影响仓库 main、annotated tag `0.1.1`、Release、CI 与资产身份一致；
5. 阶段三终态同步按 Planner 唯一终态值清单完成并复核；
6. 已知未完成内容、延期边界及后续开发线同步状态被准确记录。

在此之前，任何单缺陷成功、阶段测试通过或分支可用都不等于 0.1.1 已发布完成。
