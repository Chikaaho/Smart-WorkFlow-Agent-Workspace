# P64：高级流程编排方案

2026-10-08；Planner；XL；产品与架构方案。目标和正式通过条件以[主方向](direction-p64-mes-advanced-orchestration.md) R01—R12/A01—A12为准，本文说明能力如何组成业务闭环及选择理由。Owner已授权开始完整P64实施，阶段Ⅰ已通过，当前进入阶段Ⅱ；实现结构、接口、迁移和验证设计由Executor确定。

## 1. 方案结论

采用“业务主链关联多个已发布流程”的编排方式。主业务表单保存单据，任务级业务表单保存本轮办理数据，BPM变量提供有类型的数据引用，Trigger只读判断，可靠动作负责派发，岗位规则决定实际办理人，父子关系负责数据隔离、回写与等待。

运行主线为：**合法提交 → 冻结有效数据 → 解析变量 → 判断并匹配 → 可靠记录动作意图 → 发起关联实例 → 办理与结果回写 → 等待条件结算 → 继续业务主链**。用户从业务单据能查到每个环节的对象、轮次、责任人和结果。三个业务场景复用这些通用能力，场景差异由表单、流程模板及映射配置表达。

优先做数据产生到可靠动作的完整链，因为没有任务数据、类型变量和可靠触发，后续选人、子流程及MES只能形成页面演示。第二个能力边界解决跨人员、跨流程的数据协作，第三个边界再证明三场景实际业务结果。

当前P64=IN_PROGRESS；阶段Ⅰ由[验收08](../receipts/planning-review-phase-1-08-passed.md)确认PASSED，当前按[阶段Ⅱ方向](direction-p64-phase2-personnel-parent-child.md)继续人员与父子协作；完整[实施授权](authorization-p64-implementation-20261008.md)有效，整体A01—A12尚未通过。现状输入来自[已复核探索](../../../search_fallback/p64-mes-advanced-orchestration-readiness-20261008.md)及[事实附件](../../../search_fallback/p64-mes-advanced-orchestration-readiness-20261008-attachments.md)；7项缺失/5项部分具备表示接缝现状，不作为完成率。

## 2. 六项架构决策

以下为规划侧架构取向。Executor的工程ADR须记录实际实现、跨模块依赖、提交边界、兼容窗口和回退点；发现接缝无法满足产品语义时回报具体差距，由Planner调整方向。

| ID | 采用方向 | 理由与承担的代价 |
|---|---|---|
| PD01 编排与子流程 | 在BPM编排域管理独立已发布实例、父子关联、派发批次、输出回写和等待；复用P62可靠命令发起实例，图层提供配置与运行状态入口。 | 对应Owner多流程业务主链，能复用已验收发起与恢复接缝；编排域须承担派发、取消、回写和单次推进的一致性责任。引擎表达方式由Executor确定。 |
| PD02 类型变量 | 建立独立BPM变量契约：稳定引用、显式类型、三类来源、有效轮次、聚合及只读运行快照；通过受控表单读取接缝取得数据。 | 统一主表、节点表和系统值的业务表达，支持人员/部门/行集合；需新增设计器配置、发布校验和运行诊断。 |
| PD03 判断与动作 | BPM拥有独立的只读Trigger上下文和动作配置。脚本执行资源可复用既有运行基础，但BPM可用能力只限授权变量读取与标量返回；副作用由平台可靠动作承担。 | 保持预览与判断的明确权限边界，恢复时能分辨判断和动作结果；须证明执行空间、超时与排队限制实际生效。 |
| PD04 节点业务表单 | 人工任务绑定已发布低代码表单版本，任务与合法轮次拥有独立业务数据身份；意见、草稿和最终业务提交分别表达。 | 同时满足质量数据、人员选择、表格及历史回看；表单提交与任务办理需保持一致，数据可供后续变量读取。 |
| PD05 岗位委托 | 后台组织域维护通用源岗位→受托岗位关系，BPM依据组织上下文解析并冻结办理快照。 | 同一组织关系可供多个流程使用，岗位变更可追溯；组织管理权限与办理权限需分别控制，多任职由节点办理规则结算。 |
| PD06 隔离与回写 | 表单与BPM共享稳定来源行和允许字段契约，所有实际数据出口执行对象及行范围约束；回写按冻结行身份与版本处理。 | 防止父表排序、并发修改和旧轮次造成错行写入；需要同时覆盖读取、导出、办理、回写和冲突展示。 |

新增能力落在探索确认的表单、BPM和组织接缝内；IoT及OpenAPI承担设备/外部结果衔接。执行侧依工程宪法核实具体依赖方向，禁止通过扩大跨模块依赖绕过契约。

## 3. 用户配置与运行体验

| 入口 | 用户完成的工作 | 运行时应看到的结果 |
|---|---|---|
| 表单设计与发布 | 发布主单据及节点业务表单，配置检验、人员、部门、表格等字段。 | 表单版本与任务/轮次关联，草稿、最终提交及历史数据可区分。 |
| 流程设计器 | 选择节点业务表单；配置变量来源/聚合、触发事件、判断脚本、结果动作及输入输出映射。 | 发布前能定位无效引用、类型冲突、重复匹配、空集合与超限配置。受控预览显示取值及判断结果。 |
| 参与者配置与岗位管理 | 将业务职责绑定源岗位，配置特殊部门选岗及后台岗位委托。 | 待办能解释来源职责、委托路径、实际人员和名单冻结时点。 |
| 主子流程配置 | 选择已发布子模板，设置集合/分组、可见数据、回写字段、等待策略。 | 父流程展示预期子流程、已完成/失败项、回写结果和等待原因。 |
| 任务办理 | 各角色在授权数据范围填报、审批及确认业务动作。 | 只读/可填字段明确，重复提交返回原结果；失败项给出有权用户可执行的恢复动作。 |
| 业务单据与实例详情 | 查看主链、父子实例、检验轮次、来源行、变量快照、动作与数量账结果。 | 用户能从一个单据追踪到最终业务效果，辨认审批结果、动作受理和实际结算。 |

业务界面使用业务名称及可选对象；内部物理表列、实例ID和JSON由平台解析。角色入口与常见桌面/窄屏可用性属于A11交付条件。

## 4. 数据与生命周期约束

配置版本、运行快照和效果记录分别保留。流程发布冻结表单/变量/判断/动作/映射配置；进入合法轮次时冻结有效办理名单、读取来源和派发集合；运行后保留动作、子结果和实际业务效果。修改设计草稿不改变已运行实例。

| 关键交接 | 必须成立的关系 | 失败时的产品行为 |
|---|---|---|
| 节点业务提交→有效事件 | 最终表单与合法办理结果一致；退回、撤回和取消不混入完成事件。 | 部分提交失败不能形成可供后续使用的成功数据；已提交事件的派发责任可追踪。 |
| 事件→可靠动作 | 事件、轮次、触发配置、动作和目标集合有稳定业务身份；源业务与意图记录的提交关系由工程ADR明确。 | 意图记录失败不能报告动作已可靠受理；源提交已成功但动作失败时保留可恢复责任，不丢失。 |
| 动作→关联实例 | 同一目标重复/并发/恢复后对应同一合法结果；同身份输入冲突拒绝。 | 已成功目标沿原结果回查，恢复只处理未完成项。 |
| 子结果→回写→继续 | 来源行、允许字段、版本和有效轮次一致；所需回写提交后才可结算等待并推进一次。 | 冲突或失败展示阻断原因；回写失败不凑成功数。 |
| 取消/退回→旧批次 | 旧批次写回和推进权终止，已生效结果保留事实。 | 迟到结果进入可追踪记录，不能覆盖当前轮次；外部既有效果按真实状态处理。 |

四种等待策略沿主方向§3.3：ALL要求全部有效完成且必需回写已提交；ANY/COUNT采用闸口冻结结果；NONE在可靠派发意图提交后继续。剩余办理和迟到反馈保留独立版本。岗位委托采用主方向§3.4的组织范围、唯一有效关系、最多4跳及同轮冻结规则。

复检、派发、嵌套和脚本使用主方向§3.5的有限护栏。这里的设计值不作为容量或性能通过证据。关闭新入口后，存量办理、回调、查询和恢复仍须运行至收敛；旧定义/实例沿原义至结束。

## 5. 三阶段能力交付

阶段按可使用的产品能力划界；Executor自主安排内部工作，不从下表推导预设编码Step。每阶段提交自身适用的最小充分行为证据，Planner独立验收。

| 阶段 | 可交付结果 | 正式验收覆盖及停止边界 |
|---|---|---|
| I 数据到动作 | 用户发布节点业务表单与变量，实际办理形成数据，判断命中后可靠发起单个/集合/分组关联实例，并能查询动作结果和恢复。 | A01—A04；A11/A12中本阶段实际触及的配置、权限、可用性与兼容项一并核实。尚不裁决三场景或整体P64通过。 |
| II 人员与父子协作 | 后台岗位委托生效，上一轮表单聚合生成准确下一会签；单/N子流程隔离、准确回写、四等待策略及取消/退回/迟到处置形成真实闭环。 | A05—A07及相关A11/A12；阶段I已过项锁定，发生实现变化只重新核实受影响项。 |
| III 场景与整体交付 | MES正常/异常主链、招商集合规则/组织例外/聚合会签、安信四行三子流程完整运行，配置资产可复用，多角色可回查真实业务效果。 | A08—A12并复核A01—A07覆盖完整；全部通过后才进入整体PASSED及独立终态同步。 |

三阶段属于已获Owner实施授权的完整P64目标。阶段Ⅰ已通过，当前阶段ⅡREADY，Executor在授权范围内自主连续推进，各阶段由Planner独立验收；阶段回执不代表整体完成，不为内部步骤或已授权后续阶段重复索要许可。

## 6. 三场景的闭环终点

- **MES**：从工单追到领料逐行实际结算、质量轮次、异常整改、终检返工/报废/让步接收、成品入库和工单关闭。仓库有权角色确认数量效果；关联检验及设备/外部结果有来源身份与证据层级。
- **招商**：八组合真值表随发布冻结，未匹配有明确处置；部门职责先选源岗位再走委托，上一轮有效表单人员并集得到甲/乙/丙/丁的下一会签实际待办。
- **安信**：host-01/03、host-02、host-04按三个负责人派发；各子流程只取得授权行，反馈准确回写；前两个完成时保持等待，全部有效完成后生成一次运维复核，领导查看完整汇总。

完整ERP/WMS、周期调度、厂商实网、真实工厂部署和P62延期性能继续按主方向既有边界留账。新增持久数据的非空PG追加升级、旧实例兼容和回退窗口纳入A12；迁移版本与产品发布版本分别记录。
