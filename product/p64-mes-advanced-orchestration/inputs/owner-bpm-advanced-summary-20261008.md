# aPaaS BPM 高级流程功能简易摘要

## 1. 总体设计原则

平台中的复杂业务流程不应全部堆在一张流程图中。

整体采用：

**业务主链 + 多流程实例 + 表单 + BPM变量 + 触发器 + 动态参与者**

流程负责人员和状态流转，表单负责业务数据，BPM变量负责屏蔽数据来源，触发器负责跨流程判断和编排。

核心关系：

```text
低代码表单
    ↓
BPM变量映射
    ↓
bpmAdapter 动态取值
    ↓
Trigger JS 判断
    ↓
返回结果
    ↓
配置化触发动作
    ↓
发起其他流程 / 子流程
```

---

# 2. BPM变量

流程设计人员可以配置 BPM 变量，无需写代码。

变量只需要定义：

```text
变量名称
变量类型
数据来源
来源字段
```

数据来源至少包括：

```text
主业务表单字段
节点审批表单字段
流程系统变量
```

例如：

```text
变量：
inspectionResult

来源：
首件检验节点审批表单

字段：
检验结果
```

底层通过 `bpmAdapter` 动态读取实际数据。

内部实际可能对应：

```text
bpm_form_table_xxx.col_xxx
```

但这些属于平台内部实现，业务人员和普通流程使用人员无需关心。

---

# 3. 节点审批表单

人工审批节点默认只有：

```text
审批意见
[文本框]
```

但可以绑定一个低代码表单作为节点审批表单。

例如“质量检验”节点可以配置：

```text
检验结果：PASS / NG
缺陷类型：工艺 / 设备 / 物料
缺陷等级
不良数量
处理建议
审批意见
```

节点审批表单字段也可以成为 BPM 变量来源。

因此后续流程可以根据前面审批过程中产生的数据继续处理。

---

# 4. Trigger 触发器

触发器本身不需要动态展示全部业务字段。

流程开发人员提前配置 BPM 变量后，在 JS 中通过封装函数读取：

```js
const result = 流程变量取值('inspection_result');

if (result === 'PASS') {
    return 1;
}

if (result === 'NG') {
    return 2;
}

return null;
```

Trigger JS 只负责：

**判断和返回结果。**

不直接负责启动流程、修改数据库等操作。

实际动作配置化：

```text
结果 = 1
→ 发起 A 流程

结果 = 2
→ 发起 B 流程
```

即：

```text
Trigger JS
负责“判断”

Trigger Action
负责“执行”
```

这样可以避免 JS 脚本承担过多副作用。

未来返回值可以支持：

```text
Number
String
Boolean
```

例如：

```js
return 'PASS';
return 'REWORK';
return 'SCRAP';
```

# 6. MES 建议采用多流程编排

业务上是一条完整生产流程，但系统上可以拆成多个独立流程。

例如：

```text
生产工单流程
领料流程
首件检验流程
工艺异常流程
不合格品处理流程
返工流程
设备维修流程
成品入库流程
```

通过 Trigger 串联。

例如：

```text
首件检验结束
    ↓
读取 inspectionResult

PASS
→ 发起批量生产流程

NG + PROCESS
→ 发起工艺异常流程

NG + MATERIAL
→ 发起物料异常流程

NG + EQUIPMENT
→ 发起设备维修流程
```

异常流程处理结束后还可以再次触发：

```text
工艺异常整改完成
    ↓
重新发起首件检验
```

形成完整业务链。

# 8. 招商证券案例：动态分支 + 动态并行审批 + 审批人聚合

## 8.1 表格部门数据驱动分支

业务表单中存在一个表格，其中包含部门组件。

流程需要根据表格里的部门集合决定分支。

规则示例：

```text
只有 A
→ 分支 1

有 B 但没有 A
→ 分支 2

有 A + B
→ 分支 3

有 A + B + C
→ 分支 1

没有 A / B / C
→ 分支 4
```

本质上是：

```text
表格
↓
提取部门集合
↓
JS 集合判断
↓
return 分支结果
↓
进入不同流程分支
```

适合通过 BPM变量 + Trigger JS 实现。

---

## 8.2 根据部门动态生成并行审批人

分支结束后进入并行审批。

表格中所有部门需要解析审批人。

默认规则：

```text
部门
→ 部门分管领导
```

但存在特殊规则：

```text
总经办
→ 秘书
而不是总经办分管领导

指定特殊部门
→ 部门负责人
而不是分管领导
```

因此需要一个通用的动态参与者解析能力：

```text
业务表格中的部门
        ↓
去重
        ↓
组织架构解析
        ↓
特殊规则覆盖
        ↓
生成审批人集合
        ↓
动态并行审批
```

---

## 8.3 上一轮审批人聚合为下一轮会签人

每个并行审批节点的审批表单中存在：

```text
下一阶段审批人
[人员选择组件]
```

并行审批结束后：

```text
读取所有并行实例
        ↓
读取每个实例审批表单中的人员字段
        ↓
合并
        ↓
去重
        ↓
生成新的人员集合
        ↓
作为下一节点会签审批人
```

例如：

```text
审批 A：
甲、乙

审批 B：
丙

审批 C：
乙、丁
```

最终：

```text
甲、乙、丙、丁
```

作为下一会签节点参与者。

需要支持：

```text
多实例审批节点
审批表单字段读取
审批结果聚合
人员集合去重
动态会签参与者
```

# 9. 安信证券案例：表格拆分子流程 + Fan-out / Fan-in

业务场景：

每周领导发起：

```text
低利用率主机回收
```

---

## 9.1 主流程

领导发起流程，并选择若干运维人员。

运维人员在业务表单表格中填写主机信息：

```text
主机
利用率
负责人
其他信息
```

形成完整主机列表。

---

## 9.2 按负责人动态拆分子流程

主流程运行到指定节点以后：

```text
读取主机表格
↓
按照“负责人”分组
```

例如：

```text
host-01 → 张三
host-02 → 李四
host-03 → 张三
host-04 → 王五
```

拆分为：

```text
张三子流程
host-01
host-03

李四子流程
host-02

王五子流程
host-04
```

即：

```text
一张主表
↓
GROUP BY 负责人
↓
生成 N 份数据
↓
动态启动 N 条子流程
```

---

## 9.3 子流程数据隔离

负责人只能看到属于自己的主机。

例如张三只能看到：

```text
host-01
host-03
```

不能看到李四、王五负责的机器。

因此需要：

```text
父流程数据拆分
子流程数据映射
行级数据隔离
负责人动态绑定
```

---

## 9.4 子流程反馈

负责人填写：

```text
低利用率原因
是否可回收
处理建议
备注
```

提交后数据回写主流程对应行。

因此父子流程之间需要保存关联关系，例如：

```text
parentProcessInstanceId
parentFormInstanceId
parentRowId
childProcessInstanceId
ownerId
```

从而实现：

```text
子流程某一行
↓
准确更新
↓
主流程原表对应行
```

---

## 9.5 等待全部子流程完成

主流程不能在第一个子流程结束后继续。

需要支持 Fan-in / Barrier：

```text
预期子流程数量 = N
已完成子流程数量 = N
```

全部结束以后主流程才继续。

即：

```text
主流程
   ↓
Fan-out
   ↓
┌─ 子流程 A
├─ 子流程 B
├─ 子流程 C
└─ 子流程 N
   ↓
等待全部结束
   ↓
Fan-in
   ↓
主流程继续
```

---

## 9.6 子流程完成后的主流程

全部负责人反馈完成后：

```text
所有子流程结束
        ↓
反馈数据已经回写主表
        ↓
运维人员复核
        ↓
领导最终查看
        ↓
领导看到完整汇总数据表
```

完整链路：

```text
领导发起
    ↓
选择运维人员
    ↓
运维填写主机列表
    ↓
按负责人拆分
    ↓
动态发起 N 个子流程
    ↓
负责人分别反馈
    ↓
数据回写主表
    ↓
等待所有子流程结束
    ↓
运维复核
    ↓
领导查看完整汇总
    ↓
结束
```

# 10. 主子流程能力建议

平台后续至少应支持：

```text
普通单子流程
动态 N 子流程
按集合批量启动
按字段分组启动
父子表单数据映射
子流程局部数据权限
子流程结果回写
等待全部完成
等待任意完成
不等待
父子流程实例关联
动态参与者
```

可进一步抽象 Trigger Action：

```text
发起单个流程

批量发起流程

按集合元素发起流程

按字段 GROUP BY 后发起流程
```

等待策略：

```text
ALL
ANY
COUNT
NONE
```

# 11. 核心平台抽象

最终平台可以形成：

```text
Form
负责数据结构

BPM Process
负责流程结构

Approval Form
负责节点运行时业务数据

BPM Variable
负责统一数据引用

bpmAdapter
负责动态解析变量实际值

Trigger Script
负责复杂业务判断

Trigger Action
负责配置化执行动作

Participant Resolver
负责动态审批人解析

Parent/Child Process
负责复杂业务拆分与聚合
```

核心目标不是把所有业务场景写死，而是：

> 通过足够通用的表单、变量、触发器、参与者和主子流程能力，让复杂业务可以通过配置 + 少量 JS 完成。
