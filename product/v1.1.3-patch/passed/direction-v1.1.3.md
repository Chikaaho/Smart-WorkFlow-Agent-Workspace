## 1. 目标

Graph 执行经过超时恢复或取消之后，列表、详情和节点轨迹上显示的状态都要和实际一致，每一行都能点开详情。

| ID | 内容 | 验收标准 |
|---|---|---|
| B1（P72，优先） | 人工任务超时自动恢复后，会多出一条新的执行行（显示成功），原来那行一直显示「等待人工」，「待我处理」里已经没有这条任务；这类子执行行按执行编号查详情返回 404 | 超时恢复后，执行列表里不再有停在「等待人工」、实际已无待办的行：旧行要么变成与实际一致的终态，要么不再作为独立行显示，由执行方按根因选定一种并写明理由。列表里每一行都能打开详情，不返回 404。父执行、子执行、恢复产生的新执行之间的关系，在详情里能看出来。已有的旧数据行同样要显示正确，自动纠正不了的在回执说明原因和处理方式 |
| B2（P73） | 执行取消后，详情「节点轨迹」里的人工节点仍显示「等待人工」；头部状态是「已取消」，人工任务行是「已关闭」 | 取消后，节点轨迹里所有未完成的节点显示「已取消」或对应的中文终态，与头部状态、人工任务行一致。用受理号、执行编号各取消一次，结果相同 |
| B3 | Graph 执行列表「发生时间」显示 ISO 原值（1.1.2 第一轮登记的候选） | 显示为 `yyyy-MM-dd HH:mm:ss`，和流程模块列表的时间格式保持一致 |
| B4（2026-11-19 追加） | 图定义列表「更多 → 执行历史」把 graphDefId 用 `Number()` 转换，雪花 ID 精度丢失，跳过去列表 0 行（`execution-113-01.md` §5 发现，2026-08-21 起就存在） | graphDefId 全程按字符串透传；从入口跳过去以后，列表只显示这张图的执行，而且有数据 |

## 2. 非目标

- 不做 P67、P68，不加新节点，不改人工节点超时的时长和策略本身。
- 不改取消接口、详情接口的地址和入参格式。
- 原则上不加数据库迁移。如果执行方查清根因后认为 B1 必须加迁移，先在第一份回执说明理由，等规划确认后再做。
- 不处理 superadmin 跨租户取消的语义（`execution-112-02.md` §4.3，属于设计豁免）。
- 1.1.2 已锁定的取消行为（两种编号取消、级联关闭、404/错误返回）不重新设计，只验证没有退化。

## 3. 影响与风险

- B1 的根因还没查清。已知线索：子执行行不在受理行簿上（W5 既有边界），所以按执行编号查不到。执行方开工时先回答下面三个问题，写进第一份回执：
  1. 超时恢复时，系统新建了哪一行、旧行为什么没有进入终态；
  2. 详情 404 是因为查找只认受理行，还是这一行本身缺数据；
  3. 修复是改恢复时的状态写入、改列表和详情的读取，还是两样都改。
- B1 的修复会碰执行生命周期。1.1.2 修好的「取消时同步结果执行行」（G1）和「待办残留」（G2）不能退化。
- B2 的状态文案要和 1.1.2 B3 的状态中文映射一致，不另起一套叫法。
- 演示环境上已有 1.1.0 以来留下的旧行。部署后要确认这些行显示正确；纠正演示环境的数据前，先在回执列出要改的行，规划确认后再动。
