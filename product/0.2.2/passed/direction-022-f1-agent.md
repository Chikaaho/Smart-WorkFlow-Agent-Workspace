## 目标

Agent 成为完整的 graph+RAG 功能：供应商、模型、graph、知识库在一处统一管理；模型接入改用 LangChain4j，三种 API 格式（OpenAI Chat Completions、OpenAI Responses、Anthropic Messages）的任意兼容供应商都可接入；后台按配置复用单例实例，由模板装配构造。

## 非目标

见 D022-08。另外：F2 应用导入导出不在本方向；不改流程、表单模块；不改 Spring Boot 主版本。

## 分支

Server 与 Web 各自从核实后的 `develop` 建立并推送 `feature/0.2.2-agent`（Owner 规定功能轮用 `feature/` 前缀）。根仓沿 `develop-sw`。Web `vite.config.ts` 的在途改动不得提交。

## 分阶段

三个阶段依次推进。每个阶段完成后提交阶段回执，由规划独立验收；验收通过的阶段锁定，下一阶段才算正式开始。每个阶段末的提交就是该阶段的回滚点。

### 阶段 1：模型接入基座

1. 先验证 LangChain4j 依赖与现有 Spring Boot 3.4、Jackson 的兼容性，得出可运行的依赖组合（D022-01）。
2. 按 D022-02 建供应商、模型两级表（PG 与 H2 双方言迁移），按 D022-03 迁移旧数据并保持旧 id 引用可解析。
3. 三种格式各有装配模板；单例复用与失效按 D022-04；多密钥轮换按 D022-05。
4. 编排、图执行、单步调试三个调用点全部切换到新装配；图执行和调试校验模型及供应商是否启用。Spring AI 的 OpenAI/Ollama 组件移除；`application.yml` 中未使用的全局 spring.ai 默认配置一并清理。
5. 连通性测试改为对所选模型发起一次真实的最小调用：成功才判可用；鉴权失败、模型不存在、超时分别给出可读原因，不回传密钥。
6. 前端用"供应商 → 模型"两级管理替换现有大模型管理页：新增/编辑供应商（选格式、填地址和密钥，密钥脱敏、留空保留原值），在供应商下增删模型、标注能力、测试连通。

**完成断言：**
- 用 Command Code 三种格式各配一个供应商和模型（模型见下表），连通性测试全部成功。
- 在一个已发布的 graph 中，三个 LLM 节点分别使用这三个模型，执行成功并能看到各节点的真实输出。
- 填错密钥时，连通性测试报鉴权失败，响应和日志中都不出现密钥。
- 修改模型参数后，下一次调用生效，且不需要重启服务。
- 迁移前已有的模型配置迁移后可正常使用：旧 graph 不用改就能执行，旧会话可以正常打开。

### 阶段 2：graph 完善

1. 按 D022-06 实现发布版本快照，版本列表可查；执行和调试记录可以看到所用的快照版本。
2. LLM 节点改为选择"供应商+模型"，只列出启用中的模型；LLM 节点可以挂工具，在节点内完成工具调用循环。
3. graph 增加图级执行超时；超时按现有错误分类返回，不留下半完成的执行记录。
4. Agent 首页（现为空白页）改为统一工作台：供应商与模型、graph、知识库、最近执行的概览与入口。

**完成断言：**
- 同一个 graph 发布两次，生成两个快照。用第一版执行的记录在第二次发布后仍显示第一版。
- 一个挂了工具的 LLM 节点在真实模型下完成至少一次工具调用，执行轨迹里能看到工具的输入和输出。
- 超时场景返回超时错误。
- 首页各入口都能打开对应页面。

### 阶段 3：RAG

1. 知识库管理：新建知识库并选定一个 EMBEDDING 能力的模型；上传文档（至少支持 PDF、Word、TXT、Markdown）；切分参数可配；查看文档处理状态和分片数；能删除文档和知识库，向量数据随之删除。
2. 按 D022-07 用 pgvector 存储向量，按租户隔离。
3. 检索测试：输入问题，返回命中分片和相似度。
4. graph 新增知识检索节点：选择知识库，配置 topK 和相似度阈值，把检索结果写入变量，供下游 LLM 节点使用。

**完成断言：**
- 上传一份文档后完成切分和向量化，检索测试能命中文档中的具体内容。
- 一个"知识检索 → LLM"的 graph，在真实模型下回答出只有该文档里才有的事实。
- 另一租户看不到、也检索不到这个知识库。
- 删除文档后，再检索不到该文档的内容。
