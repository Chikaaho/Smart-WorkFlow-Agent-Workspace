## 目标

管理员可以把一个应用整体导出成一个文件，再导入到另一个环境或租户，得到一个可以继续编辑、逐个发布的新应用。导入不会覆盖或改动目标环境里已有的任何对象。

## 导出内容

以一个应用为单位，只导出各对象的当前版本：

- 应用：名称、图标、颜色、排序、可见范围（范围主体按 D022-13 处理）；
- 目录；
- 应用下的业务表单：表单定义、列表配置、扩展查询契约、交易动作定义；
- 关联流程：主表单属于该应用的流程定义，导出当前 `graph_json`；
- 这些流程节点引用的审批意见表单；
- 包内表单、流程用到的字典类型及字典项。

不导出：业务记录、子表数据、附件文件（D022-10）；表单历史快照和流程历史版本；生命周期审计、轨迹、交易流水等运行数据；菜单、工作台卡片、统计卡；外部数据源的连接信息和密码。

导出文件包含格式版本号和导出时的系统版本号。导入时格式版本不兼容就直接拒绝，并说明原因。

## 导入规则

1. **两步导入**（D022-15）：上传后先预检，展示包内对象清单、审批意见表单冲突、外部引用匹配结果；用户确认后才真正写入，写入在一个事务里完成，失败整体回滚。
2. **一律新建**（D022-11）：应用重名时自动加后缀；业务表单 key 冲突时自动重新生成；包内所有相互引用都按新 id、新 key 改写。
3. **审批意见表单**（D022-12）：目标租户没有同 key 的就新建并关联。有同 key 的，在预检结果里逐个列出，每项默认给一个随机新 key，用户可以采用或手动修改；新 key 必须在目标租户内唯一，否则不能确认导入。
4. **外部引用**（D022-13）：角色、岗位按编码匹配；字典类型同编码复用、缺失新建；数据源按名称匹配；指定用户、部门置空；流程分类按名称匹配。匹配不上的置空，记入导入报告。审批人被置空的流程节点要在报告里标出来，方便发布前补配。
5. **导入状态**（D022-14）：表单、流程全部为草稿。
6. **导入报告**：导入完成后可以查看、下载，内容包括新建对象清单（原 key → 新 key）、复用对象、置空的引用及其位置。每次导入留一条记录：操作人、时间、包名、结果。

## 权限与租户

- 导出、导入各设一个独立权限，默认授予现有应用管理角色（`form:app:manage` 所在角色）；按钮按权限显示。
- 导出只读取当前租户的数据；导入只写入当前租户。超管旁路时也以当前选择的租户为准，不跨租户写入。
- 导出文件里不出现任何密钥、密码或数据源连接串。

## 非目标

- 业务数据迁移、增量同步、覆盖更新已导入的应用。
- 多个应用合并成一个包、跨应用引用的整体打包：引用到包外表单的 REFERENCE 字段按外部引用处理（置空并记入报告）。
- 断点续导、导入撤销（导入后由管理员手动删除新应用）。
- Agent 的 graph、模型和知识库：它们与应用没有引用关系，不在包内。
- 修改流程、表单现有的发布和建表逻辑。

## 影响范围

- Server：应用中心（`sw_form_app` 系列）、表单定义及下挂配置、流程定义、字典的读取与新建；新增导出、预检、确认导入接口和导入记录表（PG、H2 双方言迁移）。
- Web：应用管理页增加导出、导入入口；导入预检与冲突处理页、导入报告查看。
- 新增权限与菜单脚本。

## 风险方向

- **引用改写漏项**：意见表单、节点表单、交易动作、子流程等待动作、表单之间的引用分散在 `graph_json` 和 definition JSON 里，漏改一处，导入后就会指向源环境的 id。执行前先列出全部引用位置的清单，导入后逐项校验，包内不允许残留源 id。
- **字典编码全局唯一**：唯一约束不含租户，跨租户导入时可能出现编码已被占用、无法新建的情况，按 D022-13 计入报告。
- **审批意见表单为空**：已有已知问题，运行时读的 `opinionForm` 前端没有写入入口。导出时如实带上节点里的现有配置，不在本功能中补齐这个设计器缺口；如果执行中确认会影响往返一致，就报告规划。
- **事务体量**：一个应用可能有几十张表单，确认导入时要在单个事务里完成；导入阶段不建物理表（草稿状态），体量可控。
- **IoT 设备、通知渠道**：设备 id 按外部引用置空；通知渠道是枚举值，原样保留。

## 完成断言

- 在租户 A 准备一个应用：至少 2 个目录、3 张业务表单（含 REFERENCE、DICT、TABLE、DATASOURCE 字段各一处），2 个流程（含审批人为角色、指定用户两种节点，引用审批意见表单，含一个交易动作节点）。导出后导入到租户 B，预检能正确列出对象清单和外部引用匹配结果。
- 租户 B 已有一个同 key 的审批意见表单：预检逐个提示，默认给随机 key；手动改成一个已存在的 key 时不能确认；改成唯一 key 后导入成功，流程节点关联到新表单，租户 B 原有的表单没有变化。
- 导入后的应用、表单、流程都是草稿；逐个发布后，表单能新建记录，流程能发起并走完一次审批。
- 包内引用全部指向新对象：数据库回读确认导入对象里不残留源租户的表单 id、流程 id 和交易动作 id。
- 指定用户的审批人被置空，并在导入报告里列出；按角色配置的审批人匹配成功。
- 同一个包再导入一次，生成第二个新应用，名称带后缀，表单 key 与第一次不同，第一次导入的应用不受影响。
- 导入过程中人为制造一次失败（比如中途抛错）：数据库里不留下任何部分导入的数据。
- 导出文件里搜不到数据源密码或连接串；没有导出、导入权限的用户看不到按钮，直接调接口返回无权限。
- 往返一致：把导入到 B 的应用再次导出，与原包相比，除 id、key 和置空的外部引用外，结构一致。
