## 2. 未通过项

### 2.1 验收 1 / 5 / 7：测试证据没有覆盖真实生产权限拒绝链

- step1 明确披露：生产 `GlobalExceptionHandler` 会捕获方法级鉴权抛出的 `AuthorizationDeniedException`，实际返回 HTTP 500 + body code=500。
- 同一回执又声明新增测试通过测试环境定制处理器，将该异常重抛给 `RestAccessDeniedHandler`，从而得到 HTTP 403 + body code=403。
- 因此“无权限请求 403”的自动化证据验证的是被测试专用逻辑改写后的链路，不是当前生产链路。completion/test-receipt 将其表述为真实请求级 403，与回执自身披露矛盾。
- D121 要求真实 API 与 Mock 的错误语义一致，并要求接口允许、拒绝、未认证分别有自动化证据；当前只能证明方法被拒绝且数据未修改，不能证明真实生产响应契约达到方向要求。

### 2.2 验收 4 / 5：停用普通角色仍继续授予菜单与按钮权限

- step3b 后端回执以请求级、Service 级和真实用户装配用例确认：角色停用后，roles 列表虽移除该角色，但菜单树和按钮 permission 仍按原绑定装配。
- 这意味着停用角色不能作为有效撤权手段，用户仍可能看到菜单、按钮并通过相应 permission 调用接口。
- 该行为直接影响普通角色授权边界，不能仅以“既有行为”作为非阻塞挂账后继续确认完整权限闭环。
- D121 禁止执行层自行扩项修复，但不等于规划层必须忽略执行回执暴露的真实安全缺陷；应先纳入权威问题注册与状态同步，再由规划层决定修正方向。

### 2.3 验收 4：Mock 的 `admin` / `superadmin` 身份语义未闭合

- step3b 前端回执显示默认 Mock 超管会话仍为 `roles:['admin']`、`superAdmin:true`，且登录 username=`admin` 会切换到该超管会话。
- D121 明确要求普通 `admin` 不触发超管旁路，并要求 Mock 中超管/普通管理员语义与当前后端双角色契约一致。
- 当前证据未说明该会话为何可以同时使用普通角色 code `admin` 与超管标志，也没有普通 `admin` 会话的显式授权/撤权对照；因此不能确认 Mock 双角色语义已消除历史混淆。

### 2.4 验收 10：阶段三同步不完整且终态提前

- stage3 回执确认两项可复现生产问题均未登记新 issue；`knowledge/known-issues.md` 只给已关闭 I49 增补后续证据，没有为真实 500 响应和停用角色继续获权建立开放问题。
- memory/handoff 虽记录“挂账”，memory/issues 却没有对应开放条目，信息层次不完整。
- 在上述偏差未处理前，功能清单 F02/F03→✅、P1 核销、功能数 26 都只能视为执行层提前同步，不能获得规划层最终确认。
