# 治理方向：治理信息与终态契约单一化

> **任务性质**：管理员治理任务，不属于业务功能实现，不进入业务功能三阶段状态机。
> **下发角色**：规划。
> **承接角色**：管理员。管理员须在独立的「管理员」会话中读取 `system.md` 与 `roles/admin.md` 后执行。
> **状态**：PASSED（2026-08-25，管理员治理完成且 GR-1 补正经规划核对通过）。

## 1. 目标（一句话）

建立“Planner 可直接决策的最小状态摘要、当前状态与历史记录分离、单一严格终态契约与公共 Validator、核心规则唯一权威、Governance Implementation 明确归属”的统一治理基线，消除信息中转、状态残留、宽松校验、Harness 漂移和职责歧义。

## 2. 治理裁定

### G1. `memory/` 必须是 Planner 可用的最小状态摘要

- `memory/` 不得退化为只指向 Planner 无权读取的 `knowledge/` 的跳转页。
- 在不复制完整知识库的前提下，至少直接保存足以支持 Planner 恢复与决策的当前摘要：当前治理/业务状态、活动任务、唯一下一动作、已锁定基线摘要、未关闭阻塞、近期有效决策和必要硬约束。
- 每项摘要须附权威来源路径与“截至日期/同步点”；发生冲突时仍以 `knowledge/` 为权威，由有权限角色修正摘要。
- 保持短文件与总量上限；历史证据、完整命令输出和完整决策正文不得回填进 `memory/`。

### G2. 当前状态与历史状态物理分离

- `knowledge/current-status.md` 只保存一份最新当前快照，不再混存过程历史。
- 历史状态迁移到独立、可追溯、追加式的 history/decision 载体；迁移时保留日期、决策号和来源，不丢失审计链。
- 当前状态更新必须是整份快照替换或等价的结构化原子更新，不允许“顶部更新、下部残留”。
- `session-handoff`、`memory` 和其他入口不得成为第二份当前状态；它们只保存各自职责内的摘要或指针。

### G3. 终态契约采用严格、封闭校验

- 合法 `state` 使用显式白名单/枚举；未知、大小写变体和自造状态一律失败。
- 所有必填字段同时校验：存在、非空、类型正确、格式正确、取值范围正确；不得只检查键存在。
- 对数组、对象、数字、布尔值和字符串分别定义边界；禁止通过隐式类型转换、空白字符串、`null`、空集合或额外未知字段绕过约束。
- 合法终态与角色/阶段组合必须可判定；失败输出应精确到字段和原因，且不从自然语言推断或补默认值。
- 契约必须同时包含正向样例与逐类反向样例，覆盖未知状态、缺字段、空字段、错类型、越界值、额外字段和角色/终态不匹配。

### G4. 只维护一份公共终态契约与 Validator

- `.codex/governance/terminal-contract.json` 或管理员确认后的等价单一位置，是终态 schema/状态集合的唯一机器权威。
- 只维护一个公共 Validator 实现；Claude、Codex 及后续 Harness 的 Hook/入口只负责提取标准输入、调用公共 Validator、透传统一退出码与诊断，不复制状态表、字段规则或校验分支。
- Harness 适配层不得自行扩展或削弱合法终态；契约或 Validator 变更必须由同一组契约测试证明所有 Harness 同步生效。

### G5. 核心规则唯一权威，历史材料退出规范入口

- 角色门禁、权限边界、状态机、终态、阶段协议和停止条件等核心规则，每条只能有一个规范定义位置；其他文件仅作短引用，不复制改写正文。
- `system.md` 保留唯一宪法入口与公共协议；角色专属规则只在对应 `roles/*.md` 定义；工程专属规则只在对应工程宪法定义。若管理员盘点发现现有切分仍产生重复，应先给出权威归属矩阵，再按矩阵去重。
- 历史原因、事故复盘、迁移说明和 superseded 规则迁入独立 `decision/`、`history/` 或现有等价知识载体，不得继续作为当前规范正文。
- 所有 Harness 入口只做加载和路由；全文审计不得存在与权威定义竞争的规则副本。

### G6. 明确 Governance Implementation 的归属与隔离

- `.claude/hooks/`、`.codex/hooks/`、公共 Validator、终态契约及其治理契约测试统一归类为 **Governance Implementation**。
- Governance Implementation 由 Admin 维护，但权限只覆盖治理执行机制，不因此获得业务源码、业务测试、业务实现或业务状态裁决权限。
- 治理脚本与业务源码在目录、权限清单、评审范围和测试入口上保持可验证隔离；Hook 只执行治理门禁，不承载业务逻辑。
- 将该分类和允许/禁止清单写入唯一权威治理规则，并同步各 Harness 入口的引用，不复制定义。

## 3. 非目标

- 不修改任何后端、前端业务源码、业务测试、数据库迁移、依赖或部署配置。
- 不改变现有业务功能状态、完成数量、P/I 编号、测试基线或验收结论。
- 不借治理去重重新设计三角色职责，也不扩大 Admin 到业务规划、业务实现或业务验收。
- 不为每个 Harness 新建独立 schema、Validator 或状态表。
- 不删除历史记录；只允许迁移到明确的历史载体并保留可追溯关系。
- 不以文档声明代替可执行的 Validator、契约测试和跨 Harness 调用证据。

## 4. 影响范围（治理级）

- 工作区宪法与角色规则：`system.md`、`roles/*.md`。
- 压缩记忆：`memory/*.md` 的内容契约、模板与维护规则。
- 完整知识状态：`knowledge/current-status.md` 及管理员确定的历史归档载体。
- 终态机器契约与公共校验：`.codex/governance/terminal-contract.json`、公共 Validator、治理契约测试。
- Harness 适配：`.claude/hooks/`、`.codex/hooks/` 及其入口配置/说明。
- 工程宪法、知识索引和历史 decision/history 文档中受权威归属调整影响的引用。

实际文件清单由管理员先做只读盘点后确定；不得因本方向列举路径而跳过引用扫描或擅自触碰业务代码。

## 5. 风险方向

1. **摘要再次退化**：只强调“唯一权威”可能再次把 `memory` 清空成不可用指针；验收必须直接证明 Planner 无需读取 `knowledge` 即可恢复最小上下文。
2. **历史丢失**：拆分 `current-status` 时若直接删除旧段落会破坏审计链；必须先建立映射再迁移。
3. **双实现假统一**：两个 Hook 即使引用同一 JSON，仍可能各自实现不同校验；必须证明它们调用同一 Validator 入口。
4. **严格化破坏合法回执**：收紧 schema 可能拒绝现有合法终态；需用当前合法样例建立兼容基线，并将不合法兼容行为明确拒绝。
5. **规范去重造成悬空引用**：移动历史或规则正文后，旧章节号和入口可能失效；必须做全工作区非业务文本引用审计。
6. **Admin 权限外溢**：将脚本归为治理实现不能成为读取/修改业务代码的理由；文件清单和零业务改动证据必须可复核。

## 6. 验收标准

管理员完成后提交治理回执，至少以可复现证据证明：

1. `memory/` 每个保留文件都含 Planner 可直接使用的最小摘要或有明确职责；关键恢复信息不再全部是不可读 `knowledge` 的裸指针，并报告各文件字节数与总量。
2. `knowledge/current-status.md` 只含单一最新快照；历史记录已迁移到独立载体且有“原位置 → 新位置”映射。对旧状态、旧下一动作、旧基线做全文零残留审计，同时单独证明历史记录仍可追溯。
3. 终态契约对所有 `state` 使用封闭白名单，并对全部必填字段执行存在、非空、类型、格式和范围校验；未知字段策略明确且被测试锁定。
4. 契约测试至少逐类覆盖：全部合法终态、未知状态、缺字段、空白/`null`、错类型、越界值、额外字段、角色/阶段不匹配；输出包含用例总数及通过/失败计数。
5. Claude、Codex 两套 Hook 均调用同一个公共 Validator；静态全文审计证明 Harness 目录内不存在第二份状态白名单、字段 schema 或独立校验分支。
6. 产出“核心规则 → 唯一权威文件/章节 → 引用方”矩阵；重复正文和局部矛盾清零，历史原因与事故经验已迁移为非规范 decision/history 内容，入口引用有效。
7. 宪法明确 Governance Implementation 的定义、Admin 允许维护范围与业务隔离红线；治理变更 diff 对后端/前端业务源码、业务测试、迁移和业务状态文件为零。
8. 两套 Harness 使用相同合法/非法样例运行后得到一致退出码与字段级诊断；任一 Harness 不能单独接受公共 Validator 拒绝的输入。
9. 回执提供：只读盘点、实际修改文件清单、原路径到新路径映射、契约测试原始摘要、跨 Harness 一致性结果、全文零残留查询及 `git diff --check` 结果。

## 7. 管理员执行边界

- 执行前先读取 `system.md`、`roles/admin.md` 和两端工程宪法中与治理配置相关的章节；若当前 Admin 权限文本与 G6 的目标分类发生冲突，先在回执中列出冲突，再在本次用户已下发的治理授权范围内完成权威边界修订。
- 先做只读盘点并形成“现状 → 权威目标 → 迁移/去重动作”矩阵，再修改治理文件。
- 可自行拆分治理实施与验证工作，但不得转化为业务功能 Step，不得执行 Maven、pnpm、数据库或部署命令。
- 只运行静态检查、治理契约测试和 Hook 级隔离验证；若现有测试入口会编译或运行业务工程，必须停止并报告，不得越权执行。
- 不执行 Git 提交、推送、历史改写或发布；如需发布，另行向用户说明仓库、远程、分支、范围与风险并取得明确授权。
