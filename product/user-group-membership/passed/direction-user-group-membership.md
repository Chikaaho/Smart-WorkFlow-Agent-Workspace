## 1. 目标（一句话）

建立租户内扁平虚拟用户组的维护与成员多对多绑定闭环，使跨部门人员能够形成稳定、可复用的业务集合，并为后续流程与权限消费提供不依赖部门层级的引用基础。

## 2. 产品语义

### 2.1 用户组模型

- 用户组是**租户内的扁平虚拟集合**，用于跨部门归集人员；它不是部门树节点，不参与部门上下级关系，也不改变用户的唯一归属部门。
- 每个用户组具有租户内稳定且唯一的业务标识、名称、启停状态和说明；业务标识创建后不可随意改变，避免后续流程或权限引用失效。
- 用户组不建立父子层级，不设置负责人、审批流或有效期；创建审计沿用系统统一审计字段。
- 用户组采用逻辑删除。删除后不得再出现在可选列表或有效成员查询中，原业务标识能否复用必须遵循双方言一致且有自动化证明的安全语义，不允许产生两个同时有效的同标识用户组。

### 2.2 成员关系

- 用户与用户组是**多对多**关系：一个用户可加入多个组，一个组可包含零个或多个用户。
- 成员关系必须支持保存、追加或整量替换、移除、清空和详情回填；组主记录与成员变更须保持事务一致，失败时不得留下半完成关系。
- 只允许绑定同租户、未逻辑删除且当前操作者有权查看的用户；不得借用户组入口绕过现有租户隔离或五档数据权限。
- 用户被停用、锁定或逻辑删除时，不静默物理删除历史成员关系；有效成员查询和选择器必须排除不可用用户，同时管理详情应能以可解释方式呈现已失效成员，便于管理员清理。
- 用户组停用后保留配置与成员，但不得作为后续业务的新引用对象；重新启用后恢复可选资格。

### 2.3 权限边界

- 用户组本轮只是业务人员集合，**不是角色、菜单、按钮或数据权限主体**；加入用户组不得授予角色、菜单、按钮、数据范围或 `superadmin` 能力，也不得改变登录认证结果。
- 用户组管理应具有独立的查看与管理权限，并通过生产菜单可达；普通已授权管理员可维护其数据权限范围内的组和成员，未认证、缺权和已授权请求分别有明确 401/403/成功证据。
- `superadmin` 继续沿用既有旁路语义，但用户组实现不得新增任何基于用户 ID 的超管判断。

## 3. 非目标

- 不把用户组直接绑定角色、菜单、按钮或五档数据权限，不改登录权限装配、`sys_user_role`、`sys_role_menu` 或 `sys_role_dept` 既有语义。
- 不在本轮实现 BPM 候选人/候选组、流程节点指派、通知群发或其他消费端；M01-F04-01 的“供流程与权限引用”只有在后续消费端真实接入后才能整体判定为 ✅。
- 不实现用户组层级、负责人、动态规则组、成员审批、有效期、批量导入导出或跨租户组。
- 不重做 D97/D101 已完成的部门、岗位、普通角色、角色菜单/按钮和组合查询能力。
- 不合并 M02-F02/F03 的菜单自身管理、全系统 Controller 权限纳管等并列缺口。
- 不处理前端用户组合查询旧注释或其他与用户组无直接关系的历史文档欠账。

## 4. 影响范围（模块级）

### 后端

- System 用户组领域：新增用户组主模型、成员关系模型、持久化、服务、管理接口和查询契约。
- System 用户领域：只增加用户组成员候选、回填或必要的用户组关联查询，不改变既有用户 CRUD、部门/岗位/角色绑定契约。
- Security / DataScope：复用现有认证、租户和数据权限能力；为用户组管理增加最小独立权限，不新增新的授权模型。
- Root Flyway：在执行前重新确认当前链尾；基于已知 V33 后新增 H2/PostgreSQL 同语义迁移，覆盖主表、成员关系、唯一约束及必要索引，不修改已发布历史迁移。

### 前端

- System 用户组管理：列表筛选、创建、编辑、启停、逻辑删除、成员选择和详情回填。
- 契约/API：稳定区分用户组业务标识、展示名、状态和成员 ID，不把部门、岗位或角色 ID 混作组成员。
- 路由、生产菜单与权限：提供真实可达入口及查看/管理权限表达。
- Mock/夹具：与真实接口的租户、状态、成员替换/清空、不可用成员和权限语义一致。

### 规划与知识状态

- 功能完成后可关闭 I36 中剩余的“用户组绑定”缺口；不得据此宣称用户组已经接入流程或权限消费端。
- M01-F04-01 在本轮完成后最多由 ⬜ 上调为 🟦；只有维护、成员绑定以及流程/权限实际引用全部闭合后才能升为 ✅。

## 5. 风险方向

1. **权限概念混淆**：用户组不得被实现为隐式角色或数据权限主体；必须证明加组前后用户权限集合不变。
2. **跨租户与数据权限越界**：成员候选、绑定请求、列表和详情均可能泄露其他租户或超出操作者数据范围的用户。
3. **关系半写入**：用户组主记录与多成员关系写入、替换、清空和删除必须具有事务一致性及失败回滚证据。
4. **稳定引用**：业务标识、逻辑删除和将来消费端之间需保留稳定契约，不能依赖可变名称或前端展示值。
5. **失效成员语义**：停用、锁定、删除用户不应继续成为有效成员，但也不能因状态变化静默丢失历史配置。
6. **分页与重复行**：成员多对多查询不得导致用户组列表或总数重复；组合筛选必须保持结果集与总数一致。
7. **迁移兼容**：双方言表、约束、索引与逻辑删除唯一语义必须一致，新库和既有 V33 库升级均须 migrate + validate。

## 6. 验收标准

1. 用户组列表、创建、编辑、启停、详情和逻辑删除完整可用；业务标识在租户内稳定唯一，名称/状态筛选、无结果和非法输入响应稳定。
2. 用户与用户组多对多关系支持保存、替换、移除、清空和回填；一个用户加入多个组、一个组跨部门包含多个用户均有自动化证据。
3. 构造成员写入失败时，组主记录和全部成员关系保持事务一致；删除组后有效查询不再返回该组或其成员关系。
4. 双租户、不同数据权限范围、逻辑删除用户、停用/锁定用户和停用用户组均有结果集证据；跨租户 ID、不可见用户 ID 或不存在 ID 的构造请求必须拒绝且不产生部分写入。
5. 加入、移出或查询用户组不会改变用户角色、菜单、按钮、数据范围、登录结果或 `superadmin` 判定；以权限快照或等价自动化测试证明零隐式授权。
6. 用户组管理入口在生产菜单真实可达；未认证、缺少查看/管理权限和已授权请求分别有 401、403 和成功证据，前端按钮与后端强制鉴权一致。
7. H2/PostgreSQL 迁移语义一致；全新库 V1→链尾以及既有 V33→新链尾均 migrate + validate，通过唯一性、逻辑删除、外键/索引和冲突安全测试；不得修改既有 V1-V33 的已发布内容。
8. 前端列表、表单、成员选择、替换/清空、失效成员展示、权限和 Mock 均有专项测试；typecheck、lint、test、build 四门全绿。
9. 后端受影响模块测试与项目级全量测试全绿，数量不低于当前 **600 tests** 基线；前端数量不低于当前 **69 spec files / 628 tests** 基线。
10. 所有编译测试遵守 2G 内存上限与前后端互斥；回执提供实际互斥检查、命令、退出码、测试计数及任何未运行的 PG/真实服务证据边界。
