# P51 Agent Coding Engine 管理员治理总方向

> 下发角色：规划（Planner）
> 指定角色：管理员（Admin）
> 方向状态：READY
> 日期：2026-08-31
> 任务性质：Owner 特别授权的单任务治理收口
> 唯一入口：`product/p51-agent-coding-engine-decoupling/README.md`

## 一、Owner 特别授权

Owner 明确要求本轮 P51 全部交由管理员治理，不再拆分管理员与执行角色任务。本方向是本轮唯一活动任务，覆盖此前尚未核销的根级运行时、治理入口、项目配置、Harness、语言无关契约和证据收口事项。

本轮管理员在不接触真实业务实现的前提下，可统一读取和维护根工作区全部 Engine 非业务文件，包括：

- `system.md`、`roles/`、根 README、AGENTS 与项目说明模板；
- `.codex/`、`.claude/` 中的治理契约、Validator、Hook 和 Harness 配置；
- 根级 `knowledge/`、`memory/`、`product/`、`todo/`、`search_task/`、`search_fallback/` 的通用初始内容、索引、模板和治理记录；
- 本功能方向、历史回执和新的持久证据包；
- 为治理验证创建的临时、无业务语义示例工作区和仓库夹具。

本特别授权不授予管理员读取或修改真实 coding 仓业务源码、业务测试、迁移、业务配置，不授予业务状态裁决权，也不授权远端发布或历史改写。

## 二、最终目标

将 `main` 收敛为可直接使用的通用 Agent Coding Engine：根级标准结构完整；用户只需填写项目说明并配置一个或多个 coding 仓库目录，即可按统一角色和工作流协议开始工作；Engine 不绑定任何项目、语言、框架、工具链、仓库数量或生命周期动作。

`develop-sw` 继续作为 Smart-WorkFlow/OA 示例，现有分支、分叉点和回滚记录保持不变。

## 三、根级运行时契约

`main` 根目录直接提供：

- `system.md`、`roles/`；
- `knowledge/`、`memory/`；
- `product/`、`todo/`；
- `search_task/`、`search_fallback/`；
- 项目说明、README、AGENTS；
- 治理契约、Validator、Harness 配置和 Hook。

标准目录必须包含可直接运行的通用初始入口。所有内部引用均须真实存在并可解析；新项目不需要复制目录、运行结构生成器或改写通用治理文件。

## 四、项目说明契约

项目说明是 Engine 识别当前实例的唯一项目配置入口，以仓库为基本单元声明：

- 项目身份、目标和边界；
- 仓库标识、目录、职责及单仓/多仓关系；
- 每个仓库的工程规则入口；
- 项目实际提供的工程动作、验证入口、适用条件与资源约束；
- 项目实际需要记录的验证基线和生命周期字段。

除项目身份、仓库目录和职责外，其余工程动作按项目实际情况可选。项目未声明的动作，Engine 不推断、不生成、不调用，也不把缺失判定为异常。

## 五、语言与工具链无关契约

- Engine 面向任意语言、框架、工具链以及无编译阶段的项目；
- 通用治理只使用“工程动作”“项目验证入口”“coding 仓库规则”等概念；
- 是否存在编译、测试、数据库迁移、服务启动、制品构建或部署，由项目说明决定；
- 资源限制和跨仓并发约束由项目说明或仓库工程规则针对具体动作声明；
- 阶段三只记录项目已声明且本功能实际涉及的验证基线，不固定要求后端、前端、迁移或其他技术类别；
- Harness、Hook 和终态契约只校验角色、流程、证据与终态，不识别或限制语言、扩展名、包管理器、框架或数据库。

## 六、治理与权限不变量

- 用户必须显式声明一个角色；
- Planner 不读取 `knowledge/` 和 coding 仓库，不执行实现；
- Executor 不作规划裁决；
- Admin 常规职责仍是治理维护，本轮扩展范围只适用于本 P51 总任务；
- 三阶段、状态机、`ready/receipts/passed` 流转、阶段三与终态机器契约保持原语义；
- Admin 的治理验证不得生成 Planner `PASSED` 或业务 `COMPLETED`。

## 七、Harness 与工作区定位

Harness 和 Hook 必须能够从以下位置定位同一个 Engine 根及其终态契约：

- Engine 根；
- Engine 自身普通子目录；
- 项目说明声明、且具有独立 `.git` 的 coding 仓根及其子目录。

定位机制不得把嵌套 coding 仓的 Git 根误认为 Engine 根。合法终态应放行，非法或缺失终态应按机器契约阻断。

## 八、治理验证边界

管理员可以创建临时无业务语义夹具，验证 Engine 契约，但不得伪造跨角色业务裁决。治理验证至少覆盖：

1. 根级标准文件与内部引用全部可解析；
2. 项目说明可读出项目身份、单仓/多仓关系、工程动作和验证入口；
3. 一个无编译、迁移和部署动作的项目可正常登记其实际验证入口；
4. 一个异构多仓项目的仓库动作、资源约束和验证基线互不串用；
5. 未声明工程动作产生零调用；
6. 两个独立 Engine 工作区的项目身份、路径、状态、记忆、方向、回执和待办无交叉；
7. Engine 根、普通子目录和嵌套 Git coding 仓目录下的 Hook 正反行为一致；
8. 终态契约与 Validator 原有合法状态集合、字段和判定语义不变。

示例方向、探索回执、执行回执等文件可作为治理通道夹具，但最终规划裁决仍由本任务结束后的规划角色作出。

## 九、允许修改范围

管理员可按最终目标修改：

- 根级 Engine 文档、项目说明模板和入口；
- `system.md`、`roles/`；
- 根级标准知识/记忆/产品/待办/探索目录的通用初始内容；
- `.codex/`、`.claude/` 治理实现和配置；
- P51 顶层索引、总方向、管理员总回执和持久证据包。

管理员可删除已确认不属于最终根级架构的通用化中间文件，可整理未提交的本任务改动，并在全部验收证据成立后创建一个或多个本地中文 Conventional Commit。不得修改 `develop-sw` 历史、真实 coding 仓内容或远端状态。

## 十、禁止事项

- 不读取或修改真实业务源码、业务测试、迁移和业务配置；
- 不执行真实项目的编译、测试、数据库或部署动作；
- 不建立语言、框架、包管理器或工具链白名单；
- 不固化容量数值、固定命令、环境变量、端口、仓名、测试计数或迁移版本；
- 不生成 Planner 验收结论，不把治理夹具标为业务通过；
- 不执行 push、force push、远端分支删除、tag 发布或历史改写；
- 不重复创建分支或改变已锁定分叉与回滚点。

## 十一、最终验收标准

1. `main` 根级标准结构和初始状态完整，所有内部引用为 0 缺失。
2. 仅填写项目说明中的项目身份和 coding 仓库目录，即可建立当前实例；工程动作完全按声明加载。
3. 通用文件不包含固定项目事实、本地绝对路径、固定仓名、语言/框架/工具链要求或固定资源数值。
4. 无编译项目、异构多仓项目和未声明动作零调用均有持久行为证据。
5. 两个独立 Engine 工作区的正向归属和反向零交叉断言成立。
6. 从嵌套 Git coding 仓目录触发 Hook 时仍能定位 Engine 根，合法/非法终态结果符合机器契约。
7. 三角色权限、三阶段、状态机和终态机器契约没有扩权或语义变化。
8. `main` README 能让首次使用者完成项目配置，并能进入 `develop-sw` 示例。
9. 所有证据持久保存在 `product/p51-agent-coding-engine-decoupling/receipts/evidence-admin-consolidated/`，包含固定输入、命令、退出码、原始输出及正反断言。
10. 实际修改只属于本总方向；真实 coding 仓、`develop-sw`、远端和历史均未改变。

## 十二、管理员总回执

管理员只提交一份总回执：

`product/p51-agent-coding-engine-decoupling/receipts/completion-admin-p51-engine-governance-consolidated.md`

回执必须包含：

- 最终文件与提交清单；
- 验收标准 1～10 的逐项核销；
- 持久证据包索引；
- 权限和终态语义差异核对；
- 全文通用性检查；
- 工作树、提交、回滚点和未远端发布证据；
- 未触碰真实业务实现与 `develop-sw` 的范围声明。

管理员以治理任务完成结论结束，不裁决 P51。规划角色仅以本总方向和该总回执进行下一次验收。
