## 1. 背景与等级裁决

P61 最初按 L 级探索。探索确认问题已超出局部文案调整：Server 的公共错误响应缺少稳定语义标识和安全诊断分层，认证码与流程码存在数值冲突，Web 对网络与服务异常大量塌缩，前后端存在文案与类型双权威，全系统尚未真正接入国际化，同时存在原始异常、租户标识、SQL/JDBC、第三方响应与完整 Java 栈向用户界面或接口消费者外露的路径。

因此 P61 升级为 XL：它是一次跨 Server/Web、跨认证安全与公共错误契约、需要兼容窗口和分阶段验收的系统级治理。升级不改变 P61 的产品目标，也不授权无关架构重构。

## 2. 产品目标

1. 所有真实可达的用户提示都使用自然、行业惯用、符合目标受众认知且能指导下一步的表达，不再把内部实现状态、代码标识或原始异常当作用户文案。
2. 建立稳定的机器错误语义；既有数值 code 保持兼容，新增语义能够跨模块唯一识别，Web 不再依赖冲突数值或文案子串决定行为。
3. 将用户消息与诊断信息彻底分层：用户得到安全、可行动的结论和可沟通的事件引用，运维仍能在受保护载体中定位真实原因。
4. 正式启用 zh-CN 与 en-US 两套语言能力，Server、Web 与 Element Plus 在同一会话中保持语言一致，不出现局部中英混杂。
5. 建立术语、错误语义和静态文案的单一权威；同一语义跨页面、跨端、跨桌面/移动入口不得漂移。
6. 明确区分成功、处理中、可重试、不可重试、权限不足、对象不存在、输入错误、冲突和系统故障；加载失败不能再伪装成空数据或无反馈。

## 3. 核心规划裁决

### 3.1 公共错误契约与机器码兼容

- 既有公共响应的 code、msg、data 字段继续兼容；本轮不删除、不改名，也不把原始诊断详情加入 msg。
- 新增一个可选、稳定、全局唯一且带业务命名空间的语义错误标识 errorKey。errorKey 是新增调用方和 Web 分流、国际化的首选机器契约；数值 code 继续服务旧调用方。
- 本轮不直接重编号既有 0.1.0 数值 code。认证与流程的 2101—2104 冲突、BPM 内部 2415 重复通过不同 errorKey 明确消歧，并在错误目录中登记为已弃用的数值歧义；新错误不得继续复用这些冲突值。
- Auth 2101—2104 的现有安全收敛语义保持不变。Web 不得再仅凭 2101—2104 数值选择业务文案；冲突码缺少 errorKey 时使用安全通用兜底，不猜测所属模块。
- Web 的 1204—1208 兜底必须恢复为后端真实码义；表单设计器本地预检使用独立的 Web 语义键，不能伪装成后端错误码。
- ApiResponse 对 msg/message 的类型与运行时约定必须形成一个正式兼容契约。旧字段读取可在声明的兼容窗口内保留，但不得继续作为未说明的隐性双字段。
- 任何用异常文案、子串或完整 msg 控制业务分支的路径必须解除。P61-S-BPM-16 是已知强制前置；全系统还需以同一原则完成零残留核对。

### 3.2 用户消息与诊断信息分层

- 公共 msg 只承载面向当前受众的安全结论与恢复建议，不出现 Java 字段名、类名、Bean、数据库列、SQL/JDBC、文件路径、栈、tenantId、密钥片段、第三方原始响应或未经筛选的 exception message。
- 不在通用 R 响应中新增可直接透传的原始 detail 字段。需要定位的失败必须提供稳定事件引用，并能与服务端结构化日志、受权限保护的诊断记录或既有业务记录关联；事件引用的兼容承载形式由执行层依据现有追踪能力确定。
- 完整异常与第三方原文保留在仅授权运维可访问的日志或诊断载体中，并执行脱敏、长度限制和访问审计。普通用户、未认证用户及一般业务管理员均不能获得完整栈或敏感环境详情。
- 管理员页面可以展示经过分类和脱敏的诊断摘要，例如失败类别、第三方状态码、发生时间和事件引用；不得把“管理员可见”当作原始栈、租户秘密或外部响应全文公开的理由。
- 开放 API 的开发者受众可以得到稳定 errorKey、合法参数名称、协议状态和可执行修复建议，但仍不得得到服务端栈、密钥、内部路径或未经筛选的第三方原文。

### 3.3 双语与语言选择

- P61 正式交付 zh-CN 和 en-US。所有静态用户文案、服务端可外显错误、表单校验、空态、对话框、通知、状态标签、无障碍标签及 Element Plus 内建文案均必须有两种语言。
- Web 在登录页和登录后应用壳提供同一语言选择能力，并在当前浏览器中持久化；未选择时以浏览器语言为候选，无法识别时回退 zh-CN。
- Web 请求向 Server 传递当前语言；Server 对可本地化的用户消息使用同一语言。errorKey、code、事件引用和诊断记录不随语言变化。
- 不允许以机器翻译占位、中文夹英文实现词或英文夹中文兜底完成验收。动态业务名称、用户输入与第三方品牌名保持原值，但周围句式按当前语言生成。
- 本轮只交付 zh-CN/en-US，不扩充其他语言，也不新增账号级语言偏好或跨设备同步。

### 3.4 单一文案源与术语治理

- 先建立覆盖终端用户、设计者、管理员和开放 API 开发者四类受众的中英术语表、消息分类和写作规则，再由这些规则约束全量改写。
- Server 产生的业务失败由 Server 消息目录和 errorKey 作为权威；Web 直接展示已安全本地化的服务端消息，不再长期维护一份按数值 code 复制的业务文案表。
- Web 自身产生的交互、校验、空态和状态文案由 Web locale 目录作为权威。相同 Web 语义只保留一个键，桌面端、移动 H5 和同模块不同页面共同消费。
- Mock、测试夹具和示例数据不计为生产用户文案权威，但必须与正式 errorKey、code、字段名和语言契约一致，不能继续传播 2104/2105 或 1204—1208 的错误语义。
- 测试不得再用完整文案承担业务分支或唯一语义断言；确需验证文案质量的测试应明确标注为文案契约，其余测试优先断言 errorKey、状态与行为。

### 3.5 状态、失败与恢复语义

- 错误消息至少归入：输入可修正、认证失效、权限不足、对象不存在、业务冲突、处理中、可重试基础设施失败、不可重试配置失败、系统故障九类；每类有一致的标题、语气和恢复动作。
- 可重试失败必须说明何时或如何重试；重试无效的配置/权限问题必须指出应修改配置、返回上一步或联系哪类管理员，不能统一写“稍后重试”。
- 加载失败必须有错误态和重试入口，不能渲染成“暂无数据”；提交失败必须有反馈，不能仅保留成功 toast。
- 前端不得在无法识别异常时猜测单一成因。网络中断、超时、HTTP 4xx/5xx、业务错误和客户端异常必须进入不同且可复核的展示语义。
- 批量操作统一提供总数、成功数、失败数、处理中数及可下钻失败明细；失败明细使用安全消息和对象标识，不直出原始异常。

### 3.6 认证与敏感信息边界

- 首方登录继续保持账号不存在、密文非法、解密失败和密码不匹配的防枚举收敛；验证码缺失、失效、内容不匹配和已消费继续按既有安全分组收敛。
- 未认证的 SSO 发起与回调不得暴露 Provider 配置、租户标识、绑定关系、回调白名单或第三方原文。可以向用户说明登录未完成及重新发起路径。
- 账号锁定、停用和身份绑定冲突只有在不扩大账号/租户枚举面的前提下才能展示；无法证明安全时使用统一提示，并把精确原因保留在授权诊断层。
- P61 不降低现有认证、权限、租户隔离、日志脱敏和审计要求。

## 4. 功能范围

- Server：统一响应与异常出口、错误码目录、认证/会话/租户/SSO、表单、流程、通知、存储、任务、IoT、Agent、开放 API 及所有会进入用户响应或受保护管理页面的诊断字段。
- Web：请求归一、类型契约、错误映射、路由与权限反馈、登录/SSO、全局组件、Element Plus locale、所有业务模块的 toast、dialog、表单校验、空态、状态标签、批量结果、移动 H5 与无障碍文本。
- 契约资产：中英语义目录、术语表、errorKey/code 兼容目录、Mock/fixture、必要的接口说明与文案契约测试。
- 探索未完全覆盖但属于原目标的边界：数据库种子或迁移中的真实用户说明、设备/第三方可控 error 字段、文件超限真实响应以及静态扫描无法确认的运行时可达消息。执行层必须在对应阶段关闭这些边界，不能把“未发现”写成“确认不存在”。
- 正面范例应保持其可行动性，不为追求形式统一而把已有清晰提示退化成泛化文案。

## 5. 非目标

- 不改变 P61 之外的业务功能、流程规则、权限模型、数据模型语义或页面信息架构。
- 不在本轮执行破坏性数值错误码重编号，也不创建新的破坏性 API 大版本；未来如需移除歧义数值码，另行立项。
- 不建设完整日志平台、链路追踪平台或通用客服工单系统；只补足本功能所需的安全关联与诊断承载。
- 不验证此前 Owner 已延期的真实 SSO Provider 与五类外部通知渠道成功链；可以用受控对端验证错误净化、分类和恢复提示，不能冒称真实 Provider 验收。
- 不把内部类名、方法名、注释或纯日志文本仅因措辞不自然而纳入用户文案改写；只有实际外显或作为诊断载体时才治理其暴露边界。
- 不扩充 zh-CN/en-US 之外的语言，不新增账号级语言偏好和跨设备同步。

## 6. XL 阶段边界

### 阶段 A：机器语义与安全分层

形成 errorKey、数值 code 兼容目录、msg/诊断边界和事件关联能力；解除文案控制流，消除 2101—2104、2415 与 1204—1208 对 Web 和新调用方的歧义。阶段通过不等于功能完成。

### 阶段 B：全局出口与认证入口

完成统一异常出口、请求归一、通用错误分类、登录/会话/租户/SSO 的人性化与安全收敛，使未认证入口不再泄露内部原因，并保留可追踪诊断。

### 阶段 C：表单与流程主链

完成表单设计、发布、填写、查询、导入导出、流程设计、发布、草稿、审批、批量操作及其前后端语义统一，清除字段名、SQL/JDBC、BPMN 实现词和原始异常的无边界外显。

### 阶段 D：支撑模块与受保护诊断

完成通知、任务、存储、IoT、Agent 和开放 API；特别关闭完整 Java 栈、脚本/编译器原文、MQTT/第三方 HTTP 原文和设备可控 error 字段的暴露，同时保持授权运维可定位。

### 阶段 E：双语与全站文案收敛

让 zh-CN/en-US、语言选择、Server locale、Web locale、Element Plus 与各业务模块共同生效；完成同义异文、裸状态/ID、实现术语、标点和无障碍文本治理。

### 阶段 F：覆盖闭环与整体回归

以更新后的自动盘点、真实接口和可见浏览器覆盖全部可达入口，关闭探索中的未确认项，证明兼容、安全、诊断、双语、失败分类及主要业务主链同时成立后，才可提交功能级 completion receipt。

以上阶段是产品依赖和验收边界，不是执行层 Step；Executor 在不改变本方向的前提下自行制定实施计划。

## 7. 功能级验收标准

1. 公共响应继续兼容 code、msg、data；旧客户端在不认识 errorKey 时仍可安全工作，新客户端可用全局唯一 errorKey 区分同码不同义。
2. 2101—2104 与 2415 的每个现有语义均有独立 errorKey；Web、Mock 与自动化不再仅凭冲突数值分流，新错误没有继续复用已知冲突值。
3. 1204—1208 的服务端码义、Web 兼容兜底、表单本地预检与契约说明一致；ApiResponse 的 msg/message 兼容规则与真实响应一致。
4. P61-S-BPM-16 不再按文案子串决定业务行为；全系统扫描和行为证据未发现其他以用户文案控制业务分支的残留。
5. 对受控注入的 Jackson、Java 字段名、SQL/JDBC、POI、栈、Provider、tenantId、文件路径、脚本编译、MQTT 和第三方原文标记，公共 API 与普通用户 DOM 均为零暴露。
6. 上述失败的完整或等强度诊断能够在受保护载体中通过同一事件引用定位；普通用户看到的事件引用、授权诊断记录和服务端事实一一对应。
7. 首方登录的账号与凭据失败继续满足防枚举收敛；未认证 SSO 失败不披露账号、租户、绑定关系、Provider 配置或第三方原文。
8. 网络中断、超时、401、403、404、409/业务冲突、5xx 和客户端异常得到可区分的安全反馈；加载失败不显示为空数据，失败操作不存在静默吞错。
9. 所有可重试提示包含有效恢复动作；不可重试的配置、权限和数据问题不误导用户重复操作；成功、处理中和失败状态互不混用。
10. 批量导入、批量审批和批量通知均展示总量及各结果计数，并能查看安全的逐项失败信息；汇总与实际结果一致。
11. zh-CN 与 en-US 均可从登录页和登录后应用壳切换并持久化；Web、Server 与 Element Plus 同步切换，刷新、重新登录和错误返回不产生混合语言。
12. 两种语言下，登录、表单、流程、通知、任务、存储、IoT、Agent、系统管理、403/404/500、列表空态和移动 H5 的代表性主链文案自然、术语一致且不溢出或遮挡。
13. Server 业务错误只有一个语义/文案权威，Web 本地交互只有一个 locale 权威；同码异文、同义异文和桌面/移动重复定义均按目录收敛，未经批准的静态用户文案由自动检查阻止。
14. 任务日志、IoT 解析/脚本错误、通知失败原因、SSO 审计与开放 API 回调记录按受众展示分类和脱敏摘要；无权限身份不能读取更深诊断。
15. 文件超限真实响应、数据库种子/迁移用户文本和设备/第三方可控错误三个探索边界均有明确行为结论和证据；不能继续以静态推定代替。
16. 以探索基线的 5 个 ErrorCode 枚举/127 常量、9 个统一异常出口、4 个安全响应出口、Web 354 个消息调用点与 229 个含 CJK 文件为起点生成更新盘点；新增、已治理、保留和排除项可复算，排除项逐条有不可达或非用户文案依据。
17. 既有表单、流程、认证、通知、任务、IoT、Agent、存储和开放 API 的受影响主链保持成立；人性化改写没有改变业务状态、权限、租户隔离或失败处理。
18. Server/Web 受影响测试和正式工程门禁通过，计数来自实际输出；正式可见浏览器证据为 headless=false，并包含 DOM、网络响应、语言、身份、对象和视口信息。

## 8. 行为证据要求

- 每个阶段以追加式回执记录当前基线、实际改动范围、真实请求/响应、事件引用、诊断定位、页面行为和受影响回归；结构与自述只作定位辅助。
- 兼容证据必须同时覆盖旧调用方只读取 code/msg/data、新调用方读取 errorKey、冲突数值缺少 errorKey 的安全兜底，以及 Mock/真实接口的一致性。
- 泄露验证使用可识别的受控标记注入原始异常、字段名、租户号、SQL、栈和第三方响应；分别证明用户层零出现、受保护诊断层可定位、无权身份被拒绝。
- 双语证据必须对同一身份、同一对象和同一错误在 zh-CN/en-US 下成对展示；只展示 locale 文件或键名不构成通过。
- 正式页面验收至少覆盖登录/SSO、表单设计与填写、流程设计与审批/批量、通知记录、任务日志、IoT 脚本与连接、Agent 模型、存储上传、系统列表和错误页；必须来自用户可见、可交互浏览器会话。
- 探索已锁定的 0.1.0 发布事实和 P60 证据不重验；P61 只回归自身影响的既有主链。Owner 延期的真实 Provider 成功链继续按延期/未验证记录。
- completion receipt 必须逐项对照十八条验收标准，并保存可回读的原始证据位置、命令结果、退出码和计数。执行层自验通过不等于规划验收。

## 9. 风险与停止条件

- 若兼容存量调用方只能通过破坏性重编号才能完成消歧，停止该路径并回传消费者、影响面和版本化迁移方案，不得静默破坏 0.1.0。
- 若用户层安全提示与诊断可定位性只能通过公开原始 detail 同时满足，停止并重新设计承载层，不能以可运维为由放宽暴露。
- 若账号/租户/外部身份的精确提示会扩大未认证枚举面，优先保持统一安全提示，并将精确原因限制在授权诊断层。
- 若国际化需要长期保留硬编码与 locale 双权威，或 Server 与 Web 必须各自维护同一业务错误文案，不得进入下一阶段。
- 若静态盘点与真实运行冲突，以真实行为为准，更新盘点和剩余范围；不得删除未解释项来满足覆盖率。
- 发现与 P61 无关的业务缺陷、真实 Provider 成功链或 UI 全面改版需求时，只记录并交回规划，不并入本轮。
