# R3 方向冲突 · 现有产品模型无法构造「有历史快照且当前可编辑」的表单

## 审查要求（planning-execution-prompt §2 R3）

> 使用同时具有历史快照和可编辑当前态的真实表单：记录当前编辑内容及持久化值 → 打开一个内容不同的历史版本 → 关闭预览 → 当前编辑内容与持久化值均保持原值。若现有发布模型不存在"有历史且可编辑当前态"，提交明确的方向冲突。

## 模型事实（逐条来自后端实现，非推测）

1. `FormDefServiceImpl.publish`：仅当 `status == DRAFT` 才允许发布（否则 1100 FORM_ALREADY_PUBLISHED）；发布成功后 `status → PUBLISHED`、`formVersion+1`、写入一条 `sw_form_snapshot`。
2. **发布是一次性状态迁移**：不存在"发布新版本"路径——已发布表单再次 publish 直接抛 1100（本轮真实环境实测：对表单 A 第二次 publish 请求被 1100 拒绝）。
3. 已发布表单在工作台全页灰化（保存/发布禁用、画布 readonly、字段冻结提示条），**无任何编辑入口**；草稿表单从未发布过，`sw_form_snapshot` 必然为空。
4. 因此「`sw_form_snapshot` 有行」与「该表单当前可编辑」在现有状态机下**互斥**，R3 要求的"内容不同的历史版本 + 可编辑当前态"无法在真实数据上构造。

## 已实现且不依赖该场景的只读保护事实（辅助定位，非替代证据）

- 历史预览组件（HistoryVersionsDialog）仅消费两个只读 GET 端点，源码级零回写路径；真实页面已验证打开/关闭预览后当前画布内容不变。

## 结论

**方向级冲突**：R3 的验收场景要求产品提供"已发布表单可继续编辑/发布新版本"的能力（即方向 §4 明确排除的"版本治理/回滚"类语义），超出方向授权范围。需规划裁决：要么修订 R3 场景（在现模型下等价改写，例如以"只读已发布表单的当前冻结内容与历史对照"为对象），要么立项"表单版本可编辑演进"作为前置功能。执行层按提示不自行造近似场景。
