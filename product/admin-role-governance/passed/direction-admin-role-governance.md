## 1. 目标（一句话）

建立“不可变的内置 `superadmin` + 初始化 seed、默认具备当前管理权限且后续可配置的普通 `admin`”双角色基线，并让普通管理员能够被分配给用户、配置菜单/按钮权限、端到端访问 job/storage，关闭 P24 / I49。

## 2. 产品语义

### 2.1 `superadmin`

- 继续以启用角色 `code=superadmin` 作为系统超管身份，不改成 `userId==1` 或权限通配串判断。
- 角色记录为内置角色，后端必须阻止任何会改变其身份或有效性的操作，包括改名、改 code、停用、删除、修改数据范围以及修改菜单/按钮授权。
- 前端角色管理同步隐藏或禁用上述操作，但前端限制不能代替后端强制保护。
- 现有 seed 用户及其 `superadmin` 绑定保持不变，不迁移、不降权。

### 2.2 `admin`

- 初始化 seed 一个普通管理员角色：名称“管理员”、稳定 code=`admin`、启用、非内置角色、默认数据范围为 ALL。
- `admin` 不触发超管旁路；它必须与普通角色一样通过显式用户角色、角色菜单和按钮 permission 获权。
- 初始权限覆盖迁移时系统已有的管理菜单与按钮权限，并明确包含 job/storage；未来新增功能不因 code=`admin` 自动旁路或自动获权。
- `admin` 按普通角色规则可配置：允许修改名称、状态、数据范围、菜单与按钮授权；code 的编辑规则沿用系统对普通角色的统一约束。
- 不新增默认用户、不生成默认密码、不自动改绑任何现有用户。

### 2.3 配置闭环

- 超管必须能够在现有系统管理界面为普通角色读取、写入和回填菜单/按钮权限。
- 系统必须提供将已有用户绑定到 `admin` 或其他普通角色的最小可用入口，并能正确读取和回填；不要求同时补齐部门、岗位等 P1 其余关联/筛选缺口。
- 菜单可见性与接口 authorization 必须分别闭合：看到 job/storage 菜单不代表自动拥有接口权限。

## 3. 非目标

- 不创建第二个默认账号，不设置或展示任何默认密码。
- 不迁移现有 seed 用户或生产环境用户的角色绑定。
- 不把 `admin` 做成第二个超管，不为其增加 code 旁路、`*:*:*` 通配或不可撤销权限。
- 不完成 P1 中部门筛选、人员查询、岗位关联、角色关联等无关缺口。
- 不重构完整 RBAC、租户体系、数据权限引擎或菜单路由架构。
- 不改变 job/storage 业务能力、页面功能或数据模型；只补访问控制与默认授权闭环。
- 不自动把未来新增菜单授权给 `admin`；后续功能按迁移或人工配置显式授权。

## 4. 影响范围（模块级）

### 后端

- System 角色服务与接口：强制保护 `superadmin`；支持普通角色菜单/按钮权限读取、写入和回填。
- System 用户角色关系：补齐已有用户与普通角色绑定的最小读写闭环。
- Security 权限装配：保持 `superadmin` code 旁路；验证普通角色只从显式按钮 permission 获权。
- Job / Storage 接口：建立明确的方法级 permission 边界，保证授权角色允许、未授权角色拒绝。
- Root Flyway：新增 H2/PostgreSQL 同语义迁移，seed `admin`、当前默认菜单/按钮授权及 job/storage 所需权限记录；兼容全新库与 V30 升级库。
- Bootstrap 测试：扩展永久 Flyway 全链验证及角色、菜单、权限关系断言。

### 前端

- 角色管理：对 `superadmin` 展示只读保护；为普通角色提供菜单/按钮权限配置与回填。
- 用户管理：提供已有用户绑定普通角色的最小入口与回填。
- Mock/夹具：纠正仍将 `admin` 当作超管的陈旧语义，保持与生产双角色模型一致。
- job/storage 页面本体原则上不改；若权限控制仅需既有路由/菜单机制生效，应保持零业务改动。

### 规划与知识状态

- 完成后关闭 I49、核销 P24。
- I36/P1 只记录本轮已闭合的“角色菜单/按钮权限配置 + 最小用户角色绑定”子集，不得把 P1 其余缺口误标完成。

## 5. 风险方向

1. **历史升级冲突**：生产库可能已有自建 `code=admin` 或迁移拟用 ID。迁移必须幂等或显式安全失败，不得覆盖、夺取或静默改写已有角色。
2. **越权风险**：`admin` 默认权限是显式授权，不是旁路；权限读取、保存和接口校验均须服从租户隔离，不能跨租户配置角色。
3. **仅菜单可见的半闭环**：V29 页面/目录记录不能代替按钮 permission 与后端方法级鉴权，验收必须覆盖允许和拒绝两条路径。
4. **超管锁死风险**：保护范围只针对角色治理操作，不能误伤超管用户自身合法的账号安全操作；同时任何 API 绕过前端都不得改变 `superadmin` 角色。
5. **双端契约漂移**：前端 `admin/superAdmin` mock 旧语义必须清除，角色字段、权限树与回填契约须和后端一致。
6. **范围膨胀**：本轮只收敛角色治理最小闭环，不借机完成 P1 全部组织关系功能。

## 6. 验收标准

1. 全新数据库与从 V30 升级的数据库均能完成迁移和 validate；H2/PostgreSQL 迁移语义一致，Flyway 链计数按新增迁移正确增加。
2. `superadmin` 保持启用 code 旁路，且通过后端 API 无法被改名、改 code、停用、删除、修改数据范围或菜单/按钮权限；前端无可执行入口。
3. 数据库存在启用的普通 `admin` 角色，名称“管理员”、code=`admin`、非内置、数据范围 ALL；它不触发超管旁路。
4. 不新增默认用户、不改变任何既有用户角色绑定；已有用户可由超管通过受支持入口绑定/解绑普通角色，并能正确回填。
5. 普通角色菜单/按钮权限可读取、保存、清空和回填，租户边界正确；`superadmin` 的权限关系不可被该入口修改。
6. `admin` 初始获得迁移时全部既有管理菜单/按钮的显式授权，至少完整包含 job/storage 菜单、子页面和接口 permission；管理员可在配置界面撤销或重新授予这些权限。
7. 绑定 `admin` 的用户能够看到并使用 job/storage；移除相应权限后菜单不可见或入口不可达，相关接口返回拒绝；未授权普通角色始终不能调用相关接口。
8. job/storage 的方法级 permission 与数据库按钮权限记录一致，不依赖仅登录即可访问；菜单可见与接口可调用分别有自动化证据。
9. 前端 mock、契约和测试不再把普通 `admin` 标记为超管；真正 `superadmin` 的界面保护与后端语义一致。
10. 后端模块测试、项目级全量测试以及前端 typecheck/lint/test/build 全部通过，测试数量不低于当前基线（后端 543；前端 66 spec / 576 tests）；所有编译测试遵守 2G 上限和前后端互斥。
11. 功能清单、`knowledge/current-status.md`、功能追踪、known-issues 与需求池完成全量同步：I49/P24 关闭，P1/I36 仅更新本轮子集，清单计数有证据且无无关状态漂移。
