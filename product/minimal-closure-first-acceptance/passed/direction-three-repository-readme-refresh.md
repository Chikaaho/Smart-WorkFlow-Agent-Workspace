# 三仓 README 重构与现状同步方向

> 本会话角色：规划（Planner）
> 方向状态：READY
> 日期：2026-08-29
> 性质：上一轮最小闭环验收完成后的独立文档同步任务
> 当前唯一任务：把三仓 README 重构为准确、可长期维护的项目入口文档

## 一、背景

当前工作区根仓、后端仓和前端仓的 README 存在多处内容落后，并呈现为持续追加的变更记录，不能让首次进入项目的人快速理解项目定位、仓库关系、运行方式、工程约束和权威文档入口。

本任务不撤销 `minimal-closure-first-acceptance` 的 `COMPLETED（已确认）`，也不新增正式功能；它只负责三份 README 的结构重构与当前事实同步。

## 二、目标

将以下三份文件分别改造成其所在仓库真正的 README：

1. 工作区根：`README.md`；
2. 后端仓：`Smart-WorkFlow/README.md`；
3. 前端仓：`Smart-WorkFlow-Web/README.md`。

完成后，读者应能从任一仓库 README 快速知道“这是什么、包含什么、如何开始、去哪里查权威细节”，而不是先阅读按日期或功能堆积的变更记录。

## 三、三份 README 的职责边界

### 1. 工作区根 README

作为三仓统一入口，至少清晰说明：

- Smart-WorkFlow 产品定位与当前可用的核心业务闭环；
- 工作区根、后端仓、前端仓以及 `product/`、`knowledge/`、`memory/` 的职责关系；
- 三种会话角色和唯一治理入口只做简短导航，规则正文一律链接 `system.md`，不得在 README 复制或重定义治理条款；
- 新参与者应按什么顺序进入后端、前端或规划文档；
- 当前正式状态与测试基线只保留一段精简快照，并明确权威来源，避免 README 成为第二份状态库。

### 2. 后端 README

作为后端开发入口，至少清晰说明：

- 后端职责、技术栈、模块层级与依赖方向；
- 主要业务模块及当前边界；
- 环境要求、数据库模式、配置入口和安全的本地启动方式；
- 当前真实可用的构建、测试和迁移校验命令，包括 Maven 2G 内存约束；
- H2/PostgreSQL 双方言迁移规则和当前迁移终点；
- 工程宪法、API/架构/知识文档的权威入口；
- 不在 README 维护逐功能变更流水账。

### 3. 前端 README

作为前端开发入口，至少清晰说明：

- 前端职责、技术栈、目录分层和与后端 API 的关系；
- 环境要求、依赖安装、真实后端模式与 Mock 模式的启动方式；
- 当前真实可用的 typecheck、lint、test、build 命令，包括 Node 2G 内存约束；
- 鉴权、菜单、路由和模块边界的关键入口；
- 工程宪法及进一步开发文档的权威链接；
- 不在 README 维护逐功能变更流水账。

## 四、内容重构原则

三份 README 必须共同遵守：

- 结论优先，面向首次进入项目的开发者或协作者；
- 采用稳定栏目组织内容，不以日期、需求编号、提交批次或“本轮新增”作为主体结构；
- 删除已经过期、互相冲突、重复堆叠或仅有历史价值的当前性描述；历史变化依赖 Git 历史或链接现有历史文档，不继续占据 README 主体；
- 动态状态只保留当前精简快照和权威路径，不复制完整功能清单、known issues、决策历史或会话交接；
- 命令、路径、端口、模块名、环境变量和文档链接必须与当前仓库事实一致，不得沿用记忆中的旧写法；
- 三仓对同一事实使用一致口径，避免根 README、后端 README、前端 README 各自维护不同版本；
- README 只承担导航和上手说明，不重新定义 `system.md`、角色文件或两端工程宪法中的规则。

## 六、非目标与禁止事项

- 不修改业务代码、测试代码、迁移、依赖、构建配置或工程宪法；
- 不修改 `system.md`、`roles/` 或治理实现；
- 不新增功能、不修改功能数、清单计数、P 编号或功能终态；
- 不把 README 扩写为完整架构设计、API 手册、开发日志、版本发布记录或知识库副本；
- 不发布、不提交、不推送 Git；如后续需要发布，必须由 Owner 另行授权；
- 除三份 README 和本任务回执外，不得顺手修改其他文件。若发现权威文档本身冲突，只在回执中报告，不自行扩大同步范围。

## 七、执行要求

执行角色应先读取当前三份 README，再以当前仓库结构、实际构建配置、工程宪法和权威知识状态核对其中每个可变事实，然后自行设计重构结构。

最终交付必须包含：

1. 三份 README 修改前问题矩阵：过期项、冲突项、变更记录式内容和缺失的入口信息；
2. 三份 README 各自的目标读者、职责边界和最终栏目；
3. 实际修改文件清单，必须只有三份 README；
4. 对命令、路径、端口、模块名、环境模式、文档链接和当前基线的逐项核对结果；
5. 相对链接有效性检查，以及 `947`、`1057`、`V43`、旧测试计数、旧启动命令和日期式变更标题的残留检查；
6. 明确证明三份 README 主体已不再是变更记录，且没有复制治理规则或建立第二份状态库；
7. 追加回执到 `product/minimal-closure-first-acceptance/receipts/`，回执物理末行保留唯一合法 `SWF_TERMINAL` 并通过公共 Validator。

## 八、验收标准

只有同时满足以下条件才可通过：

- 三份 README 均能独立完成其仓库的“项目说明 + 快速开始 + 权威导航”职责；
- 三仓定位、仓库关系、命令、路径、环境和正式基线一致且无当前事实错误；
- 变更日志式主体、过期信息和重复状态正文已清理；
- 所有重要相对链接真实可达；
- 未修改三份 README 之外的项目文件，未越权发布或改变正式状态；
- 回执提供实际文件内容与检查输出，而不是仅声明“已更新”。

证据不足时保持 `VERIFYING`；发现 README 无法在限定范围内与权威事实对齐时如实 `BLOCKED`，不得自行修改权威规则或扩大文件范围。
