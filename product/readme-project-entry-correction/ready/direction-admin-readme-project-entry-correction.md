# 三仓项目入口 README 修订方向

> 下发角色：规划（Planner）
> 指定角色：管理员（Admin）
> 方向状态：READY
> 日期：2026-08-30
> 性质：文档治理修订，不新增正式功能

## 一、目标

将三份 README 统一修订为面向项目使用者和开发者的稳定入口文档，重点回答：

- 项目解决什么问题；
- 当前包含哪些主要能力；
- 三个仓库分别负责什么；
- 如何安装、启动和进行日常开发；
- 架构、治理和完整开发说明应从哪里继续阅读。

README 的主体以项目介绍、架构概览、快速开始和文档导航组织。运行环境差异、自动化代理约束、验收状态和动态工程数据不进入 README 正文。

## 二、权威修订口径

Owner 于 2026-08-30 明确：

1. 编译内存上限及前后端编译互斥来自 Owner 当前机器的资源条件，不是项目本身的通用使用要求；
2. README 是项目说明和上手入口，不是验收清单、执行回执、测试基线看板或变更记录。

本口径覆盖上一轮 `direction-three-repository-readme-refresh.md` 中要求把 2G 资源限制、编译互斥、功能计数、测试计数和迁移终点写入 README 的部分。历史方向与回执保留，不得覆盖或改写。

## 三、允许修改范围

仅允许修改：

1. 根仓 `README.md`；
2. 后端仓 `Smart-WorkFlow-Server/README.md`；
3. 前端仓 `Smart-WorkFlow-Web/README.md`；
4. 本任务追加回执：`product/readme-project-entry-correction/receipts/receipt-admin-readme-project-entry-correction-20260830.md`。

不得修改 `system.md`、`roles/`、工程宪法、knowledge、memory、todo、业务代码、测试、构建配置、依赖、迁移、Git 状态或历史回执。

## 四、内容职责

### 根仓 README

- 产品定位与典型使用场景；
- 根仓、后端仓、前端仓的关系；
- 主要能力的稳定概览，不列功能完成数量、P/I 编号或当前验收结论；
- 最短的仓库进入路径和文档导航；
- `system.md` 只作为治理入口链接，不复制角色或执行规则正文。

### 后端 README

- 后端定位、主要技术栈、模块分层和核心业务域；
- 环境依赖、配置入口、数据库选择及普通启动方式；
- 开发者常用 Maven 命令可简洁保留，但使用项目通用写法，不附带本机内存上限或跨仓互斥操作；
- 链接工程宪法、架构说明和 API 入口，不维护当前测试数、迁移计数或发布验收状态。

### 前端 README

- 前端定位、主要技术栈、目录分层和后端 API/Mock 两种开发模式；
- 环境依赖、安装与普通启动方式；
- typecheck、lint、test、build 可作为简短开发命令参考，每条命令单独置于 Markdown 代码块中；
- 不附加 `NODE_OPTIONS`、前后端编译互斥、当前 spec/test 数、全绿声明或提交前验收门；
- 链接工程宪法和进一步开发文档。

## 五、成稿原则

- 从正向的项目入口结构重新组织三份 README，不按原段落逐句修补；
- 标题、开场、栏目和链接描述只呈现项目当前形态，不解释本次纠偏过程；
- 可使用少量列表帮助导航，但不能形成逐项验收表、状态清单或按日期堆叠的更新记录；
- 命令必须使用 fenced code block，一行一条，不能挤成一段正文；
- 不使用 `NODE\_OPTIONS`、连续星号等 Markdown 转义或加粗残片；
- 稳定事实才写正文；动态状态统一链接权威位置，不复制快照；
- 三份 README 不复制治理规则，也不把个人机器环境包装成项目硬约束。

## 六、验收标准

1. 三份 README 分别具备清晰的项目说明、核心能力/结构、快速开始和进一步文档入口。
2. README 正文不包含 `NODE_OPTIONS`、`MAVEN_OPTS`、2G 内存上限、前后端编译互斥或 `knowledge/shared-constraints.md §9` 的机器执行要求。
3. README 正文不包含正式功能数、清单计数、spec/test 数、迁移计数、PASSED/COMPLETED/全绿等动态验收快照。
4. 不存在日期式变更主体、“本轮完成”、任务编号流水账或提交检查门禁。
5. 所有命令块渲染正常，每条命令独立成行；不存在 `NODE\_OPTIONS`、`****`、一行粘连多条命令等格式错误。
6. 三仓定位、目录名称、启动入口和相对链接与当前仓库事实一致，重要相对链接检查为零缺失。
7. README 中不出现“已删除某约束”“不再作为清单”等面向本次会话的纠偏说明；这些差异只写入回执。
8. 实际修改范围严格为三份 README 与一份新回执，不运行编译、测试、构建、迁移、服务或发布命令，不提交、不推送。

## 七、回执要求

管理员回执至少提供：

- 三份 README 的最终栏目与目标读者；
- 实际修改文件清单；
- 对验收标准 1～8 的逐项结果；
- 资源限制、动态基线、变更记录式内容和 Markdown 格式残片的全文零残留检查；
- 三份 README 的相对链接检查结果；
- `git diff --check` 结果及未修改其他文件、未运行工程命令、未提交推送的范围说明。

管理员任务不使用 Executor 的 `SWF_TERMINAL`；回执以普通 Markdown 结论结束。
