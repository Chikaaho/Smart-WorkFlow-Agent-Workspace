## 1. 目标（一句话）

补齐人员与部门、岗位、普通角色的可配置关联及组合查询闭环，使现有用户管理从“基础 CRUD + 部分关系”升级为可真实支撑组织管理和权限分配的日常入口，并收敛 I32、I34、I35 及 I36 尚未闭合的用户绑定子集。

## 2. 产品语义

### 2.1 人员组织关联

- 一个用户必须归属一个有效部门；创建、编辑、详情回填和列表展示使用同一部门语义，不再要求管理员手工输入部门 ID。
- 一个用户可关联零个或多个岗位；岗位关系必须可保存、替换、清空和回填，停用或已删除岗位不得被新绑定。
- 一个用户可关联零个或多个普通角色；角色关系必须可保存、替换、清空和回填，停用或已删除角色不得被新绑定。
- 人员主记录与岗位、角色关系在同一次业务操作中保持一致：任一必要写入失败时不得留下半完成关系。

### 2.2 超管授权边界

- `superadmin` 仍按 D93-D97 的不可变内置角色语义处理；人员管理入口不得让普通管理员借角色绑定获得超管身份。
- 非 `superadmin` 操作者不得查看到可分配的 `superadmin` 选项，也不得通过构造请求绑定或解绑该角色；前端隐藏仅作体验，后端必须强制拒绝。
- 本轮不改变现有 seed 用户与 `superadmin` 的既有绑定，也不设计新的默认超管账号。

### 2.3 人员组合查询

- 用户列表必须支持现有关键字与状态筛选，并补齐部门、岗位、角色筛选；筛选条件可组合，返回结果和总数必须一致。
- 关键字统一覆盖人员日常可识别字段，至少包括用户名和真实姓名；可复用现有契约支持的手机或邮箱，但不得以模糊匹配扩大到敏感字段。
- 部门筛选采用“所选部门及其下级部门”语义，适配组织树使用习惯；岗位和角色按明确绑定关系筛选。
- 无筛选条件时保持现有分页行为；空条件、非法 ID、停用关联项和无匹配结果均返回稳定、可解释的结果，不静默退化为全量查询。
- 所有查询继续受租户隔离、逻辑删除和已落地的数据权限约束；新增关联查询不得绕过现有数据权限链。

## 3. 非目标

- 不实现部门拖拽排序或部门条件查询（M01-F01-02、M01-F01-04 / I31）。
- 不新增岗位、角色、部门本身的 CRUD 能力，也不重构其既有页面。
- 不改角色菜单/按钮权限配置、普通 `admin` 初始授权或 job/storage 鉴权；这些已由 admin-role-governance 完成。
- 不实现用户组、批量导入导出、SSO、验证码、密码策略或登录失败锁定。
- 不改变五档数据权限定义、不纳管 I46 的手写 SQL 通道，不借机重构 Security 或租户体系。
- 不把“人员角色绑定”扩展成授权审批流、临时授权、有效期授权或跨租户授权。

## 4. 影响范围（模块级）

### 后端

- System 用户领域：扩展人员创建、编辑、详情与分页查询契约，补齐部门、岗位、角色关系的读取和写入闭环。
- System 岗位与角色关系：复用现有角色关系，新增或补齐用户岗位关系及必要查询；关系写入须具备事务一致性与租户边界。
- System 查询层：支持关键字、状态、部门树、岗位、角色的组合筛选，并与分页总数保持一致。
- Security：沿用现有权限装配与 `superadmin` code 语义；仅补人员角色绑定入口所必需的服务端越权防护。
- Root Flyway：如现状确实缺少用户岗位关系表或必要索引，新增 H2/PostgreSQL 同语义迁移；当前最高版本 V31，执行层须先核实现场占号后选择版本。

### 前端

- 用户管理：部门树选择、岗位多选、普通角色多选、详情回填及组合筛选；移除手工输入关联 ID 的交互。
- 契约与 API：保持字段含义清晰，区分部门单值与岗位/角色多值；不得在展示名和持久化 ID 之间混用。
- Mock/夹具：与真实契约、状态语义和 `superadmin` 分配边界一致。

### 规划与知识状态

- 完成后关闭 I32、I34、I35；I36 仅在确认其剩余“用户与角色绑定管理入口”全部闭合后关闭，不得覆盖其他未完成语义。
- 按功能清单真实完成度更新 M01-F02-01、M01-F02-04、M01-F03-01、M02-F01-01；只有清单描述全部满足的行才能升为 ✅。

## 5. 风险方向

1. **权限提升**：用户角色写入是直接授权面，必须防止普通管理员绑定 `superadmin`、跨租户角色或停用角色。
2. **关系半写入**：用户主记录、岗位关系、角色关系必须在事务内一致更新，创建失败、编辑失败和清空关系都要有明确语义。
3. **数据权限绕过**：多表关联筛选容易绕过或重复叠加现有数据权限、租户和逻辑删除条件，必须验证结果集合而非只验证 SQL 被调用。
4. **部门树语义**：下级部门递归须复用已有部门层级能力并防环；不得为查询便利引入与现有部门模型冲突的第二套层级来源。
5. **查询性能**：岗位/角色多对多筛选可能造成分页重复行或总数错误，应验证去重、索引和组合条件下的稳定性。
6. **契约兼容**：现有用户 CRUD 调用方、登录装配和 D97 最小用户角色绑定不能因 DTO 扩展而回归。

## 6. 验收标准

1. 用户创建、编辑、详情回填均可使用部门选择、岗位多选和普通角色多选；保存、替换、清空关系后再次读取结果准确。
2. 用户主记录与岗位/角色关系具有事务一致性；构造任一关系写入失败场景时，不产生部分更新或孤儿关系。
3. 普通管理员无法从页面或直接 API 将任意用户绑定/解绑 `superadmin`；真正 `superadmin` 的既有绑定和 D93-D97 语义无回归。
4. 列表关键字、状态、部门（含下级）、岗位、角色筛选分别有效且可组合；无条件分页、无结果、非法筛选值的响应稳定，总数与结果集一致且无重复用户。
5. 关联读取与查询遵守租户隔离、逻辑删除和现有数据权限；至少以两个租户、不同部门数据范围和已删除/停用关联项证明不会越界或误回填。
6. 如新增用户岗位迁移，H2/PostgreSQL 表、约束和索引语义一致；全新库与 V31 升级库均 migrate + validate 成功，迁移冲突不得静默覆盖既有数据。
7. 前端不再要求手工输入部门 ID；选择器展示名称、提交 ID，岗位/角色的禁用与不可分配状态表达正确，Mock 与真实契约一致。
8. 现有登录、用户 CRUD、角色治理、菜单按钮授权和数据权限回归均通过；后端项目级全量测试和前端 typecheck/lint/test/build 全绿，数量不低于当前基线（后端 551；前端 66 spec / 576 tests）。
9. 所有编译测试遵守 2G 内存上限与前后端互斥；回执提供实际进程检查、命令、退出码和测试计数证据。
10. 完成 §3.3 第10项知识库全量同步：功能清单变更明细、I32/I34/I35/I36 状态、current-status、功能追踪、known-issues、session-handoff 与需求池均按全文当前状态核对；无关清单行零漂移。
