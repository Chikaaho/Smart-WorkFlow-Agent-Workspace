# 工作区根治理宪法与定义一致性审计方向

> 下发角色：规划（Planner）
> 指定执行角色：管理员（Admin）
> 方向状态：READY
> 日期：2026-08-29
> 性质：根工作区治理只读审计，不是业务功能，不授权修复或发布

## 一、目标

对 `/usr/local/projects/Smart-WorkFlow` 根工作区的治理宪法、角色定义、Harness 入口、终态契约和相关定义进行一次完整一致性审计，识别：

- 同一事项由多处重复定义且语义冲突；
- 已被新规则替代但仍以当前口径存在的旧规则；
- 文件职责越界、权威入口不唯一或引用链断裂；
- 角色权限、生命周期、终态和目录规则之间无法同时满足的矛盾；
- 根 README 或入口文件复制治理正文、形成第二权威源；
- 章节号、路径、文件名、状态值、命令约束和 Validator 引用已经落后；
- Claude/Codex/Agent 等不同 Harness 入口对同一工作区给出不同治理行为。

本轮只回答“根工作区治理是否自洽、当前、唯一且可执行”。发现问题后形成精确审计报告，由 Owner 决定是否另行授权修复。

## 二、角色与权限门禁

本任务必须在用户明确声明为 `管理员` 的会话中执行。管理员开始前必须完整读取：

1. `system.md`；
2. `roles/admin.md`；
3. 根目录当前 Harness 入口及 Governance Implementation 定义。

不得由规划或执行角色代做；不得因本方向来自规划角色而扩大管理员权限。若本方向与 `system.md` / `roles/admin.md` 冲突，以 Owner 最新明确指令及唯一宪法入口为准，并在报告中列明冲突。

## 三、审计范围

### A. 唯一宪法与角色定义

- `system.md`；
- `roles/planner.md`；
- `roles/executor.md`；
- `roles/admin.md`。

重点检查：角色声明门禁、三角色读写边界、阶段一至三职责、探索通道、product 生命周期、重复失败收敛、状态机、终态同步、memory/knowledge 分层和 Owner 最终裁量是否相互一致。

### B. 根 Harness 入口

- 根 `AGENTS.md`；
- 根 `CLAUDE.md`；
- 根 README 中的治理导航；
- 根目录 `.claude/`、`.codex/` 中负责入口、Hook、权限或行为路由的非业务配置与说明。

重点检查：入口文件是否只负责加载和路由 `system.md`，是否复制、改写或另行定义角色、权限、状态、命令、确认门禁；不同 Harness 是否得到同一治理结果。

### C. 终态机器契约与 Governance Implementation

- `.codex/governance/terminal-contract.json`；
- `.codex/governance/validate-terminal.sh`；
- `.claude/hooks/`、`.codex/hooks/` 中与终态校验相关的实现及配置；
- 角色文档、模板、Hook 对上述契约和 Validator 的所有引用。

重点检查：合法角色、合法 state、schema、必填字段、物理末行规则、回执状态与功能状态解耦、Validator 与 Hook 诊断是否一致；禁止从旧角色文档或 Hook 内另造合法终态。

### D. 当前性与引用完整性

检查根治理文件中的所有关键引用是否仍真实存在并指向正确权威位置，包括：

- 章节号和迁移映射；
- `product/ready|receipts|passed` 生命周期路径；
- `search_task/` / `search_fallback/` 通道；
- `knowledge/current-status.md` 与 memory 摘要关系；
- 两端工程宪法路径；
- Maven/Node 2G 与前后端编译互斥约束；
- 已废弃的 Step 0、`done/`、旧终态、旧角色名、旧确认流程或过期目录引用。

只允许读取为核对根治理引用所必需的非业务文档与配置；不得读取业务源码或业务测试源码。

## 四、必须回答的审计问题

1. 当前是否只有 `system.md` 一个行为宪法入口？哪些文件仍在重复定义治理规则？
2. `system.md` 与三个角色定义之间是否存在权限、职责、写入路径或停止条件冲突？
3. Planner、Executor、Admin 的读取/写入清单是否分别闭合，是否存在某任务被要求完成但没有任何角色有权完成的“权限空洞”？
4. 三阶段工作流、功能状态、product 目录流转和终态同步协议是否能形成无矛盾状态机？
5. Executor terminal、阶段三 terminal 和功能状态是否在契约、Validator、Hook、角色文档中保持一致？
6. 重复失败收敛规则在 system/planner/executor 中是否采用相同触发次数、提示等级和责任边界？
7. memory/knowledge/search/product 的读写边界和权威层级是否在所有入口一致？
8. AGENTS、CLAUDE、Codex/Claude Hook 是否存在独立规则、过期规则或不同 Harness 行为分叉？
9. 根 README 是否只做导航，是否仍含会漂移的治理正文或旧状态口径？
10. 是否存在失效链接、错误章节号、错误目录、废弃状态、旧命令或已被替代的当前性描述？

## 五、问题分级与报告格式

每个发现必须使用唯一编号 `GOV-AUDIT-01` 起，并包含：

| 字段 | 要求 |
|---|---|
| 等级 | `BLOCKER` / `HIGH` / `MEDIUM` / `LOW` |
| 位置 | 文件、章节或行号 |
| 冲突双方 | 两个或多个实际文本/契约位置 |
| 当前事实 | 必要短摘录，不复制大段全文 |
| 权威裁决依据 | Owner 指令、`system.md`、`roles/admin.md` 或机器契约 |
| 影响 | 会导致什么错误角色行为、状态错误或 Harness 分叉 |
| 建议方向 | 应由谁、在哪些文件、按什么原则修复；不得直接实施 |
| 是否阻断 | 是否阻断当前治理任务或后续业务执行 |

报告同时提供四张汇总表：

1. 文件职责与唯一权威矩阵；
2. 三角色读写权限闭合矩阵；
3. 状态机与终态契约对照矩阵；
4. 失效/过期引用清单。

如果未发现问题，也必须列出实际检查文件、引用数量、契约分支和零问题证据，不能只写“均一致”。

- 不创建业务需求、不改变功能状态、功能数、清单、P 编号或正式测试基线；

- 不把发现的问题直接改掉，不把“建议修复”写成已完成。

## 八、验收边界

本任务的通过表示“审计范围完整、问题证据准确、分级和建议可执行”，不表示“所有治理问题已经修复”。

- **PASSED**：范围完整，所有问题均可追溯，四张矩阵齐全，未越权修改；
- **VERIFYING**：范围或证据不完整，需要补充只读核验；
- **BLOCKED**：角色权限、文件不可读或权威规则互相矛盾到无法完成审计，必须列出唯一阻塞点；
- 发现 `BLOCKER/HIGH` 问题不自动导致审计失败，只要问题被准确识别；但在 Owner 授权修复前不得声称治理已经一致。
