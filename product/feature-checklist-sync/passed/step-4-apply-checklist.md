将 `Smart-WorkFlow/功能清单.md` 中全部 89 条明细的「状态」列，按 `product/feature-checklist-sync/passed/step-3-synthesis.md` §4/§5 给出的精确目标值，逐条设置为目标状态（⬜/🟦/✅）。这是纯机械的字符串替换任务，**不需要、也不允许**你自行判断任何一条的状态——目标值已经确定，你只负责把文档中的标记改成给定值。

推荐模型：deepseek-v4-flash
选择理由：纯机械字符串替换，目标值已完全给定，无判断空间

本 Step 不涉及任何判断、设计或架构决策，是"读取目标表 → 定位文档中每一行 → 替换状态列字符"的纯执行工作，Flash 完全胜任。

## 10. 关键实现约束

- 89 条明细必须逐一按映射表设置，不允许合并批量替换导致误改（尤其注意 M07/M08/M09 内部各条明细也要逐条确认修改到位，不能因为"统一设为⬜"而跳过检查）
- 若发现文档中某 ID 对应的行本来就已经是目标状态，无需改动，但仍需在回执中确认核对过（避免因为"看起来一致就没检查"漏检）
- 若发现映射表中某个 ID 在 `功能清单.md` 中找不到对应行（ID 不匹配/格式差异），停止对该行的处理，在回执「9. 遇到的问题」中如实报告，不要猜测或跳过

## 11. 边界情况

- 若 `功能清单.md` 的状态列使用的符号与本方案假设的 ⬜/🟦/✅ 不完全一致（例如全角/半角差异、额外空格），以文档原有的符号写法为准做替换，保持格式一致性，不要引入新的符号变体
- 若发现同一 ID 在文档中出现了不止一次（重复行），在回执中报告这个异常，两处都按目标值设置，但需说明发现了重复

## 12. 风险和回滚方案

- 本 Step 只修改状态列文字，风险极低。若执行中发现改动范围超出预期（意外改动了其他列），应立即停止，在回执中如实报告已发生的范围外改动，供规划层评估是否需要通过 git diff 回滚
- 回滚方式：`git checkout -- Smart-WorkFlow/功能清单.md`（若发现误改且尚未提交），执行代理本身不得自行执行此回滚命令，仅在回执中提出，由规划层决定是否需要该操作
