## Context

代码检查发现两类系统性违规：

1. **Controller 返回值大量使用 `Map`**：全仓 21 个 Controller、57 个接口方法返回 `Map` / `List<Map>` / `PageResult<Map>`（43 个顶层 Map、12 个 List<Map>、2 个 PageResult<Map>）。`BpmMyInstanceController` 的 `myInstanceCount`、`myInstanceDetail`、`instanceRelation` 是典型；同文件还有 22 处全限定类名。
2. **全限定类名（FQCN）普遍存在**：main 代码约 166 个文件、790+ 行，测试代码 151 个文件、1250 行，违反工程宪法 §9.1“import + 短类名，仅同名冲突用 FQCN”。

目标：在不改变 HTTP JSON 契约、不改变业务行为的前提下，把 Controller/Service 对外返回的 Map 全部替换为 DTO，并把不满足同名冲突例外的 FQCN 全部改为 import。前端请求层只解包 `R.data`，不做运行时 schema 校验，因此**字段名不变则前端零改动**。

## 判级与交付口径

- 按模块拆成内聚批次，单批为 M 级重构；HTTP JSON 契约保持不变。若执行中发现必须改前端契约，单批升级并先报告。
- 先做 FQCN 全量清理（机械、行为中性），再做 DTO 分批改造；每批通过编译/测试后再进入下一批。
- **默认不 commit、不 push**，所有改动留在工作树；最终按批次给出可直接使用的提交拆分建议。你明确要求后再提交推送。

## Phase 1：FQCN 全后端清理

覆盖 `Smart-WorkFlow-aPaaS-server` 的生产、测试及仓库内维护的验证辅助源码，排除 `target/`。

1. 写一个 Java 源码词法扫描/替换脚本：跳过字符串、字符字面量、注释；识别 `包.类`、`包.外部类.内部类`、泛型、`new`、静态调用、方法引用、`.class`、注解参数中的真实类型引用。
2. 按文件建立符号表（package、已有 import、通配 import、简单名使用），逐处替换：
   - 同包/`java.lang`：直接去前缀；
   - 已有同 FQCN import：直接用短名；
   - 无冲突：补 import，再用短名；
   - **仅当同一类中确实同时使用不同包的同名类型**：保留其中一个为 FQCN，并登记“文件 + 两个完整类型名 + 引用位置”。
3. 维护 import 分组（`com.sw` / 第三方 / `java`），去重、排序，尽量不重排既有 import 造成无关 diff。
4. 应用后依次跑 `mvn -q -DskipTests compile`、`mvn -q test-compile`，人工修复脚本无法正确判定的冲突。
5. 残余扫描：代码中的 FQCN 应为零；保留例外逐条列出并证明是真实同名冲突。

## Phase 2：Controller/Service 返回 DTO（按模块分批）

### 通用规则

- DTO 放在模块既有 `dto` 包（如 `com.sw.ck.bpm.process.dto`、`com.sw.ck.form.dto`），命名 `XxxDTO`，Lombok `@Data`（需要时 `@Builder`），与 `MyInstanceItemDTO`、`ApprovalHistoryItemDTO` 风格一致。
- Service 接口/实现同步改返回类型，Controller 只做 `R.ok(dto)`；不再有 `R.ok(serviceMap)` 透传。
- **JSON 字段名、嵌套结构、类型保持不变**；`Long/long` 继续用 `Long/long`，保持全局 Long→String 序列化行为。
- 动态业务数据（`formData`、`opinionData`、`definition`、`data`、`variables`、`samples`）作为 DTO 的 `Map<String,Object>` / `Object` 字段保留。
- 整份响应就是动态字典的（`categoryCounts`、动态表单查询行），用带 `@JsonAnyGetter` 的 DTO 包装，JSON 结构不变。
- 原 Map 条件性省略 key 的（`instanceRelation` 的 NONE 分支、`trigger/preview`、`script/preview`），DTO 用 `@JsonInclude(NON_NULL)` 保持“null 不出现”；并加序列化测试锁定。
- 内部私有辅助方法可以继续用 Map，不纳入“API 返回 Map 清零”口径。

## Phase 3：最终验证

1. 全仓 grep：Controller/Service 公共 API 返回类型中不再出现 `Map` / `List<Map>` / `PageResult<Map>`（内部动态字段和私有方法除外）。
2. FQCN 残余扫描：代码引用为零；例外清单逐条可解释。
3. `MAVEN_OPTS="-Xmx2g" mvn -q -DskipTests compile`、`mvn -q test-compile`、`mvn -q test` 全绿；若测试依赖外部数据库/中间件无法启动，保留原始失败输出并说明环境缺口，不伪造通过。
4. 对 6 个复杂响应补 JSON 契约测试：`myInstanceDetail`、`instanceRelation`、`myInstanceCount`、`analyticsSummary`、`categoryCounts`、动态表单查询行。
5. 前端不改；若最终发现必须改 JSON 契约，先停下报告，不在本批擅自改前端。

## 风险与边界

- 最大风险是 FQCN 脚本误判同名类型或把字符串/注释当类型引用；用词法扫描 + 全量编译 + 残余扫描三重校验。
- 第二风险是 DTO 改变 null/缺省 key 语义；对条件性响应加 `@JsonInclude` 和序列化测试，前端消费字段逐一对照。
- `categoryCounts`、动态表单行使用 `@JsonAnyGetter` 保持 JSON 完全不变；若你认为这仍不算“DTO 封装”，需要改前端契约，届时单独确认。
- 不修改业务逻辑、不新增权限、不改数据库、不改前端。
