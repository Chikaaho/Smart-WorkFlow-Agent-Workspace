### P51 Owner 补充需求定义（2026-08-30）

#### 1. 产品目标

将当前根知识/治理仓整体通用化为 Agent Coding Engine。Engine 完整保留当前根工作区除具体 coding 仓库以外的治理、知识、记忆、规划、探索、回执、待办、契约、模板和 Harness 结构；其中的 Smart-WorkFlow 项目内容改为通用初始内容或项目接入后生成的实例数据。新项目拉取到工作区并填写最小项目说明后，即可由代理按统一规则开始规划、探索、执行、验收和交接。

#### 2. 核心边界

- Engine 标准仓库完整保留当前根工作区的非 coding 结构，包括但不限于：`system.md`、`roles/`、`knowledge/`、`memory/`、`product/`、`todo/`、`search_task/`、`search_fallback/`、根说明与 Harness 入口、治理契约、Validator、Hooks、skills、模板及归档结构。
- 这些目录不是可选插件：它们共同构成 Engine 的标准工作区协议。干净 Engine 中应带有可初始化的目录骨架、通用说明、规则、schema、模板和空状态入口；项目接入后产生的知识、记忆、任务、回执、产品方向和待办继续落在对应标准结构中。
- Engine 与当前后端、前端两个 coding 项目在仓库、目录引用、版本、发布和生命周期上彻底解耦；Engine 的安装、升级、测试和发布均不得要求这两个项目存在。
- Engine 的通用初始内容不预置具体业务代码、产品状态、功能清单、端口、构建命令、测试基线、迁移版本、模块名或 Smart-WorkFlow 业务事实；空白 Engine 在没有项目时仍应能够独立完成治理契约和标准目录完整性自检。
- 新项目接入只要求把代码仓库拉取到 Engine 工作区，并在一份最小项目说明中填写：coding 项目是什么、目标与边界、代码仓路径或多仓关系、必要工程规则、启动方式和验证入口。填写完成后，Engine 自动把该说明作为项目上下文入口，不要求修改通用 `system.md` 或 `roles/`。
- `knowledge/`、`product/`、`memory/`、`search_task/`、`search_fallback/`、`todo/` 等标准结构由 Engine 统一管理；其通用规则属于 Engine，接入后写入的项目事实属于当前 coding 项目实例。不同项目实例不得共享当前状态、历史回执、任务入口或业务记忆。
- 当前根知识/治理仓在完成通用化后就是 Engine 本体；当前后端、前端仓库仅作为一个 coding 项目的多仓代码输入。迁移过程需保留现有三角色工作流、知识、记忆、历史回执、终态校验和活动任务入口的语义，但 Engine 的通用发布物不携带该项目的实例事实。

#### 3. 新项目最小接入流程

1. 获取一份包含全部标准非 coding 结构的干净 Agent Coding Engine；
2. 在 Engine 工作区拉取一个或多个待开发代码仓库；
3. 填写唯一项目说明，声明“这个 coding 项目是什么”、仓库关系、目标边界、工程规则及验证入口；
4. Engine 校验项目说明和仓库路径，为标准 `knowledge/`、`memory/`、`product/`、`search_*`、`todo/` 等结构建立该项目的初始入口；
5. 用户声明会话角色后，代理直接按 Engine 的完整工作区协议和项目说明开始工作，无需为每个新项目复制或手工改写通用治理规则。

#### 4. 后续设计必须回答

1. Engine 的独立仓库/包边界、版本策略、安装方式和升级方式；
2. 全套标准非 coding 结构、通用模板、项目实例数据及 Harness 适配层的目录与依赖方向；
3. `system.md`、`roles/`、终态契约、Validator、Hooks、skills 与项目工程宪法之间的扩展点；
4. 多仓项目、单仓项目和不同构建工具如何通过声明式配置接入；
5. 现有 Smart-WorkFlow 历史状态、回执和记忆如何无损迁移且不建立第二状态源；
6. 最小项目说明的固定 schema、必填字段、校验方式，以及单仓/多仓的统一表达；
7. 新项目初始化、切换、卸载和归档时如何保证项目实例之间零状态串扰；
8. 如何用一个非 Smart-WorkFlow 示例工程证明 Engine 不依赖当前业务语义。

#### 5. 初步验收边界

- 同一 Engine 版本能够分别驱动 Smart-WorkFlow 和至少一个独立示例工程完成角色门禁、探索、方向下发、执行回执、规划验收及合法终态闭环。
- 在未放入任何业务仓库的全新工作区中，Engine 的 `system.md`、`roles/`、`knowledge/`、`memory/`、`product/`、`todo/`、`search_task/`、`search_fallback/`、治理契约、Hooks 和模板等标准非 coding 结构齐全，能够通过目录与治理契约自检。
- 干净 Engine 的通用发布物不存在当前后端/前端仓库依赖、Smart-WorkFlow 专属模块名、固定端口、测试计数、迁移版本或业务功能状态。
- 将一个新示例仓库拉入工作区并只填写最小项目说明后，无需修改 Engine 通用规则或重建标准目录，即可在既有 `knowledge/`、`memory/`、`product/`、`search_*`、`todo/` 体系内完成首次角色门禁、项目探索、方向下发和执行回执闭环。
- 同一 Engine 工作区先后接入两个无关项目时，两者的知识、记忆、状态、任务、回执和待办无交叉命中，移除一个项目不影响另一个项目或 Engine 本体。
- Smart-WorkFlow 迁移后既有活动入口、状态单一源、历史回执路径和 Validator 语义可追溯，关键治理契约具有自动化回归证据。
- Engine 升级失败时能够回退到上一兼容版本，不破坏项目实例数据和历史审计链。

### P21 Owner 补充需求定义（2026-08-29）

#### 1. 产品目标

在既有最小设备控制链上补齐供应商无关的 IoT 设备管理，使系统形成以下统一领域链：

`Provider / Adapter → 产品与物模型 → 设备 → 设备功能/行为 → 命令与事件 → 流程实例与执行结果`

流程设计或节点配置能够选择设备来源和已配置的设备功能；流程真实流转到目标触发点时，通过对应 Adapter 控制设备，并把设备受理、执行、失败或超时结果关联回流程实例。

#### 2. 设备管理

- 支持设备新增、编辑、停用、删除/注销、详情查询和分页筛选；设备具有稳定业务标识、所属产品、接入 Provider/Adapter、分组/标签及必要扩展属性。
- 支持设备生命周期和连接状态：未激活、离线、在线、禁用等明确状态，以及最后上线、最后上报、最后命令时间；管理状态与实时连接状态不得混为一个字段。
- 支持设备认证信息或连接配置的安全维护、轮换和脱敏展示；业务接口和日志不得明文泄露密钥。
- 支持设备详情统一查看物模型能力、最新属性、事件/行为记录、命令记录和关联流程，不因厂商不同改变上层使用方式。

#### 3. 通用物模型与行为管理

- 产品级维护物模型，至少覆盖属性、事件、行为/动作三类能力；每项包含稳定标识、名称、数据类型、约束、读写语义和说明。
- 物模型支持草稿、校验、发布和版本留痕；已绑定设备及已发布流程引用稳定版本或快照，后续修改不得悄然改变历史执行语义。
- 行为/设备功能可配置输入参数、输出结果、超时、重试边界、幂等要求和 Adapter 操作标识；参数在保存流程配置和实际调用前均需校验。
- 属性读写、行为调用、事件上报和执行结果采用统一业务模型；厂商专属字段留在 Adapter 配置或扩展区，不泄漏成流程模块的硬编码依赖。

#### 4. 自定义 Adapter 扩展

- 除内置腾讯 IoT Provider 外，允许开发者编写并注册自定义 Adapter，以接入其他云平台、网关、HTTP/MQTT 协议或本地设备。
- Adapter 对上提供统一能力契约，至少声明：设备身份映射、支持的物模型能力、状态查询、属性读写、行为调用、事件/结果接收、健康检查和错误归一化。
- Adapter 支持独立配置、启停、连通性检查和能力声明；密钥等敏感配置必须安全存储并脱敏，Adapter 不得绕开现有权限、审计和数据隔离。
- 新增自定义 Adapter 时，上层设备管理和流程模块无需增加厂商专属分支；不支持的能力必须明确返回 `UNSUPPORTED` 或等价失败，不得伪装成功或静默降级。
- 自定义 Adapter 的加载、隔离、超时、异常和资源释放必须可控；单个 Adapter 故障不得拖垮流程引擎或其他设备通道。

#### 5. 流程选择设备并触发设备功能

- 流程设计或节点动作配置支持选择“设备来源 + 设备功能 + 参数映射 + 触发时机 + 失败策略”。
- 设备来源至少支持：设计时固定设备、发起时由有权限用户选择、从表单字段/流程变量解析；运行时只能选择状态允许且具备目标功能的设备。
- 设备功能只能从所选设备已发布物模型/行为中选择；保存和发布流程时校验设备来源、功能版本及参数映射，避免运行时才发现基本配置错误。
- 触发点必须绑定明确流程事件或节点结果，例如审批通过、节点进入或节点完成；同一流程事件在重试、回调重复或服务恢复时不得造成设备功能重复执行。
- 每次触发生成唯一命令记录，保存流程实例、节点/任务、设备、功能版本、请求参数快照、Adapter、状态、时间和结果；流程侧与设备侧可用同一关联标识互查。
- 支持同步受理、异步回执、失败和超时。失败策略可配置为阻断流转、记录失败后继续或进入受控重试，但不得仅显示“触发成功”而实际没有设备命令或执行结果。
- 流程发起人、审批人和设备管理员按权限查看必要结果；设备选择、功能配置、命令触发和人工重试全部进入审计记录。

#### 6. 验收边界

以下行为证据全部成立，才可核销 P21 的“完整设备管理与流程联动”范围：

1. 能创建产品与已发布物模型，配置至少一个属性、一个事件和一个带输入/输出的设备行为，并把设备绑定到该能力版本。
2. 能完成设备新增、修改、停用、状态/最后上报查看、筛选及详情回查；停用或无目标能力的设备不能被流程选中或触发。
3. 流程能够分别使用固定设备和运行时选择设备，选择已配置功能并完成参数映射；无权限、参数非法、能力不匹配在保存或触发时被明确拒绝。
4. 流程真实流转到配置触发点后只生成一次设备命令；命令请求、Adapter 调用、设备结果和流程展示使用同一关联标识，刷新后仍可回查。
5. 成功、设备拒绝、离线、超时、重复回调和重试均有真实行为证据；界面状态与持久化结果一致，不存在伪装成功。
6. 至少一个非腾讯的自定义示例 Adapter 在不修改流程与设备管理核心逻辑的前提下完成注册、连通性检查、能力声明和一次真实契约调用；Adapter 异常被隔离并归一化返回。
7. 腾讯 IoT、模拟/测试通道与自定义 Adapter 复用相同上层契约；厂商专属配置不进入流程通用模型。
8. 权限、数据范围、敏感配置脱敏和审计可通过不同账号的真实请求验证；页面无明显空白、假按钮、错误成功提示或关键状态错位。

#### 7. 非目标与保留边界

- 本需求不承诺一次覆盖 OTA、规则引擎、时序数据分析、地图、告警中心、数字孪生可视化或海量设备压测；这些能力另行规划。
- 自定义 Adapter 是受统一契约约束的代码扩展点，不等于允许普通用户在页面执行任意脚本。
- 真实腾讯账号、物理设备现场联调和原生 MQTT 仍保留在 P21，不因通用 Adapter 或模拟链通过而自动视为完成。
