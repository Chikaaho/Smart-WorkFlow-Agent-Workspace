# P24 / I49：job/storage 普通角色菜单可达性探索

> **角色确认**：本会话角色：规划；委派角色：执行。

## 任务目标

确认 V29 已新增的 job/storage 菜单为何仅超管可达，查清现有内置角色、菜单授权关系、迁移先例与测试入口，为规划层形成一个边界明确的单功能需求方向提供证据。

## 需要回答的问题

1. V29 当前新增了哪些菜单记录（菜单 ID、父子关系、权限标识），为什么没有写入 `sys_role_menu`？普通角色即使具备接口 permission，前端菜单仍不可见的完整链路是什么？
2. 当前系统有哪些内置角色或 seed 角色可作为默认授权对象？请列出角色 ID、角色 code、既有菜单授权范围及其来源；不得凭名称推断角色用途。
3. 历史迁移中，新增菜单后同步 `sys_role_menu` 的既有模式是什么？至少给出 1 个可复用先例，并说明 H2/PostgreSQL 双方言差异。
4. 若要让“非超管的指定内置管理角色”在全新数据库与既有数据库升级后都能看到 job/storage 菜单，最小数据迁移范围是什么？是否只需后端 Flyway，前端和业务 Java 是否可以零改动？
5. 当前最高迁移版本、可用下一版本、相关迁移目录分别是什么？是否存在版本冲突或跨模块迁移顺序风险？
6. 现有永久 Flyway 全链测试能否覆盖新增迁移？还需要哪些最小断言，才能证明：菜单记录存在、指定角色获得授权、非目标角色未被扩大授权、双方言脚本对齐？
7. `knowledge/known-issues.md` 中 I49、功能清单、需求池 P24 与当前代码是否一致；是否存在会改变规划方向的冲突或更新事实？
8. 给出推荐的最小目标角色集合；若无法仅凭现有产品语义唯一确定，请列出可选角色及各自影响，让规划层向用户只确认一个关键选择。
