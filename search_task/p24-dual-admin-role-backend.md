# P24 扩展：双层管理员角色模型后端探索

> **角色确认**：本会话角色：规划；委派角色：后端执行。

## 任务目标

核实当前 seed 账号/角色、超管保护、角色可配置能力及 job/storage 权限记录，支撑“userId=1 不可变超管 + 可配置 admin 管理员角色”需求方向。

## 需要回答的问题

1. 当前 `userId=1` 的 seed 用户、roleId=1 的 `superadmin` 角色及二者绑定关系分别在哪些迁移中建立，当前字段值和后续迁移变化是什么？不得回传密码、密钥或其他敏感值。
2. 后端目前对 userId=1 的修改、删除、启停、密码重置、角色解绑/替换分别有哪些保护；roleId=1 / code=`superadmin` 的修改、删除、停用、菜单重配分别有哪些保护？逐入口给出结论。
3. 当前“超管”运行时判定是否完全依据角色 code 包含 `superadmin`；是否还有 `userId==1`、roleId==1 或权限通配符等旧判定残留？
4. 新增 seed 角色 code=`admin`、名称“管理员”、允许日常配置时，`built_in`、status、data_scope 等字段应如何沿用现有契约；哪些字段决定能否编辑/删除？
5. 现有角色 CRUD、用户角色绑定、菜单绑定 API 是否足以配置该角色；是否缺少后端写入链路或保护边界？
6. job/storage 完整可用所需菜单与按钮权限记录有哪些？仅授权菜单 16-19 是否会出现“菜单可见但接口 403”；如缺按钮记录，请列出最小权限集合和现有 Controller 权限标识证据。
7. 对全新库和已升级库，V31 最小安全迁移如何处理可能已经存在的 code=`admin` 或目标主键冲突，才能避免覆盖用户已有角色配置？这里只返回可选策略和影响，不替规划层作产品决策。
8. 现有后端测试可覆盖哪些行为；还需要哪些最小测试证明：超管身份关系不可变、运行时判定不依赖 userId、admin 可配置、job/storage 可用、迁移双方言一致？
